Q1

MCP 到底是什么？一句话能说清吗？

MCP（Model Context Protocol，模型上下文协议）是 AI 应用的"USB-C 接口"——一个开放标准，让任何大模型应用（Claude Desktop、Cursor、Claude Code……）都能用同一种方式连接外部工具和数据源。

图1：不管左边是谁、右边是谁，中间都用同一个 MCP 标准对话——就像所有设备都改用 USB-C 充电口

它由 Anthropic 在 2024 年 11 月发布并开源，现在已经是 AI 工具生态的事实标准。这份清单收录的每一个"MCP 服务器"，就是一根"插在 USB-C 上的设备"：有的让 AI 读文件，有的让 AI 查数据库，有的让 AI 操作浏览器。

Q2

为什么需要它？没有 MCP 之前人们怎么做？

早期让 AI 调用外部工具，靠的是各家自己发明的 "Function Calling"（函数调用）格式。每接一个新工具，都要为每一个 AI 应用单独写一遍对接代码。

图2：3 个应用 × 3 个工具，以前要写 9 套对接；有了 MCP，各写一次即可（3+3）

MCP 把 "M × N" 的对接爆炸变成 "M + N"：应用方只需实现一次 MCP 客户端，工具方只需实现一次 MCP 服务器，双方即插即用。这正是所有"协议"（HTTP、USB、蓝牙）的取胜逻辑——先统一语言，再谈连接。

Q3

MCP 的整体架构是什么样的？

MCP 是经典的"客户-服务器"架构，但有三个角色，容易混淆：

角色是什么例子
Host（宿主）你直接使用的 AI 应用，负责跑大模型Claude Desktop、Cursor、Claude Code
MCP Client（客户端）宿主内部维护的连接器，一个连接对应一个，负责和某个服务器说话宿主程序里内置的 MCP 模块
MCP Server（服务器）独立的工具提供方，把某种能力（文件/数据库/浏览器…）包装成标准工具本清单里的 4086 个项目
图3：一个 Host 里可以同时插多个 Client，每个 Client 只和一台 Server 通话

类比：Host 是电脑，Client 是USB 口，Server 是U 盘/键盘/摄像头。电脑不会直接跟 U 盘里的闪存芯片打交道，中间永远隔着标准化的接口层。

Q5

MCP 服务器本质上是什么？消息长什么样？

MCP 服务器本质就是一个"会说 JSON-RPC 的普通程序"——没有魔法。最常见的形式是命令行进程：宿主把它作为子进程启动，通过标准输入/输出（stdio）一行一行地互发 JSON 消息（也有走 HTTP+SSE 的远程形式）。

MCP 建立在 JSON-RPC 2.0 之上，日常只用到三种消息：请求（要结果）、响应（给结果）、通知（不用回复）。实际报文： 

{
  "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": { "protocolVersion": "2024-11-05",
              "clientInfo": { "name": "demo", "version": "0.1" } }
}
→ 服务器回： {"result": {"serverInfo": {"name": "filesystem", "version": "0.2.0"}, ...}}

协议约定了几个核心方法，全部一眼能懂：

方法方向作用
initializeClient → Server握手：报版本、报身份（每次连接必做）
tools/listClient → Server"你有哪些工具？"——返回名字+描述+参数表
tools/callClient → Server调用某个工具，附带参数
notifications/initializedClient → Server通知：握手完成（无需回复）

正因为如此简单，实验里我们甚至不需要任何 AI，就能直接和服务器"聊"起来——后面的动手实验会亲手证明这一点。

Q9

MCP 和 Function Calling、LangChain 工具是什么关系？

三个概念经常被混着说，其实是不同层次的东西：

图7：三层各司其职——能力层、标准层、应用层

模型最终"动手"靠的还是 Function Calling 这类原生能力；MCP 只是让"工具的供货方式"标准化了。框架（LangChain、CrewAI）也纷纷加了对 MCP 的适配——一个 MCP 服务器写好后，可以被所有支持它的框架直接挂载，这正是协议的价值。类比知识库里已有的概念：MCP 对工具生态的意义，类似 [[构建流水线与Pass]] 里"统一接口的 Pass"——每个阶段按约定接入，流水线即可自由替换组件。

Q10

我想自己写一个 MCP 服务器，难吗？

不难——这是 MCP 生态最惊喜的地方。用 Python 的 FastMCP 框架，一个普通函数加一行装饰器就是一台 MCP 服务器：

from fastmcp import FastMCP

mcp = FastMCP("我的工具箱")

@mcp.tool
def add(a: int, b: int) -> int:
    """把两个整数相加"""          # ← 这行注释就是给模型看的"工具描述"!
    return a + b

mcp.run()                        # 以 stdio 方式启动，等宿主来连

要点：函数签名 + 类型标注自动生成参数表（JSON Schema）；docstring 就是工具描述，直接决定模型会不会用它（呼应 Q4 的 TDQS）。清单的 Frameworks 区还列了 TypeScript 版 FastMCP、Rust 的 TurboMCP、Go 的 gomcp 等——你熟悉哪门语言都有对应 SDK。

💡 实战路径：把你已有的任何脚本/内部 API 包一层 @mcp.tool，它立刻可以被 Claude Desktop / Cursor / Claude Code 调用——这是"给自己的工作流造工具"的最短路径。
Q11

让 AI 读写我的文件、数据库……安全吗？

两大真实风险，装任何第三方服务器前都要想：

风险是什么怎么防
过度授权服务器拿到的权限大于实际需要（如整个 C 盘）启动时只授予最小目录/只读模式（实验里我们只给了一个 sandbox 文件夹）
提示注入恶意网页/文件内容里藏着"指令"，诱骗模型去调用危险工具敏感操作要人工确认；社区有专门的安全网关类服务器（如清单里的 warden）做工具扫描

类比知识库的 [[质检Gate与自我纠错循环]]：把每个 MCP 工具调用当成流水线上的一个 Pass，在"AI 想调用"和"真正执行"之间设一道人工/规则 Gate——宿主（如 Claude Code）默认就会对敏感操作弹出确认，别图省事一路放行。

Q12

本地服务器和远程服务器有什么区别？

本清单收录的都是本地自装型；还有一类"远程 MCP 服务器"（另一个姊妹清单）只需在客户端填一个 URL。对比：

🏠 本地（本清单）☁️ 远程（姊妹清单）
安装clone/npm 安装，写进宿主配置文件，宿主作为子进程拉起（stdio 传输）零安装，填 URL 即用（HTTP/SSE 传输）
数据去哪不出你的电脑，适合隐私敏感场景（本地文件、内网数据库）数据经过对方服务器，适合 SaaS 类能力
典型例子filesystem、sqlite、playwright 浏览器控制各家官网提供的在线搜索/地图/CRM 服务器
运维自己升级、管依赖对方维护，但你受制于对方可用性
💡 经验法则：碰"你自己的数据"用本地，碰"互联网上的服务"用远程——和图例里 🏠/☁️ 的划分完全一致。

实验小结 & 下一步

你已经完成了宿主连接 MCP 服务器的全部核心动作：握手 → 发现工具 → 调用工具。真实宿主（Claude Desktop 等）只是在这之上加了"让大模型来决定调哪个工具"。下一步延伸：在 Claude Desktop 的配置文件 claude_desktop_config.json 里加上这个同样的 npx @modelcontextprotocol/server-filesystem 命令（指向你的某个工作目录），就能用自然语言让 AI 操作文件——你会发现它说的每一句话，背后都是你今天亲手发过的那种 JSON 消息。

🪤 坑与备忘

📓 中文 Windows + Python：跑脚本前建议 setx PYTHONUTF8 1，避免 GBK 编码导致中文读写报错（本实验脚本已显式用 UTF-8，不受影响）。

📓 npx 首次运行慢：第一次 npx -y @modelcontextprotocol/server-filesystem 会下载包，别以为是卡死；之后再跑是秒起。

📓 stdio 服务器不"打印"：MCP 服务器的 stdout 是协议通道，调试信息走 stderr——写自己的服务器时往 stdout 随便 print 会直接破坏协议。

📓 协议版本：握手时报文里的 protocolVersion 需要双方都认识（实验用 2024-11-05），版本不匹配会被服务器拒绝。
