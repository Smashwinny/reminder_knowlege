01

它是一个 shell，还是终端模拟器？

ELYTerminal 是显示与交互外壳，bash/zsh 才解释命令。 终端模拟器把程序输出的字符和控制序列画成网格，并把键盘、鼠标输入送回程序。换主题不会让错误的命令变正确，也不是替换编译器。

当前主线以 Rust + GPUI/Ely 构建原生窗口，终端内核是 alacritty_terminal。比如 printf 输出颜色，shell 决定运行哪个程序，终端决定颜色怎样显示；把这三层分开，才知道卡顿或光标错误该查谁。

依据：README.md；Cargo.toml

02

会话侧栏为什么比堆窗口容易管理？

会话是一个独立终端运行上下文，不等于系统窗口。官方文档描述左侧新建、关闭、切换和拖动重排，右键复制会话会采用原 shell 与上次报告的目录；不是把进程内存完整克隆。

可将“服务、测试、文档”放成三行，先命名再切换，减少寻找窗口。关闭仍可能结束正在跑的进程，不能因侧栏方便就忽略代价。本次没有启动 GUI，因此“比原生终端快多少”仍须用同一任务计时，不能由作者喜爱推出效率提升。

依据：docs/zh_cn/features.md:L17-L24

03

PTY 和 OSC 133 怎样让窗口理解命令阶段？

PTY（伪终端）是一对供程序交互的字节端点；OSC（操作系统命令控制序列）是终端字节流中的元信息。本项目 shell 集成用 A=提示符开始、B=输入开始、C=输出开始、D=退出状态 标出命令边界，不靠“屏幕安静了”猜运行结束。

本次真实 Bash 子进程输出了 18 个 OSC 133 标记；false 后出现 D;1，成功命令后出现 D;0。目录则由 OSC 7 报告，含 % 的目录被编码为 %25。字节捕获与真实上游 Rust 解析器连接，仍不是 GPUI 完整数据通路验收。

依据：assets/shell-integration/bash/elyterminal.bash:L25-L83；src/term/marks.rs

04

Ely 宠物是 AI 吗？状态可信吗？

原帖把待机打盹、错误流汗描述为有趣的体验；官方文档把宠物动作关联到等待、失败、完成和工作。这是状态可视化，不是一个能理解工作质量、替你保证成功的 AI 审核员。

当前 status.rs 的显示优先级是 blocked → error → working → done → idle，同类取最近报告；进程可用 OSC 7501 上报状态。应把上报者当作信号来源：done 不能证明文件正确。可类比已学的“可逆派生状态”，但本次没有驱动宠物动画或验证通知。

依据：docs/zh_cn/features.md:L16-L18；src/term/status.rs:L337-L353

05

点击命令就能移动光标，原理是什么？

不是直接改一块屏幕，而是把点击翻译成 shell 可接受的输入。 当前源码只在 shell 处于 Reading、程序没有跟踪鼠标时进入点击移动；默认路径按目标位置计算左右方向键数量。支持点击事件的 shell 则接收 SGR 鼠标按下序列。

例如在 echo hello 末尾点 h，可转换为向左 5 次。进入 vim 的备用屏幕、点到提示符或无有效输入区时会被拒绝。原帖的流畅体验有代码依据，但不等于任何程序、任意屏幕位置都能用；本次只实际验证 readline 接收方向键，未运行这个 GUI 点击函数。

依据：src/term/click.rs:L42-L92；src/term/click.rs:L154-L182

06

中文、宽字符和软折行为什么容易点错？

“列数”与“方向键次数”不同：中文一般占两列，但只需一次逻辑光标移动；组合字符也不能按 UTF-8 字节数计算。源码统计时跳过宽字符占位格，并把软折行接成同一输入行，还把点击过行尾的位置夹到有效终点。

上游 click/tests.rs 包含中文、软折行、尾空格、两行提示符和备用屏幕用例；这是读到测试源码，不是本次执行。下一轮 GUI 验证应用 中文ab、长命令折行及带组合音标字符，比较实际插入位置和输入内容，不可拿本次 ASCII readline 成功替代。

依据：src/term/click.rs:L55-L92；src/term/click/tests.rs:L61-L90

07

为什么透明背景会让选中态“不明显”？

原帖明确把问题限定为“macOS 27、某些背景、侧栏高亮对比度”，这是作者观察，不是普遍缺陷证明。最终颜色受窗口底色、壁纸、透明度和高亮叠加共同影响；当前代码也有 glass alpha 与选中色 alpha，不能只审单个主题 hex 值。

本次用任意教学色板做 3 张纯色壁纸 × 3 档不透明度的 9 个场景。淡填充对相邻背景的比值为 1.020013–1.298294:1；即使加固定深色边，在深壁纸且 25% 不透明度时也只有 2.234323:1。所以“加深一条边就万无一失”也不成立；这些数值不是 Ely Light 或 macOS 实测。

依据：src/themes/chrome.rs:L7-L50；原帖 note_tweet；自编 contrast.json

08

怎样把“看得清”变成可复验标准？

先明确测的是文字、焦点环还是用于识别状态的图形，再记录真正相邻的颜色。W3C 的 WCAG 2.2 非文本对比度说明，以必要状态指示与相邻颜色 3:1 为参考；不能把“焦点前后两个不相邻状态的色差”直接当这个标准。

练习采用 C=αF+(1−α)B 的通道混合，再做 sRGB 线性化：L=.2126R+.7152G+.0722B，比值为 (L高+.05)/(L低+.05)。黑白=21、同色=1 的两条端点断言通过。要做实机验收，还须在最差背景找必要标记、增加形状/文字提示，并检查键盘焦点，不能据一个颜色对宣称整应用无障碍通过。

依据：W3C SC 1.4.11；exercise/lab.py contrast

可配置功能多，哪些边界值得先守住？

设置变化会立即写入平台配置文件。当前 README 说 JSON 无法解析或数值越界会阻止启动并指出字段，不会覆盖坏文件；实际排障前应备份并比较更改，不直接删除配置。这条是文档阅读结论，本次未做坏配置启动实验。

侧边 Git 面板能暂存、丢弃和提交，这些不是“只读展示”；命令行控制默认关闭，打开后可读会话、发命令。本轮不启用控制端口、不读取令牌、不使用用户 shell 配置。实验为 Bash 子进程设置空白 HOME，避免把个人启动脚本或历史误收入日志。

如何判断适合自己，而不是被可爱宣传说服？

把“喜欢”与“任务结果”分开：同一台 Mac、同一 shell 和字体，轮换 ELYTerminal 与现用终端，做 3 会话切换、命令中部修错、长命令软折行、等待提示和最差壁纸识别。每个样例重复 5 次，记录完成时间、误操作数和是否需要猜状态；次序交替，避免熟练效应偏差。

它能给我什么？五个具体用途

① 把项目终端整理成“工作台”

让服务、测试、笔记各有会话名，快速定位和切换。真正验证的是找会话耗时、误关次数，而不是截图里有多少漂亮面板。复制会话不代表复制运行现场。

② 减少命令中部修错的摩擦

点击正在输入的命令定位，再键盘修改；保留备用屏幕、鼠标跟踪、中文与软折行的例外清单。Linux 本轮只验证方向键进入 readline，不保证原生点击效果。

③ 用余光注意等待与失败

会话标记、宠物和通知可帮助发现“程序等我了”；但最终结果仍读退出码、输出文件或业务证据，不把宠物欢呼当质量门禁。

④ 为自己的界面做透明度压力测试

复用九场景色板脚本，逐个检查壁纸、底色、淡高亮和边线。增加文字与形状冗余，再在实机确认，避免从孤立设计 token 推导整窗可读性。

⑤ 学习一个可追溯的开源拆解方法

固定 SHA → 识别两个小组件 → 真跑 PTY 和上游测试 → 把结论写回候选提案。可以用于其他终端协议学习，不碰用户密钥、生产会话或付费 API。

本页前 3 项为产品功能用途；不是本次原生体验的成功声明。后 2 项练习与方法已在本云端执行。
