01它究竟帮我省掉哪一步

先找候选，再做设计判断

假设工程师小林要为小团队做 SaaS 数据仪表盘。过去，他会分别找配色、字体组合、页面结构与交互准则。UI UX Pro Max 把这些资料整理成 CSV，并用 Python 检索和规则组合给出一个起点。SaaS 指通过网络提供的软件服务；本实验的产品需求是人为构造的普通示例。输出是建议文本和结构化数据，不是已经可用的网站。

例子：把“从空白开始找参考”缩成“检查候选是否适合”，并没有省掉布局实现、用户研究和界面测试。

02怎样写一个不会含糊的输入

把用途和约束写成可检查的词

Brief 是简短需求说明。这里的核心引擎主要在英文 CSV 上做词法匹配，也就是看词语是否出现以及出现在哪些记录中。先写产品类型、主要任务、使用者和明确约束，避免把一句“高级一点”当作可验证需求。实验保存完整查询字符串；任何追加词都属于输入变化，不能悄悄当成只改颜色。

例子：例子：一个 SaaS dashboard 的需求，加上 accessibility 或 dark mode 等词后，要重新检查产品类别与规则命中，不能只看背景颜色。

03为什么要把资料分成不同的域

问什么，先决定查哪一张表

Domain 是检索域，例如 product 查产品类型，style 查视觉风格，color 查颜色，typography 查字体搭配。每个域在 CSV_CONFIG 中指定文件、搜索列与输出列。显式给域相当于先选书架；自动判域是程序依据关键词打分后挑选入口。Stack 则是 React 等技术栈的实现指南，不能把一个技术栈名当成视觉风格。

例子：查 color 的结果能提供语义颜色，却不能替代 ux 域中的键盘操作准则；两个问题需要不同的证据。

04CSV 数据库和实时设计研究有什么不同

一个固定快照，不是全网答案

CSV 是用逗号分隔的表格文本，一行是一条记录，一列是一种属性。这个版本把产品、风格、配色、排版等知识存进本地表格。固定提交号就像给教材拍下一个快照，便于重跑和追责；它不会自动读到最新设计趋势，也不能保证每条建议覆盖你的业务。数据里的性能或无障碍标签仍是建议资料，不是本项目对真实页面的测量。

例子：看到某风格的 Accessibility 字段，不等于你的表单已通过键盘、读屏或对比度验收。要检查真实渲染后的页面。

05BM25 为什么把某条记录排在前面

相关性分数不是成功概率

BM25 是一种词法相关性排序算法。它考虑查询词在记录中出现的次数、这个词在全库是否稀有，以及记录长度。稀有而匹配的词通常更有区分力；重复出现的收益会逐渐减弱；很长的记录也不会只因字多就无限占便宜。本实现默认 k1=1.5、b=0.75，分词前还做小写化、同义词归一与停用词过滤。 实际搜索还会叠加身份直达、阈值等规则。

例子：分数 6 不是“60% 正确”，也不应直接跨不同数据表解释为统一质量等级。独立重算真实产品表的 BM25，只验证实现的排序行为。

06没有可靠匹配时工具会不会乱答

检索拒答和生成回退要分开检查

Abstention 是在证据不足时不返回候选。检索会结合词语覆盖率、阈值和精确标识匹配等路径决定是否返回结果。设计生成器又是另一层：它可以在产品没有命中时使用 General 类别和默认值。因此“搜索结果为零”与“生成器仍能输出一个设计系统”可以同时发生。看见排版完整的文本，不能反推出每个字段都来自命中的资料。

例子：本轮分别用无关 UX 查询和另一条无关生成需求测试两层；它们不是同一输入的受控 A/B。检查 count、reasoning_default 和 source_identities，别只看有没有报错。

07所谓推理和多域搜索实际怎样运行

这里验证的是确定性代码路径

本地流程先检索产品类别，再读取该类别的规则，随后组合多个域的结果。Decision Rules 是限定格式的条件与动作：比如查询含 dashboard 时激活某些约束。解析器只接受允许的条件和动作，不把 CSV 内容当 Python 执行。固定输入和固定数据下，这是一条可重跑的确定性路径。README 的 AI-powered 与 parallel 描述不能代替对这段代码的检查。

例子：所检查的 _multi_domain_search 用 for 循环逐域调用 search；本实验没有调用模型、外部付费服务或并行搜索框架。

08输出颜色为什么未必等于 CSV 原始值

原始值、派生值、默认值要分层

Design Token 是颜色、间距等可复用设计值。此项目的 source_identities 记录候选来源，source_derivations 记录部分派生过程，例如暗色方案可能由原配色改写背景与前景等字段。若没有候选，还可能落到代码里的默认值。来源身份、原始单元格和最终 token 因而不是同一个东西；不能把每个输出色号都标成 CSV 原值。

例子：对暗色输出，应同时展示：选中哪条颜色记录、那条记录的原色号、采用了哪条派生标记、最终色号。

09只追加 dark mode 为什么值得警惕

查询字符串变化可能牵动整条链

如果把 dark mode 追加到完整需求后，变化的不只是配色偏好：产品检索也会看到这些词，类别和后续规则都可能改变。这是词法系统的输入敏感性。本实验专门比较完整查询、命中的类别、规则、颜色来源和输出，不把变化归因于一个不存在的独立模式开关。若产品类别漂移，应该先处理检索约束，再评价颜色是否合适。

例子：对照表中的每个结果都保留完整输入。一次观察只能证明该样例、该版本的行为，不能推断所有 SaaS 查询都会如此。

10怎样给一条设计建议建立证据链

从最终建议走回具体原始记录

Traceability 是能从结果回到来源的能力。先保存完整输入、提交号与结果，再用 source_identities 定位对应 CSV 行，记录相应的原始字段；最后单列派生与默认部分。行号便于阅读，稳定身份更适合核对，因为插入新行会使后续行号移动。实验为产品、规则、风格、配色、字体和页面模式建立对应关系，并验证身份能否唯一命中。

例子：“推荐某风格”至少应能回答：哪条 style 身份、来自哪个固定文件、为何被选中、哪些字段被代码改写。

11它和已经学过的技能包有什么关系

复用旧概念，把篇幅留给新机制

AgentSkills 的说明与脚本包装、DESIGN.md 的设计约束载体、DesignToken 的统一变量，可以直接连接到本项目。这里新增的是 CSV 按域检索、BM25 词法排序以及原值与派生值的追溯。RAG 与 RRF 只是相邻概念；本次并没有实现向量检索或混合检索。Agent-Reach、Archify 已学内容仅作目录桥接，不重复展开，也不把目录其余项目算作完成。

例子：沿用“事实与判断分离”：CSV 的记录身份是可核查事实，“这个方案适合我的用户”仍是需要验证的判断。

12做到什么程度才算有证据地学会

代码跑通只是验收的一层

本实验可以证明：固定源文件可被读取、搜索与规则能运行、输出能追到记录、负向和对照样例能暴露边界。它不能证明生成建议已经让真实网站更好看、更易用或提高转化率。后续若真的做网站，还要验收布局、移动端、键盘操作、读屏、对比度、性能，并做与目标相称的用户测试。这里没有实际建站、调用模型、安装全局技能或运行持久化写入。

例子：把验收写成两列：本次已验证的程序行为；尚未验证的产品效果。不要拿第一列替代第二列。

五项能力与四个用途

  1. 按域检索设计资料：明确产品、风格、颜色、排版等问题属于哪一组资料，减少无目标浏览
  2. 组合设计系统建议：把风格、语义颜色、字体与页面模式整理成一份可审查起点
  3. 应用可读规则与约束：查看哪些固定条件被触发，区分规则选择与人工判断
  4. 提供来源与派生线索：用身份找到 CSV 原记录，辨认暗色派生及默认回退
  5. 支持本地可复现实验：在固定快照上比较查询、负向输入与检索排序，不依赖模型 API

能用在什么地方

  1. 做新产品原型前，快速形成一份候选设计方向，交给设计者逐项筛选
  2. 给已有设计规范补一份可追溯的调色、排版候选清单，保留选择理由
  3. 把英文需求改写成更明确的产品与约束词，观察类别漂移并修正输入
  4. 学习检索系统的负向测试与来源追溯，把这套验货方式迁移到其他资料型工具

关键结果与限制

加词后换了产品类别

输入 SaaS dashboard accessible 命中 SaaS (General)；完整输入追加 dark mode 后命中 Smart Home/IoT Dashboard。这证明本版本此样例的查询敏感性，不是独立颜色参数的因果对照。

base: SaaS dashboard accessible dark_words: SaaS dashboard accessible dark mode

空检索与默认推荐同时存在

无关 UX 检索返回0条；无关生成需求 zzqqxx flarble blorpt 的 reasoning_default=true，产品与规则来源为空，但仍有回退建议。不能把输出完整误当成资料命中。

原值与派生都有可核对路径

三个生成样例的来源身份逐一解析；每个样例的20个颜色输出字段与所选配色原字段一致。另一个固定 SaaS 类别的暗色函数对照改变7个颜色字段并标记 derived-dark，焦点环/背景数值对比度约3.4541。这个数值不是页面无障碍合格证。

本地实现是顺序检索与确定性规则

普通生成链实际顺序调用 product、product、style、color、landing、typography 共6次搜索；中间重复的产品结果之后被最初结果覆盖。README 的5路并行描述与这段代码不同。

验证计数与覆盖范围分开

61项自建证据检查全过；选定上游73个测试方法全过。未运行全部测试模块、完整CI、持久化与覆盖测试。固定快照和样例可重现，不等于任意需求都能获得正确设计。

BM25 分数不是概率；代码测试通过不是设计、美感、可用性或转化率验证。本次没有实际建站、调用模型或收费服务、全局安装、执行持久化/force 覆盖。
