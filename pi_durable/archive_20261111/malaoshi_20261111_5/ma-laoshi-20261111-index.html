从浅到深 · 1—2

Q01 Pi Durable 是升级后的 Pi 命令行吗？

【源码证实】不是。它是供开发者嵌入的持久化 Agent 运行库，不是给现有终端加一个开关。Harness 管存储与调度，Conversation 管记录，Task 管可恢复状态机，Document 管应用状态。二者共用模型接入组件，不代表用户的终端自动获得 Durable 能力。

证据：核心概念 · 包与依赖

Q02 0.84.2 能直接用本文配置吗？

【源码证实】不能当作内置功能使用。用户本机安装的是 pi-coding-agent 0.84.2，不是 pi-durable 1.5.2；旧版依赖没有 pi-durable。本篇固定在新库源码上实验，需要独立 Node 项目，不升级也不修改用户机器。旧会话向 Durable 迁移、CLI 扩展桥接均【未验证】。

证据：0.84.2依赖声明 · 包与依赖

从浅到深 · 3—4

Q03 断点恢复究竟保存什么？

【源码证实】保存的是已提交记录、Document 和任务 checkpoint，不是 CPU 指令或整个进程内存。重开同一存储后 resume() 推进未完成任务；运行阶段可能从顶部重入，所以外部写入不能无条件重试。【我实际运行过（云端隔离环境）】官方恢复测试包含流式中断与压缩重开，不是物理断电测试。

证据：恢复与提交去重 · 进度丢失与恢复测试

Q04 两个实例怎么共享同一 SQLite？

【源码证实】prefix 会加在所有 Durable 表和索引名字前，不只是会话 ID 上。alpha_ 与 beta_ 形成各自 schema/metadata/records 空间。【我实际运行过（云端隔离环境）】同一文件两存储都分配 ID=2，读到各自不同内容，18 张表，重开 beta_ 仍为 BETA ONLY。

证据：表与索引前缀实现 · Node前缀验证

从浅到深 · 5—6

Q05 前缀隔离等于安全多租户吗？

【源码证实】不是。它是命名空间隔离；持有同一文件访问权限的人仍可直接读别的表。Node 打开前会校验 prefix，避免非法标识符；同一个 prefix 不应用于不协调的独立写入者。本实验只覆盖同进程两个存储，不覆盖多进程争用、授权或加密。

证据：Node前缀验证 · 前缀格式校验

Q06 压缩会把旧记录删掉吗？

【源码证实】不是。压缩增加 summary/head 标记，改变发给模型的活跃上下文，原始不可变记录仍在。【我实际运行过（云端隔离环境）】真实库+faux 摘要的回归测试检查 before 等于 after 的原历史前缀，且模型下一请求含摘要和保留轮次；这只证明组织流程，不证明真实摘要语义无损。

证据：真实压缩回归断言

从浅到深 · 7—8

Q07 System Message 顺序修复在哪里？

【源码证实】findBaseline 找到 head 之后完整的 pi.system；leadWithSystem 只把初始或基线系统消息前置，不把后续所有 system 一股脑前移。压缩保留 assistant 时旧逻辑可能让基线留在中途。【我实际运行过（云端隔离环境）】官方回归精确要求 roles=system,user,user,assistant,user，测试通过。

证据：baseline选择与前置 · 真实压缩回归断言

Q08 帖子说默认100ms，现在仍一样吗？

【作者说法】更新帖称进度提交间隔默认100ms。【源码证实】当前有两层：partialIntervalMs 与 outputIntervalMs 默认100ms；persistWithinMs 默认1000ms。1.5.0将内存可见进度与落盘延迟分离，因此不能把“100ms一次进度”解释为“100ms必落盘”。

证据：当前进度默认值 · 1.5.0延迟持久化

从浅到深 · 9—10

Q09 调大间隔到底省了多少？

【我实际运行过（云端隔离环境）】相同640字符faux流、100ms partial节流，persistWithinMs=0时27批提交/25批含文档改变；400时9批/7批。两次都 done。此处计量是 ControlledStorage 的逻辑批次，不是远端请求数、磁盘IOPS、收费金额或作者的性能倍数，实际部署需另测。

证据：只注册faux模型 · 进度丢失与恢复测试

Q10 正常关闭与崩溃会损失同样进度吗？

【源码证实】正常 close 会在关闭存储前刷出 held documents；failed Session 不再补写。【我实际运行过（云端隔离环境）】官方测试验证 clean close 保存 held partial；模拟 fail 则仅从已存内容恢复，并可能生成 aborted entry。测试通过不等于宿主强制休眠一定调用close；这部分【未验证】。

证据：close提交延迟状态 · 进度丢失与恢复测试

从浅到深 · 11—12

Q11 休眠是不是不用任何云资源？

【作者说法】帖子说待机不耗额外资源。【源码证实】sleeping task 不占一次活跃调用；onWake 把最早截止时间交给宿主、避免内部 sleep timer。宿主仍需持久存储、alarm 与重新唤醒执行，不能据此宣称零成本。【我实际运行过（云端隔离环境）】sleep/onWake 单测通过，未部署Cloudflare。

证据：持久睡眠 / 宿主唤醒 · 1.4.0睡眠与迁移

Q12 恢复是否保证工具恰好执行一次？

【源码证实】不保证外部效果 exactly-once。提交 requestId 可去重输入，但外部发送与本地提交之间存在故障窗。写工具应有幂等键、可核对回执和明确重放策略。只在自有测试环境注入故障；真实账号、用户reminder与付费模型均【未验证】，本篇不创建真实通知或日程。

证据：恢复与提交去重 · 阶段重入边界
