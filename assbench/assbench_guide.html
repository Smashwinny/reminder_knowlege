Q1 · Ass Bench 到底是个啥？

一句话：一个恶搞的"AI 跑分网站"——让各家前沿大模型按同一个提示词生成 3D 雕塑渲染图，按"保真度"排名，名字和内容都是整活。

推文原文（2026-09-08，735 万浏览）：跑 GPT 6 Astra 一周 + 每天人工转向，"已正式达到高保真臀部"，还要再自跑一个月、上更多款式，$1 就能在作品上贴你的网址贴纸。站点自称 "An interactive mannequin playground"。

工程视角：剥开段子，它回答一个严肃问题——"怎么让模型对着一个没有标准答案的目标，自己越做越好？" 推文里的关键词 loop / steering / fidelity score 就是答案的三块积木。

Q2 · benchmark 本来该长什么样？它哪里不科学？

benchmark（基准测试）：给模型出一套有标准答案的考卷，按答对率排名。正经 benchmark 有三件套：

三件套正经 benchmarkAss Bench
ground truth 标准答案有（标注数据集）没有——"美"没有标准答案
held-out 留出集有（防背题）没有
评分器确定性指标 / 人工标注启发式 + 人偶尔瞟一眼打字纠偏

README 自己都承认："Nothing here is scientific… a benchmark in the loosest possible sense of the word."（最不严格意义上的 benchmark）

学到什么：看到任何"跑分/榜单"，先问三连——有标准答案吗？有留出集吗？评分器确定吗？三连全挂的榜单，当营销看，别当事实用。

Q4 · 自改进循环怎么转？（核心机制）

自改进循环（self-improving loop）：不靠一次生成到位，而是让「生成 → 打分 → 修正」转圈，每一圈把上一圈的低分项变成下一圈的指令。仓库 README 的四步原文：

# 1. generate 拿当前种子 prompt + 转向注释，让模型生成一版输出 # 2. score rubric 评分器给输出打保真分 + 写"哪里要改"的 notes # 3. steer 把 notes 翻译成新的修正注释，追加到 prompt 尾部 # 4. repeat 回到第 1 步，每一圈的全部记录写进 runs/ 目录
图：generate→score→steer 循环（上方黄色块 = 爬山法的关键：分数只升不降）

爬山法（hill climbing）：循环里永远记住历史最高分及其 prompt，新的一圈分数更高就更新 best——像登山者只记自己到过的最高营地，保证"折腾半天至少不退步"。loop.py 全部逻辑只有 40 行：读种子 → 圈内生成/评分/写日志/更新 best → 转向。

Q5 · 它和反思模式 Reflection 有什么区别？

知识库里已有 [[反思模式Reflection]]：生成→批评→修改，双停止条件（达标即停 + 轮数上限兜底）。Ass Bench 循环是它的"跑步机变体"——不设质量阈值，靠人工转向 + 轮数上限，永远在跑。族谱对齐：

反思模式 ReflectionAss Bench 爬山循环
谁批评LLM 自己批评自己确定性 rubric + 人偶尔纠偏
停止条件达标即停 + 轮数上限轮数上限（--rounds），人不喊停就一直跑
记忆批评意见进上下文best prompt + best score 单变量
目标把这一份产出改到合格把生成配方（prompt）越调越强
风险过度自我批评评分器坏了就"优化了个寂寞"
选型口诀：改一份产出用反思；调生成配方（prompt 本身也是资产）用爬山。两者都依赖同一个前提——裁判要可信（[[LLM裁判与自动评估]]）。

Q6 · rubric 四维加权评分器怎么写？

rubric（评分细则）：把"好不好"拆成几个可打分的维度，各配权重，加权求总分。config.py 里的默认四维：

图：四维 rubric 加权（DimensionScore{value, note} → ScoreReport{dimensions, overall, notes}）

结构很干净：每维返回 0~1 分 + 一句人话评语，低于 0.5 的评语进 notes——notes 就是下一圈 steering 的原料。数据类只有三个（DimensionScore / ScoreReport / GenerationResult），20 分钟能读完全部源码。

Q7 · steering 为什么"少而小"才不漂移？

steering（转向）：每圈把得分最低的至多 2 个维度（steers_per_day=2）翻译成一句修正注释，追加到 prompt 尾部。steering.py 的注释说得极好：

原话："Keeping steers small and few per round is what keeps the loop from drifting."（每圈转向又小又少，循环才不跑偏）
图：转向步长与漂移——max_steers=2 限流就是防左边的红线

与知识库 [[修改与约束分离]] 完全同源：一次只改最少的东西，改完再看效果，单变量迭代才分得清"哪个改动起了作用"。

Q9 · 为什么要有 stub 桩后端和接缝？

model_client.py 定义了 ABC 抽象接口 ModelClient（一个 generate(prompt) 方法），目前只注册了一个 stub（桩）后端——随机编个输出编号的假模型。这是接缝设计（seam）：

图：接口是插排——stub 先插上让骨架跑通，真后端来了即插即换
可复用打法：任何"依赖外部服务"的项目，先造桩把骨架逻辑（循环、日志、CLI、report）全部跑通测好，真服务接入时只写一个子类。骨架的测试期不需要 API key、不花一分钱。与 [[双数据源适配器隔离]]、[[零依赖编程]] 同一思想家族。

Q10 · 上游评分器藏着什么大坑？

scorer.py 的占位评分器用 Python 内置 hash() 造 0~1 分——而 Python 的 hash 对字符串每个进程加盐随机（PYTHONHASHSEED）。实测铁证：

# 同一行代码，两个进程输出不同： 进程A: hash(('proportion','studio render')) = 2560065321882644929 进程B: hash(('proportion','studio render')) = -4392188187258516437 # 连跑两遍循环，同一 prompt 分数不同： 第1遍 Best score: 0.6450 第2遍 Best score: 0.6350
坑：分数不可复现 → "自改进"的爬坡曲线全是噪声，评分器必须确定性（[[确定性脚本]]：同输入同输出，裁判才可信）。修法：用 hashlib（跨进程稳定）或纯算术启发式。

第二个隐患：loop 只对 best 爬山，但 prompt 是在"当前 prompt"上持续追加——一旦中途走歪，best 是旧配方、prompt 已经变形，两者脱节。

Q11 · steer 无限累积会撑爆 prompt 吗？

会。steering.py 只追加、不去重、不设总长上限。实测第二遍循环的 best prompt：

studio render, soft rim light, … -- add more surface texture detail -- sharpen the silhouette edges; add more surface texture detail -- adjust proportions… … -- add more surface texture detail; improve shading … -- add more surface texture detail ← 同一句注释重复 4 次，prompt 单调膨胀

三重风险：上下文预算被吃掉（[[上下文预算与战略压缩]]）、互相矛盾的注释打架、旧注释污染新方向。我在实验版里的修法：幂等去重（注释已在 prompt 里就不再加）+ 达标停注（某维 ≥0.95 就不再为它转向）——两条一共 6 行代码。

Q12 · 循环死锁：注释在却没效果怎么办？

我第一次跑自己的实验版就踩了真死锁，卡在 0.4550 不动：texture 注释明明已经在 prompt 里，分数却永远是 0——而 steer 一看"注释已存在"就去重跳过，永远无法再引导这个维度。

图：幂等去重 × 参数耦合 = 自改进循环的隐蔽死锁（实测复现）
教训：给循环加"防重复"安全带时，必须保证每个 steer 注释独立生效（正交），否则安全带本身会把循环勒死。验证方法：跑 7 轮看分数是否封顶——封顶在 <1.0 就是死锁信号。

Q13 · 我能拿这个模式干什么？

把 generate/score/steer 三个槽位换成你自己的东西，这个 40 行的循环立刻迁移：

场景generate 生成什么score 怎么评steer 转什么向
提示词调优用 prompt 跑文生图/写作启发式或 LLM 裁判打分低分维度 → 补充指令
代码润色改写代码片段lint + 测试通过率（确定性！）报错/坏味道 → 修复指令
文案打磨改写标题/文案长度/关键词/AI味检测器扣分点 → 风格指令

铁律不变：评分器要确定性、转向要小步、prompt 要去重、best 要记牢。
