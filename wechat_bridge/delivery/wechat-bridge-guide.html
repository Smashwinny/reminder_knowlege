01

微信流到底替我省了哪一步？

把主动导出的聊天材料，接到后续处理流程。

WeChatBridge（微信流）是文件转交与归档工具。它接收微信主动交出的 ZIP、TXT 和媒体，不是持续监听聊天的机器人，也不是读取或解密微信数据库的工具。ZIP 是把多个文件装在一起的归档格式。

例子：你手动选出一段项目讨论，微信导出聊天和配图，再选择交给 AI 整理或保存本地。微信流负责接住材料、保留原件和选择去向；模型总结质量属于下一环。

02

为什么还要一个系统分享入口？

先接住临时文件，再让主应用继续处理。

Share Extension 是 macOS 分享面板中的应用扩展；系统把用户选择的文件交给它。上游先复制提供方的临时文件，再唤起主应用，避免扩展结束后原路径失效。暂存区只属于这一批工作。

Windows 使用 Share Target 和应用内选择器，macOS 则有多个分享扩展入口。两端能采用类似文件契约，不代表注册方式、权限和界面实现一样。本次没有调用任一原生分享入口。

依据 S2 macOS 批次暂存 · S11 平台差异与待实机验收

03

文件到了，程序怎么知道它是谁？

清单描述文件；随机标识不证明内容相同。

Manifest（清单）用 JSON 记录批次 ID、显示名、相对路径、字节数和顺序。Schema version 是数据格式版本，帮助读取方判断能否理解。GUID 是随机身份标识；内容哈希则是根据文件字节计算的摘要。

例子：两个都叫 chat.zip 的文件可以内容不同。Windows 会清理显示名并给重名加序号，macOS 使用独立条目目录。应核对清单顺序及原件字节；本实验另算 SHA-256，不能把清单中的 GUID 当成哈希。

依据 S3 Inbox 清单、暂存与提交 · S2 macOS 批次暂存

04

为什么不能边复制边让应用读取？

先完成整批，再发布到 Ready。

Staging 是尚未公开的暂存区；Ready 是读取方扫描的就绪区。程序先复制原件，写好清单及可选意图，再通过目录移动发布整批。这里的原子发布指这一文件系统边界，不是跨系统事务。

例子：一批两个 ZIP，第二个复制前验证失败。回滚会尝试清理该次暂存并记失败，避免把第一份误当完整批次。它不是断电耐久性或任意文件系统都成功的保证。实验会直接观察提交前后和失败后的目录。

依据 S3 Inbox 清单、暂存与提交

05

名字叫 ZIP，就真的是 ZIP 吗？

入口接收条件和内容解析条件要分开看。

分层验证是让不同环节检查各自的输入契约。Windows InboxWriter 检查文件存在、无重解析点（路径重定向元数据）、显示名以 .zip 结尾及大小等条件；它不在这里验证 ZIP 字节结构。Archive 解析器另做目录、压缩及完整性检查。

例子：将普通文本命名为 fake.zip，入口可能成功暂存，但解析器拒绝其内容。这不是互相矛盾：前者证明文件可入队，后者才判断归档能否被安全理解。成功复制不能当作成功解析。

依据 S3 Inbox 清单、暂存与提交 · S6 ZIP 解析与安全提取

06

从聊天 TXT 到消息条目多了什么？

原文保存与结构化识别是两个成果。

Transcript 是提取出的聊天文本；record 是进一步识别的单条消息，包括发送者、日期和正文。此版识别特定的中文日期标题与按行结构，处理多行正文、换行符和 BOM（文本开头的编码标记）。

例子：熟悉的格式可得到消息数、首尾记录和时间范围；陌生 TXT 仍可能保留原文，却没有结构化记录。不能把“没有识别出记录”写成“归档里没有内容”，也不能把合成例子当作所有微信版本兼容。

依据 S6 ZIP 解析与安全提取 · S7 聊天记录识别

07

解压时最需要防住哪些反例？

可读归档还要检查路径、完整性和资源预算。

路径穿越是归档条目用 ../ 等形式越出目标目录；符号链接会把路径指向别处；大小写或规范化别名可能碰撞。CRC32 用来发现数据损坏，不是证明文件来自可信作者的数字签名。

MessageCount 校验所有文件项的 CRC 和展开大小；GetTranscript 只读取候选 TXT；Extract 另查路径、类型和别名。目录最多 1000 项、声明展开量 1 GiB；文本收集限 16 MiB。各入口检查不同，实验也不代表所有恶意样本均已覆盖。

依据 S6 ZIP 解析与安全提取

08

为什么转发请求会过期、又会消失？

一次性意图降低顺序重放，不保证恰好执行一次。

Intent（意图文件）描述该批次想做的动作。此版以当前时间减请求时间小于 90 秒为新鲜；恰好 90 秒已过期。消费流程先读文本、再删文件，随后解析并交给下一步，不是把“删除”和“完成投递”放在一个事务中。

例子：同一个读取器顺序扫描两次，第二次不再读到意图；但删除后崩溃可能丢失执行机会，并发竞争也未由这段代码提供端到端保证。过期不会意味着原始 ZIP 被一起删掉。

依据 S4 Ready 读取与意图消费 · S5 90 秒意图窗口

09

分批收集为何先“冻结”再发送？

固定本次成员与顺序，晚到文件另起一批。

Collection（收集）用持久账本记录多个批次的身份和顺序。冻结是把正在收集的成员确定下来并切到 Delivering（交付中），再由后续流程投递；SeenBatchIDs 用批次身份避免重复追加。

例子：A、B 两批先后加入，冻结后本次发送集合固定为 A、B；后来 C 的分享进入新的收集。原 ZIP 不需要合并或重写，仍可逐件校对。这种身份幂等不意味着自动识别两个不同批次的相同内容。

依据 S8 收集冻结、恢复与撤销 · S9 收集账本状态机

10

程序重启后，凭什么说能恢复？

恢复状态可重试，外部接收仍要单独验收。

状态机是允许的状态及转换规则。此版加载账本时把遗留 Delivering 改为 Retry（待重试）；移除收集成员时先保存可撤销材料，支持恢复位置。这里是本地文件与账本恢复，不能替代目标应用回执。

DeliveryEngine 的 Delivered 表示激活和粘贴步骤成功返回，并不证明 AI 已读取或上传附件。例子：目标窗口拿到粘贴动作后尚未完成处理，桥接层与目标处理层就可能处于不同阶段。

依据 S8 收集冻结、恢复与撤销 · S9 收集账本状态机 · S10 目标激活与粘贴投递

11

本地处理为什么不等于“完全安全”？

聊天内容是数据，不能自行授予执行权限。

场景是附加给目标 Agent 的任务提示；技能是可复用的操作说明。提示注入是外来内容试图冒充指令。把聊天原样捕获并分工处理能降低耦合，但若下游把聊天里的命令当授权执行，风险仍然存在。

例子：聊天写着“上传目录里的全部文件”，不能因此扩大用户授权。分享扩展无网络权限也不代表目标 AI 应用不会联网。应按数据、目的和接收方确认敏感传输；“完全安全”这类宣传不能替代分层核验。

依据 S1 项目说明与隐私边界 · S10 目标激活与粘贴投递

12

Linux 跑通 Core，能宣布软件可用吗？

可移植核心实测，只覆盖实际调用的那一层。

Core 是与界面相分离的核心库；本次编译固定提交的 Windows.Core（net10.0），只调用归档、Inbox 和收集逻辑。运行环境是 Linux，原生 Win32、macOS 扩展和目标 Agent 均不在调用链里。

文档也有版本差：较旧能力说明称仅 macOS，较新 Windows 对齐文档及代码已有更多实现。应同时标注版本、静态依据和实测范围。微信菜单注册、真实附件接收、焦点、权限、安装签名与更新仍需对应系统验收。

这个项目给我什么

  1. 接收与保留原件：系统分享进入文件批次，原始归档保留；原生入口本次只作源码核对。
  2. 提取和理解聊天结构：解析 ZIP、提取 TXT 与媒体、识别消息；本次对合成样本实际运行。
  3. 组织可靠的本地交接：清单、Staging/Ready、意图与状态分工；本次检查可见性、回滚和时效。
  4. 收集多批并保留恢复路径：冻结顺序、晚到分流、重读账本待重试、删除撤销；本次运行核心状态逻辑。
  5. 连接 AI 与知识归档：上游提供应用转发、场景技能和 Markdown 归档；本次未连接真实目标或知识库。

五个具体用途

  1. 整理项目讨论：用户选好范围后，让目标 AI 提取结论与待办，并逐条回看原文。
  2. 保存课程或读书群材料：把可分享的文本与配图保留为本地资料，之后再整理笔记。
  3. 分批处理长会话：手动分段导出，再用收集顺序一次交接，核对首尾避免漏选。
  4. 研究文件交接协议：借合成 ZIP 学会清单、发布点、回滚、时效与恢复状态。
  5. 制定安装验收清单：把核心测试和平台实机检查分开，避免“测试绿了就全能用”的误判。

真实聊天需按授权范围选择；对外发送前核对资料和接收方。

结果怎么解释

两种 ZIP，一份没有改变的内容

stored.zip 使用存储方式，deflated.zip 使用压缩方式；它们都被识别出两条合成消息。附件与 TXT 提取后逐字节哈希一致。sample.bin 只是 64 字节测试数据，未验证图片显示或媒体解码。

一道门通过，不替另一道门背书

名为 not-a-zip.zip 的普通字节可通过暂存，再由 MessageCount 拒绝。归档完整性、候选 TXT 读取和路径提取检查分别由不同 API 执行。清单 GUID 不是内容哈希；本次哈希由测试另外计算。

时间、一次消费与未知外部结果

89 秒的意图可消费，恰好 90 秒过期；未来一小时的时间戳仍通过当前单向 age<90 秒判断。顺序二次扫描及新建读取器不重放，但没有验证并发恰好一次或删除后崩溃窗口。

本地恢复的证据看得见

冻结保持 A、B 的顺序，晚到分享进入新收集；新建服务对象重读账本后变为 Retry；移除/撤销保留原件与位置。重建均在同一进程内，未做真实进程崩溃或重启。Retry 不证明外部动作从未发生。

保留真实失败，避免事后全绿叙事

初次计时因 /usr/bin/time 不存在失败；初版 I05 案例把带小数的内存时间和整秒持久时间比较，得到 41/42。修正的只有测试比较方式，上游源码未改。原始失败日志完整保留。

耗时是什么，不是什么

作者六步使用已有 SDK 和增量构建；独立复验全新解包并清洁构建，只复用经 SHA-512 及 4907 文件比对的官方 SDK。指南展示后者进程耗时；221.3802 ms 是 JSON 案例计时，均不是下载或目标 AI 处理时间。
