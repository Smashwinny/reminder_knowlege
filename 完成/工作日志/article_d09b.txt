[blockquote] 跑通 Demo 不等于完成交付。
Agent 最危险的不是报错，而是做错了还显示“已完成”。
你怎么证明，这个 Agent 真的可以上线？

[unstyled] 我最近测了一个资料研究 Agent。它交回一份结构完整、带引用的报告，页面显示“已完成”。我随手点开三条链接：一条失效，一条根本支撑不了报告里的结论，另一条只来自搜索结果摘要。把同一个问题重新跑一遍，结论又变了。

[unstyled] 这正是最危险的 Agent 失败：它没有报错，甚至看起来已经完成了。

[atomic]  

[unstyled] 所以这篇文章，我会从一个目录、30 条真实任务和几段检查规则开始，搭出一套最小可用的 Agent Evaluation Framework。它要回答三件事：任务有没有做成，失败发生在哪里，新版本能不能发布。

[unstyled] 下面就用这个资料研究 Agent 做一遍。

[unstyled] 当前有两个版本。v1 使用原来的模型和 Prompt，v2 换了模型，修改了 Prompt，又增加一个搜索工具。我们的目标是决定 v2 能不能替换 v1，交给真实用户。

[unstyled] 整套流程可以压成八步：

[blockquote] 明确发布决策
→ 定义成功与不可接受的失败
→ 建立评测数据集
→ 记录最终结果与执行轨迹
→ 配置 Rules、Judge 和 Human
→ 重复运行并比较 v1/v2
→ 设置发布门禁
→ 把线上失败送回评测集

[unstyled] 第一版不需要先买平台，也不用一开始研究几十个 benchmark。一个目录、一批真实问题、几个检查脚本和一份清楚的评分标准，已经能把最重要的闭环跑起来。

[header-two] 先决定这次 Eval 要回答什么

[unstyled] 很多团队搭 Eval 的第一步，是搜索“Agent Eval 用什么框架”，然后开始比较平台、Judge 模型和指标。

[unstyled] 工具很快就会装好。真正要做的决定仍然没有写下来。

[unstyled] 同一套 Agent，可以因为不同决策需要完全不同的评测。

[atomic]  

[unstyled] 如果要在两个模型之间选一个，重点是同一批任务上的质量、成本和延迟。如果要判断能不能开放自动退款，越权操作和错误退款就是硬门槛。如果只是改了一段 Prompt，最重要的是新版本有没有修好目标问题，同时让其他场景发生回归。

[header-two] 先把“做完”写成可以检查的条件

[unstyled] Agent 最容易给人制造一种错觉：它做了很多步骤，所以任务应该已经完成。

[unstyled] 搜索了十次，不等于找到了正确资料。成功调用保存工具，也不等于报告内容正确。最后回复“已完成”，更不能证明外部系统真的发生了变化。

[unstyled] 资料研究 Agent 的完成条件可以先写成五条：

[ordered-list-item] 报告包含问题、结论、证据、限制和来源。

[ordered-list-item] 每个关键结论至少有一条原始来源支持。

[ordered-list-item] 来源链接能够打开，引用内容与结论一致。

[ordered-list-item] 证据不足或来源冲突时，明确保留不确定性。

[ordered-list-item] 报告写入指定目录，文件能够重新打开。

[unstyled] 这五条描述的是 Outcome，也就是任务最后留下了什么。

[unstyled] 接着写 Hard Failure。它们一旦发生，整个任务直接判失败：

[unordered-list-item] 编造不存在的来源；

[unordered-list-item] 把不支持结论的材料当成证据；

[unordered-list-item] 访问任务范围外的数据；

[unordered-list-item] 未经允许向外部系统写入；

[unordered-list-item] 工具已经失败，仍然宣称任务完成。

[unstyled] Hard Failure 不能和普通质量指标混成一个平均分。

[unstyled] 假设报告完整度 95 分，语言质量 90 分，却编造了一条关键来源。算术平均可能仍然很好看，真实业务不会接受这个结果。

[unstyled] 安全、权限和关键事实正确性更适合做 gate。成本、延迟和语言质量可以做 optimization metric。前者决定能不能放行，后者帮助我们在可用版本之间继续优化。

[unstyled] 现在再为语义质量写 Rubric。

[unstyled] “回答质量高”没有办法稳定评分。换成下面这种行为描述，人与 Judge 才有共同标准：

[blockquote] 证据支持度

通过：每个关键结论都能在所引原始来源中直接找到支持；
部分通过：主要结论有支持，但次要结论存在轻微外推，并明确标注；
失败：关键结论缺少来源、引用错位，或来源与结论矛盾。

[header-two] 建立第一批数据：30 条足够开始，远远不够上线

[unstyled] 数据集决定 Eval 最终在保护什么。

[unstyled] 如果评测集里全部是资料充足、问题清楚、工具正常的任务，Agent 很容易得到高分。真实用户不会只提交这种问题。他们会省略条件，会把两个要求写在一起，也会问资料中根本没有答案的问题。

[unstyled] 第一版先做 30 条：

[unordered-list-item] 12 条常见任务；

[unordered-list-item] 6 条边界或缺失信息任务；

[unordered-list-item] 4 条来源冲突任务；

[unordered-list-item] 4 条工具失败或空结果任务；

[unordered-list-item] 2 条已经发生过的失败；

[unordered-list-item] 2 条权限或对抗任务。

[unstyled] 这 30 条的作用是跑通框架，尽快发现大问题。准备做发布门禁时，再扩到 100–300 条。任务越重要、切片越细，所需样本越多。

[unstyled] 真实生产 trace 通常最有价值，因为它保留了用户真实说法、工具状态和环境噪声。还没有线上数据时，可以请领域专家写案例，再用模型生成边界题和对抗题，最后由人检查。模型生成的数据不能直接当金标准，否则出题和答题可能共享同一种偏差。

[unstyled] 这里不一定要保存一段唯一的标准答案。

[unstyled] 开放式研究任务可能有多种合理表达。我们更需要保存必须覆盖的事实、允许的差异、必须引用的来源，以及什么情况下应该拒答。

[unstyled] 数据集至少分成四份：

[unstyled] dev 用来日常开发，可以反复查看；holdout 在正式比较时才运行，防止团队不断针对题目调 Prompt；regression 保存历史事故；challenge 保存低频但高风险的边界和对抗任务。

[unstyled] 这四份结果应该分别报告。

[unstyled] 如果把 challenge set 和日常流量混在一起，总体通过率会被刻意设计的难题拉低；只看真实流量，低频安全风险又会被大量普通任务淹没。

[unstyled] 数据还会过期。工具 Schema 变了，政策更新了，用户开始提出新的问题，原来的测试集就不再代表当前系统。给每个数据集加版本、负责人和刷新日期，比不断往里面追加题目更重要。

[unstyled] 一个很实用的增长规则是：每次线上事故都要变成新的 regression case。

[unstyled] 问题被修好，只解决了今天。把事故放进回归集，才能防止三个月后的另一次改动把它重新带回来。

[atomic]  

[header-two] Outcome 和 Trajectory 要分开看

[unstyled] 传统 LLM Eval 常常可以写成：

[blockquote] Input → Model → Output → Score

[unstyled] Agent 中间多了一条会改变的路径：

[blockquote] Goal
→ Plan
→ Tool Call
→ Observation
→ Re-plan
→ Environment Change
→ Final Output

[unstyled] 最后报告正确，过程仍然可能有问题。

[unstyled] 它可能先访问了一个禁止使用的数据源，发现不对以后才换回允许的资料；也可能调用了 30 次搜索才碰到答案，成本已经失控。反过来，一条完全合理的执行轨迹也可能因为最后保存失败，没有交付结果。

[unstyled] Outcome Eval 先检查任务终态：

[unordered-list-item] 目标文件是否存在；

[unordered-list-item] 要求字段是否完整；

[unordered-list-item] 引用是否有效；

[unordered-list-item] 关键结论是否有证据；

[unordered-list-item] 外部系统是否真的产生目标状态。

[unstyled] Trajectory Eval 再检查执行过程：

[unordered-list-item] 该用的工具有没有用；

[unordered-list-item] 工具参数是否合法；

[unordered-list-item] 有没有调用禁止工具；

[unordered-list-item] 空结果和错误码是否被正确处理；

[unordered-list-item] 失败后有没有恢复；

[unordered-list-item] 是否发生无意义循环；

[unordered-list-item] 停止时是否已经满足完成条件。

[atomic]  

[unstyled] Anthropic 在 Agent Eval 方法中强调，Agent 的状态性、工具调用和多轮轨迹会让评测明显复杂于单轮模型回答。最终结果与执行过程需要分别设计 grader。Anthropic：Demystifying evals for AI agents

[unstyled] 每次运行都留下证据：

[atomic]  

[unstyled] 对会修改状态的 Agent，环境终态比最后回复更可信。

[unstyled] 代码 Agent 应该真正运行测试。SQL Agent 应该执行查询并检查结果。退款 Agent 要核对退款记录是否出现。资料研究 Agent 则要重新打开报告，检查链接、字段和引用关系。

[unstyled] NVIDIA 在 Agent Evaluation 方法里也把工具使用当作一等信号：允许哪些工具、必须调用哪些工具、最大调用次数和预期参数，都可以进入任务定义与轨迹评分。NVIDIA：AI Agent Evaluation

[unstyled] 没有 Outcome，我们只能判断答案看起来对不对。没有 Trajectory，失败后不知道该改模型、工具还是流程。

[header-two] 三层 Grader：能确定的用规则，模糊的交给 Judge，高风险留给人

[unstyled] 评测开始后，很快会遇到一个问题：谁来打分？

[unstyled] 全部交给人工，质量高却很难扩大规模。全部交给 LLM Judge，速度快，但 Judge 自己也会判断错误。只写程序规则，又覆盖不了开放式内容的语义质量。

[blockquote] 一个更稳妥的组合是 Rules + Judge + Human。

[unstyled] Rules 负责确定性检查

[unstyled] 资料研究任务里，下面这些事情可以直接用程序检查：

[unordered-list-item] JSON 是否符合 Schema；

[unordered-list-item] 必填字段是否缺失；

[unordered-list-item] 文件是否存在；

[unordered-list-item] URL 是否能解析和访问；

[unordered-list-item] 工具参数类型是否正确；

[unordered-list-item] 调用次数是否超限；

[unordered-list-item] 是否调用禁止工具；

[unordered-list-item] 环境终态是否符合预期。

[unstyled] 能用环境状态验证的结果，不要只让另一个模型读一遍然后说“看起来已经完成”。

[unstyled] 确定性检查便宜、稳定，也容易排错。它的限制同样清楚：链接能打开，不代表链接支持结论；字段填满，也不代表内容正确。

[unstyled] LLM Judge 负责语义判断

[unstyled] Judge 更适合判断这些问题：

[unordered-list-item] 结论是否得到引用内容支持；

[unordered-list-item] 是否遗漏重要限制；

[unordered-list-item] 来源冲突是否被准确呈现；

[unordered-list-item] 最终回答是否真正回应用户目标；

[unordered-list-item] 执行轨迹有没有明显绕路或不合理步骤。

[unstyled] 每个 Judge 只评一个清楚维度，会比“请给这份报告打一个总分”稳定。

[unstyled] 比较 v1 和 v2 时，Pairwise Judge 往往比两个独立绝对分更直接：给它同一个问题下的 A/B 结果，让它按 Rubric 选更好的一份或判定持平。

[unstyled] A/B 的顺序要随机，系统名称也要隐藏。Judge 可能偏爱出现在某个位置的答案，也可能把更长的回答误认为更好；使用与被评模型相同的模型时，还要关注 self-preference。

[unstyled] G-Eval、MT-Bench 等研究证明了强模型作为评价器的可用性，也暴露出这些系统性偏差。G-Eval；Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena

[unstyled] Human 负责标准与争议

[unstyled] 人不应该机械地给每条输出打分。

[unstyled] 更值得花人力的地方是：

[unordered-list-item] 业务专家定义 Rubric；

[unordered-list-item] 两到三位评审建立一批 gold label；

[unordered-list-item] 人处理评审分歧；

[unordered-list-item] 高风险和 Judge 低置信 case 转人工；

[unordered-list-item] 定期随机抽查自动评分结果；

[unordered-list-item] 人从线上记录中发现新的 Failure Mode。

[unstyled] 随机抽查不能省。

[unstyled] 如果只检查 Judge 主动标记为失败或不确定的样本，会漏掉它非常自信地判错的情况。高置信错误往往更值得关注。

[unstyled] Google 关于软件 patch 评测的研究也指出，人类评审本身会有分歧；共享且清楚的 Rubric 可以先提高人工一致性，再用人工校正过的标准支持 LLM Judge。Google：Human-in-the-Loop Framework for Reliable Patch Evaluation

[atomic]  

[unstyled] Judge 自己也要过 Eval

[unstyled] LLM Judge 是一件测量工具，不是标准答案。

[unstyled] 上线前准备 100–500 条由专家确认的 calibration set。比较 Judge 与人工标签的一致程度，同时检查它对严重错误的 recall、不同任务切片的表现，以及遇到证据不足时是否愿意 abstain。

[unstyled] 平均一致率不能说明全部问题。

[unstyled] 如果 Judge 对普通文风评价很准，却经常放过伪造引用，它仍然不适合给资料研究 Agent 做发布门禁。各类错误的重要程度不同，必须单独报告。

[header-two] 一次成功，还不能叫可靠

[unstyled] Agent 的输出带有随机性。模型采样会变化，搜索结果会变化，工具延迟和环境状态也可能变化。

[unstyled] 一个任务跑成功一次，只能说明这一次成功。

[unstyled] 假设某个 Agent 单次成功概率是 80%。在近似独立的情况下，连续五次全部成功的概率是：

[blockquote] 0.8⁵ = 32.8%

[unstyled] 这就是 pass@k 和 pass^k 的区别。

[unstyled] pass@k 表示运行 k 次，只要有一次成功就算通过。它适合代码探索、搜索候选方案等允许多次尝试的任务。

[unstyled] pass^k 表示连续 k 次全部成功。企业每天自动生成日报、处理订单或修改系统状态，更关心这种稳定性。

[unstyled] 用户只给一次机会时，单次 task success 最接近真实体验。任务要反复自动运行时，pass^k 会更快暴露问题。

[atomic]  

[unstyled] 因此，重要 case 至少重复运行 3–5 次。测试同义改写、字段缺失、工具返回变慢和来源顺序变化，看看系统是否还能稳定工作。

[unstyled] Princeton 的 Agent Reliability 研究把可靠性拆成 consistency、robustness、predictability 和 safety 等方面，并指出能力提升不会自动带来同等程度的可靠性提升。Towards a Science of AI Agent Reliability

[unstyled] 比较 v1 和 v2 时，使用同一批 case 做 paired evaluation。

[unstyled] 每个问题先跑 v1，再在相同初始状态下跑 v2。这样可以直接看到哪些 case 从失败变成功，哪些从成功变失败。两个版本分别拿一批随机问题，任务难度差异会把系统差异混进去。

[unstyled] 最终报告至少包含：

[unordered-list-item] Whole-task success rate；

[unordered-list-item] 关键任务的 pass^k；

[unordered-list-item] 每类 Failure Mode 的失败率；

[unordered-list-item] 各风险、难度和工具状态切片的结果；

[unordered-list-item] Cost per successful task；

[unordered-list-item] p50 和 p95 latency；

[unordered-list-item] Tool error 与 recovery rate；

[unordered-list-item] Unauthorized action rate；

[unordered-list-item] 95% confidence interval。

[unstyled] 这里不要做一个“综合质量 87.4 分”。

[unstyled] 总平均最容易藏住问题。v2 可能让常见任务提升 8 个百分点，同时让来源冲突任务退化 15 个百分点。混在一起以后，最后只剩一个看起来略有上升的数字。

[unstyled] 置信区间也不能省。

[unstyled] 100 条任务里，成功率从 80% 涨到 83%，并不自动等于 v2 已经变好。二元成功率在这个样本量下本来就有几百分点的波动。样本不足时，更诚实的结论可能是“没有发现重大回归”，还不能证明它显著更优。

[unstyled] 安全失败尤其要小心。跑了 100 次没有出现越权，只能说明这 100 次没有观察到。常用的粗略估计是：如果 n 次独立试验出现零次失败，95% 置信水平下，真实失败率上界约为 3/n。100 次零失败，对应的上界仍然约为 3%。

[unstyled] 低频、高损失的风险需要专门的 challenge set、更多试验和系统硬控制，不能只靠平均流量中的零次观察。

[header-two] 把指标变成 Release Gate

[unstyled] Eval 跑完以后，最容易出现另一种浪费：报告里有很多图，团队仍然不知道要不要发布。

[unstyled] Release Gate 要在实验前写。看到结果后再决定标准，人会自然地为自己喜欢的版本找解释。

[unstyled] Primary Metric 回答整体目标有没有进步。Non-inferiority 防止关键路径被牺牲。Safety 和权限是硬门禁。Reliability 看它能不能连续稳定完成。Efficiency 关注每次成功的成本，而不是每次请求的成本。

[unstyled] 为什么用 Cost per Successful Task？

[unstyled] 一个便宜 Agent 如果经常失败，需要重跑三次或者交给人返工，真实成本可能更高。只看单次 API 费用，会把廉价失败误认为优化。

[unstyled] 所有门禁通过后，也不用立刻把 100% 流量切过去。

[unstyled] 先跑 shadow。让 v2 接收真实请求但不影响用户，比较它和当前系统的差异。再做 canary，只开放给一小部分低风险流量，同时保留回滚。运行记录稳定以后，再逐步扩大。

[unstyled] Eval 的终点是一项可解释、可以回滚的发布决定。

[header-two] 线上失败要回到离线评测

[unstyled] 离线数据永远覆盖不完真实世界。

[unstyled] 用户会提出新的表达，外部网页会改版，API 会返回以前没见过的错误，业务政策也会更新。Agent 上线以后，Evaluation Framework 需要继续工作。

[unstyled] 完整闭环可以写成：

[blockquote] Production trace
→ Online Eval
→ Failure mining
→ Human review
→ Golden Set
→ Offline experiment
→ Regression
→ Release

[atomic]  

[unstyled] 线上不需要把每条记录都送给最贵的 Judge。可以先做便宜检查：工具错误、空输出、循环次数、成本异常、缺少引用、用户重试和人工接管。

[unstyled] 再从中抽取三类样本：

[unordered-list-item] 明确失败或触发告警的任务；

[unordered-list-item] Judge 不确定、不同 Grader 互相矛盾的任务；

[unordered-list-item] 正常流量中的随机样本。

[unstyled] 前两类帮助快速找到问题，随机样本负责发现系统没有意识到的新失败。

[unstyled] 人工复核以后，把代表性事故加入 regression，把新出现的高风险模式加入 challenge。如果问题来自某个新客户或业务切片，也要补进主测试集的抽样设计。

[unstyled] 每次修改 Prompt、模型、RAG、Skill、Tool 或 Workflow，都在同一套 case 上重新运行。一次只改一个主要变量，结果变了才知道是谁带来的。

[unstyled] 系统继续复杂以后，还可以测 Component Lift。

[unstyled] 例如固定 task、model、workspace 和 scorer，只改变是否加载某个 Skill：

[blockquote] Skill Lift = Quality(with Skill) - Quality(without Skill)

[unstyled] 同样的方法可以测 Prompt Lift、RAG Lift、Tool Lift 和 Memory Lift。这样得到的是组件的边际价值，不只是“新系统总分 85”。

[unstyled] 多 Agent 更需要这种对照。增加 Planner、Researcher、Critic 和 Verifier，会同时增加成本、延迟、交接损失和故障点。它应该和最强的单 Agent baseline 放在同一批任务上比较，证明质量增益足以覆盖新增复杂度。

[unstyled] 这部分可以留到第二阶段。

[unstyled] 第一版 Evaluation Framework 先把单 Agent、单工作流和一次清楚的发布决策跑通。工具应该跟着问题增加，不用第一天就做一套企业级 Eval OS。

[header-two] 从一个目录开始

[unstyled] Agent Evaluation 可以很小。

[unstyled] 第一天，你只需要一个明确任务、30 条真实 case、几段确定性检查和一份人工 Rubric。跑完以后，把失败分清楚，看看问题来自检索、工具、推理、验证还是停止条件。

[unstyled] 准备发布时，再把数据扩到 100–300 条，留下完整 trace，校准 LLM Judge，对重要任务做重复试验，给结果加上置信区间和切片分析。

[unstyled] 进入生产以后，接入 shadow、canary、告警和回滚。每一次真实事故，都变成下一次不会再犯的 Regression Case。

[unstyled] 回头看，整套方法一直围绕同一件事：

[blockquote] 先明确要做什么决定
→ 写清什么叫做完
→ 用真实任务建立数据集
→ 同时检查终态和轨迹
→ 用 Rules、Judge、Human 分层评分
→ 重复运行，看清可靠性
→ 用 Release Gate 做发布决定
→ 把线上失败送回评测集

[unstyled] Evaluation Framework 负责证明，它能不能稳定、安全、可解释地交回来。
