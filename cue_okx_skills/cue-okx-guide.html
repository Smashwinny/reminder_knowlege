Q1

这条教程链路是什么？

Cue（个人 Agent 应用）接入 OKX 官方技能包，走完"查资金→确认赎回与划转→确认买入方案→看回执→核对账单"的跨账户任务。学习价值不在"AI 帮你炒币"（作者自己承认证明不了盈利），而在agent 触达资金时的授权-确认-回读纪律——这是可平移到任何资金场景的工程范文。

Q2

审计发现①：OAuth 默认实盘（最大的坑）

官方 SKILL.md 原话："OAuth 用户只有单个隐式 oauth profile，没有 demo 字段；用 --demo 开启模拟盘，省略则实盘（默认）；不要用 --profile 切换模式。"——误以为"接了 OAuth 就有沙箱"的 agent，第一笔就可能在实盘花钱。

对比：API Key 模式通过显式 profile 区分 demo/live。固定文档明确 OAuth 没有 demo 字段，省略 `--demo` 就是 live；这不是“接 OAuth 就有沙箱”。

Q3

审计发现②③④⑤：pre-flight/占位符/确认矩阵/红线

发现原文要点平移价值
强制 pre-flight"任何情况下不得跳过 Step 0"；上游结论不替代亲自检查信任边界=每步自己验证
占位符陷阱未登录时的 site 字段是默认占位符("global")，须当 absent默认值的读者是程序不是人
写操作确认矩阵下单前逐项确认参数；USDT 金额须显式确认 quote_ccy/margin 模式；合约先核 ctVal 面值参数确认清单化
红线不自动处置"不要自动撤单或停 bot——呈报发现让人决定"agent 姿态=呈现选项
Q4

纪律的层次：提示词 vs 硬门

关键纪律写在 SKILL.md；文档还引用部分 CLI guard 行为，但本轮未审计 CLI 源码或验证硬门。提示词覆盖依赖 agent 遵守，真正的不可绕过性需机制测试。不能把“文档提到 guard”当作已证明底层强制，也不能把跨账户链当作原子事务。

Q7

资金操作四步纪律（交付物）

① 授权模式二选一：OAuth 默认实盘（--demo 才模拟）/ API Key 显式 profile
② 写操作逐项确认：参数确认矩阵 + 合约先核面值报总价
③ 执行后回读对账：看 fills 与账单，回执≠成交
④ 红线不自动处置：撤单/停机/平仓呈报人决定
Q8

跨账户任务的两个结构陷阱

  • 账户类型混说：教程操作的是交易所 Earn/资金/交易账户，不是链上钱包——两者授权模型完全不同，转述时别合并；
  • 工作区幻觉：安装回执里的 /workspace 只是 bot 的工作目录，推不出"代码跑在你本机"——执行位置的证据要单独拿。
Q9

给非交易场景的平移示例

同一四步纪律平移到：自动续费管理（授权→确认扣款项→回读账单→退款红线呈报）、广告投放 agent（授权→确认预算→回读消耗→超支红线）——凡 agent 碰钱，四步一个不能少。

一页总结

  • Omit --demo = 实盘：接入交易技能第一问默认姿态；
  • pre-flight 不可跳过，上游结论不作数；
  • 写操作确认矩阵+合约核面值；
  • 回执≠成交，红线不自动处置；
  • 提示词纪律≠机制硬门，CLI 实现要另审。
