02 / 从原帖走进清单

Q01 原帖到底列了哪18个？引用帖在说什么？

完整名单在 note_tweet，不在被截断的短文本里：1 Microban，2 MiniLoong，3 Poppy Humanoid，4 Otto DIY，5 pib，6 Mini Pupper，7 Petoi Bittle，8 Stanford Doggo，9 SpotMicro，10 OpenQuadruped，11 Puguette，12 SO-ARM100，13 RoArm-M2，14 OpenMANIPULATOR-X，15 LeKiwi，16 TurtleBot3 Burger，17 OpenBot，18 Duckiebot。作者写它们覆盖人形、四足、机械臂和移动机器人，并给出部分 3D 模型署名。引用帖不是这份名单的来源，而是同一作者前一天的观察：Release 4 强调物理推理，包含成功与失败尝试，并认为“标注机器人为什么失败，可能和记录它如何成功同样有用”。引用帖自己又引用了与本项无关的旧手机帖，不把那条当作资料。[S1]

清单收录时间 2026-10-24 23:32:50 不是发帖时间。发帖是当天 21:15:47（Asia/Shanghai）。本批未把 140 秒视频逐帧 OCR 当作名单来源。

Q02 作者后来为何又说“并非全部都是开源”？

一天后作者回复 @RobotCaveCom：“But not all of them are open source.” 这句比标题更准确。最清楚的反例是 Duckiebot：duckietown/Hardware 的 LICENSE.pdf 是 Software Terms of Use v1.2 摘要，允许个人教育、认证高校课程和研究（需署名），明确禁止未经书面授权的商业使用，并要求贡献转让版权。这不是 OSI 意义上的开源许可。Microban 硬件是 CC BY-NC-SA 4.0，可分享但挡住商业利用；pib 与 RoArm-M2 使用 AGPL-3.0，对网络服务有源码提供义务。把 18 个项目一律写成“开源可商用复刻”不符合原帖自己的补充，也不符合一手文件。[S1][S3]

AGIBOT WORLD 2026 本身也是 CC BY-NC-SA 4.0，和这 18 个机器人是不同对象，不能把数据集许可套到机械臂套件上。

深入一层 / 分类与许可

Q03 “开源机器人”至少要查哪几层？

至少四层，而且经常不一致。一是控制软件仓库的 SPDX 许可；二是硬件 / CAD / STL，可能是另一种 CC 或 FAQ 与文件打架；三是第三方零件与 3D 署名，原帖已写出 SpotMicro 设计是 KDY0523 的 CC BY 3.0、OpenBot 轮子来自 FreeCAD 库；四是仿真与数据集，SO-ARM 的 URDF 在同一仓，AgiBot 数据却是独立的 NC 协议。已有概念[[开源验货三查]]和[[内容型开源与双许可]]可以复用：先固定提交，再打开 LICENSE，再看宣传是否等于实货。[S3][S6]

pib 官网 FAQ 写硬件也是 AGPL-3.0，但 pib-stls 仓的 LICENSE.txt 是 GPL-3.0。应以文件为准，并把不一致记下来，而不是自行“统一”。

Q04 按人形、四足、机械臂、移动平台怎么分？

原帖的四类大体可用，但有两个边界项目。Otto DIY 是桌面双足，放在人形/双足更老实。LeKiwi 是移动底盘加臂的移动操作平台，不应只算纯机械臂或纯移动底盘。本批对照表：人形 4（Microban、MiniLoong、Poppy、pib）+ Otto 双足；四足 6；机械臂 3（SO-ARM100、RoArm-M2、OpenMANIPULATOR-X）；移动操作 1（LeKiwi）；移动平台 3（TurtleBot3、OpenBot、Duckiebot）。分类只为筛选，不代替看工作空间和传感器。[E2]

已有 vault 的 openarm 是 enactic 的 7 自由度双臂，不是本清单中的 SO-ARM100。筛选时先对名字，再对仓库。

深入一层 / 许可陷阱

Q05 双许可和 NC 条款到底挡住什么？

Microban 的 LICENSE 首部写得很清楚：cad/ 下硬件是 CC BY-NC-SA 4.0，其余控制软件是 GPL-3.0。非商业（NC）允许个人、教学和学术分享，但出售整机、套件或把设计用于商业产品需要另行授权；ShareAlike 还要求改作保持同类许可。Poppy Humanoid 是另一种双许可：硬件 CC BY-SA 4.0（无 NC），软件 GPL-3.0；根目录没有单一 LICENSE，GitHub API 因此显示为空。原帖 3D 署名与我们实读一致：Microban 标了 CC BY-NC-SA 4.0，Poppy 标了 CC BY-SA 4.0。[S3]

这不是法律意见。若要商用或做衍生套件，应联系权利人并固定你使用的那个提交。

Q06 AGPL 和自定义非商用条款有何不同？

AGPL-3.0（pib-backend、RoArm-M2）仍是 OSI 开源许可，允许商业使用，但若通过网络提供修改后的程序，通常要向用户提供对应源码。这与“不能商用”不是一回事。Duckiebot 的条款则直接写 You may not use this software in a commercial enterprise，除非得到 Duckietown Foundation 书面授权；贡献还被要求转让版权。二者都需要在筛选表上单独标记，不能用同一个“开源”格子打勾。[S3]

TurtleBot3、SO-ARM100、Mini Pupper、LeKiwi、OpenMANIPULATOR-X 的软件仓是 Apache-2.0，对商用友好比前两者宽松，但仍要核对零件商标、教程和第三方网格。

深入一层 / 对错仓库

Q07 作者推荐的 SO-ARM100，和现在的 SO-101 是什么关系？

TheRobotStudio/SO-ARM100 当前 README 标题已是 Standard Open SO-100 & SO-101 Arms，并写明 SO-101 是下一代，SO-100 文档标为 deprecated。同一提交 a758567c3978 里同时有 Simulation/SO100/so100.urdf 和 Simulation/SO101/so101_new_calib.urdf。本批解析正运动学：SO-100 零位夹爪（jaw）约在 (0.000, −0.176, 0.147) m，沿 −Y 折叠；SO-101 的 gripper_frame_link 约在 (0.391, 0.000, 0.226) m，沿 +X 伸出。零位约定不同，不能把一份关节角原样接到另一套模型上。这是官方 URDF 的几何事实，不是真机标定，也不是作者性能指标。[S3][E6]

本批未加载网格，也未运行 MuJoCo。缺 STL 不影响关节链计算；实物行程、齿轮间隙和电机方向待验证。

Q08 SpotMicro 的设计仓库和软件仓库是同一份吗？

不是。原帖署名 “SpotMicro design by Deok-yeon Kim / KDY0523 (CC BY 3.0)”。我们核到的活跃软件仓 mike4192/spotMicro 是社区 ROS 实现，LICENSE 为 MIT，最后推送停留在 2021-03-20。MIT 覆盖的是这份软件，不自动覆盖 Thingiverse 上的原始设计。类似地，Stanford Doggo 的活动仓在 Nate711/StanfordDoggoProject，而不是旧的 stanfordroboticsclub 路径。找错上游，后面的 SHA 和许可都会错。[S1][S3]

筛选表要有“设计来源”和“可编译软件来源”两列。星星数高只说明关注度，不证明文件仍在维护。

深入一层 / API 不可靠

Q09 为什么不能把 GitHub 的 license 字段当成最终依据？

本批看到三类陷阱。第一，API 返回 NOASSERTION 或空：OpenQuadruped 的 LICENSE 明明以 MIT License 开头，API 仍是 NOASSERTION；Poppy 因为双文件许可，API 为空；Microban 双许可也被标成 Other。第二，仓库重定向会指到另一台机器人：请求 OttoDIY/OttoDIY 会落到 OttoNinja（MIT），那是另一款项目，不能拿来填 Otto DIY 的格子；Otto DIY 软件库应看 OttoDIYLib（GPL-3.0）。第三，PetoiCamp/OpenCat 与 isl-org/OpenBot 是改名或组织迁移，需要记录最终 full_name，但它们仍是同一项目。固定 SHA 必须写在最终路径上。[E2][E3]

本批用公开 API 拉元数据，再用 git ls-remote 固定默认分支 SHA，并用 raw.githubusercontent.com 读取该 SHA 下的 LICENSE。没有登录，也没有用用户密钥。

Q10 为什么失败标注可能和成功轨迹同样重要？

引用帖的判断与已有概念[[失败反馈具体化]]同向：只告诉系统“失败了，重来”，信息量接近零。对机器人数据，至少应记录哪一段失败、失败类型、原因、是否可恢复。官方 README 也设计了 Error Frame，以及 frame_detail.error_cause、restorable。若字段存在却几乎不用，或原因字符串不统一，训练程序很难把“失败”用起来。Theme 3 的强化学习说明另有 succeed / Error / Intervention 字段，那是另一主题，不能直接算进 Release 4 的 Physical Reasoning 统计。[S2][S4][S6]

“失败也是数据”是研究方向，不是本批已经训练出更好策略的证据。本批只统计公开标注字段。

Q12 “成功与错误样本同等权重”得到证实了吗？

没有。我们读取了出版清单中全部 98 个 info.json（18 个任务，opensourcev4-20261001 与 20261003），关键帧类型合计 Success Frame 8259、Error Frame 2、Intervention Frame 2。两条 Error 分别在 task_86632 episode 55 与 task_96812 episode 49，原因字段几乎同义却不统一：Operation Process Issue - Operation Pause 与 Operation process problem - Operation pause，restorable 均为 true，comment 为空。两条 Intervention 的 frame_detail.comment 竟是 “Command executed successfully”。官方文章所称“成功与错误样本同等权重”，与这份公开 key_frame 计数不相符。Schema 有 error_cause，不等于 Release 4 已经提供可学习的大规模失败原因。[S2][S5][E5]

首次扫描有 9 个文件因 SSL 中断失败，随后用 curl 重试全部成功，Intervention Frame 正是在重试中补到的。统计以 98/98 为准。本批没有下载视频，不能验证这些帧在画面上是否真的失败或被介入。
