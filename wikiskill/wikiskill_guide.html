小模型打败大模型？不微调、不重训，让技能和一本"活百科"共同进化

作者：Liyan Tang, Cyrus Rashtchian, Chun-Sung Ferng, Andrew Tomkins, Da-Cheng Juan, Tu Vu
本指南：疑问式导读 + 零 API 方法层 toy 复现（F:\reminder\wikiskill\exercise，4 实验全跑通）

0一句话说清

给 AI 智能体配一个只会越来越厚的"维基百科"（wiki 层）和一个可以整体换血重来的"技能手册"（skills 层）：智能体干活留下原始轨迹，维护员把经验沉淀进 wiki，提案员照着 wiki 写新技能，验收员试跑后只保留让成绩变好的技能，但 wiki 永远不回滚。转几圈之后，9B 小模型 + 技能 = 47.4% > 27B 大模型裸考 39.4%——权重一个参数没动。

查证结论（诚实边界）：论文真实（arXiv HTML 全文已读、多源交叉确认）。官方没有放代码，网上只有第三方复现；本指南实验是方法层 toy 复现：用确定性脚本模拟"模型"，验证机制本身，不复现论文分数。

1WikiSkill 到底是什么？和推文说的"颠覆性"是一回事吗？

WikiSkill 是一个技能演化（skill evolution）框架：让智能体在反复做题中，把经验"编译"成两种持久资产——知识（wiki）和技能（skills），从而不改模型权重就提升能力。它不训练模型、不微调，全靠外挂的持久知识层。

"颠覆性"要打折听：它不是让小模型凭空变强，而是用"外挂经验"换"参数规模"——本质上是一种极省钱的能力搬运术。方向确实诱人，但论文自己列了 4 条局限（见 Q12），离"颠覆"还有距离。

2"小模型打败大模型"的数字是怎么来的？

论文用 5 个基准（LiveMath 数学 / SealQA 搜索 / SpreadSheetBench 表格 / OfficeQA 长文档 / ALFWorld 具身交互）× 5 个模型。最抓眼球的对照：

Qwen-3.5-9B + WikiSkill 47.4%  vs  Qwen-3.6-27B 裸考 39.4%
参数量差 3 倍，分数反超 8 个点——权重零改动

而且模型越大，WikiSkill 增益越大：4B / 9B / 27B 平均提升分别为 +12.3 / +17.5 / +23.9 分（SpreadSheet 上 27B 更是 +40.9）。技能和规模是互补关系，不是穷人的 substitutes。

3之前的技能演化方法差在哪？

Trace2Skill / EvoSkill / SkillOpt 这批前作都在做同一件事：从执行轨迹里提炼"技能"。它们的共同盲区是——技能被门控拒绝时，背后提炼出的"理解"也跟着丢了。一条经验要么变成技能存活，要么整个蒸发，学习没有"复利"。

WikiSkill 的关键一步是把仓库拆成两层：wiki（理解，永不回滚）+ skills（可执行步骤，严格验收）。技能被拒了，但这次踩坑学到的知识已经写进 wiki，下轮提案员还能从 wiki 里重新长出更好的技能。经验从"一次性消耗品"变成"复利资产"。

4三层工作区各存什么？

workspace/
├── raw/                 ① 原始执行轨迹：每道题怎么做的、对没对。只追加、不可变（案卷底档）
├── wiki/                ② 持久知识层（只能由 Wiki Maintainer 写）
│   ├── patterns/*.md        模式页：一类坑的根因分析与正确做法（如 adddays.md"日期要用真日历"）
│   ├── logs.md              演化日志：每轮发现了什么（流水账）
│   ├── skill-impact.md      技能提案审计：谁提的、改了什么 diff、验收分数、收还是拒
│   └── index.md             索引：所有模式页的一句话目录（改了页就同步改索引）
└── skills/              ③ 可执行技能层：SKILL.md（怎么做）+ PURPOSE.md（为什么）
                             可以整批换掉、回滚——像一叠可以随时重印的说明书

类比本仓库 vault：[[第二大脑LLMWiki]] 说"raw 人写只读、wiki 归 LLM 维护"——WikiSkill 把这套搬进智能体：raw 是自动留下的案卷，wiki 是消化后的理解，skills 是照着能直接上手的操作卡。三层权限不同、寿命不同：raw 和 wiki 只增不删，skills 随时可以回炉。

5四个角色怎么组成一台"进化机器"？（Algorithm 1）

每轮五步：训练 rollout → Wiki 维护（吃采样轨迹子集，防上下文爆仓）→ 技能提案 → 候选集上验证 → 门控。验证分数超过历史最优才接受整批候选技能，否则技能回滚到上一代；无论收拒，wiki 都保留。每轮验证后，外层程序自动往 skill-impact.md 追加一条审计（提案元数据 + unified diff + 分数 + 收/拒）。

6为什么推理 Agent 训练时偏偏不许读 wiki？

反直觉但极重要：训练 rollout 时推理 Agent 只拿到技能全文注入系统提示，wiki 对它封锁。消融实验证明让它读 wiki 反而更差：

Proposer 读 wiki（默认）63.7% vs 推理时也读 wiki：60.9%
LiveMath 上掉得更狠：72.6 → 64.8

原因：答案能从 wiki 直接抄到，轨迹就没有信息量了——模型"开卷抄作业"，维护员反而提炼不出真经验。类比：教室里先闭卷考（暴露真实弱点），再由老师把错题整理进错题本（wiki），下次带的是"解法卡"（skills）而不是整本错题本。

关联：[[三层记忆]] / [[记忆四层模型]] 讲"经验怎么分层压缩"；WikiSkill 补了一刀——压缩的原料必须来自"真实暴露的失败"，喂料端被污染，整条流水线退化。

7Wiki Maintainer：图书管理员怎么"补丁式"维护 wiki？

每轮拿到两样东西：当前 wiki 全状态 W(k-1) + 采样的轨迹子集（采样是为了不撑爆上下文窗口）。它做三件事：

1
根因分析
对失败任务问"为什么错"，对通过任务提炼"为什么对"
2
补丁式编辑
新建模式页，或对已有页做追加 / 替换 / 插入文本片段——注意：没有自动 merge，也没有 prune（剪枝），页数只增不减（局限 3：长期跑可能臃肿）
3
同步索引和日志
模式页变了就更新 index.md；每轮往 logs.md 追加发现摘要

论文里真实长出的模式页如 take-examine-move-loop.md（ALFWorld 的"取-查-动"循环）、multi-operation-loop.md（表格多步操作）。

8Skill Proposer：侦探式按需检索，不是"一次性塞全库"

提案员起步只拿三样轻量材料：wiki 索引、skill-impact 审计、全部训练任务的成败摘要。然后它像侦探一样用 read_file 工具自己决定深挖哪几页模式页、翻哪几条原始轨迹，最后产出原子提案——一次只改一个技能。

这和 [[RAG检索增强生成]] 的"先向量检索 Top-k 再喂给模型"不同——检索权在 agent 手里，是主动查阅不是被动投喂；和 [[分层按需加载]] 的精神一致：索引常驻，正文按需。

9Gating：为什么技能可以整批回滚，wiki 却一刀不动？

门控规则简单粗暴：候选技能集上验证集，分数必须严格超过历史最优，否则整批回滚。这保证了技能集永远单调不退步。但 wiki 被刻意豁免——因为 wiki 存的是理解，不是行为：这次提案失败了，但"我们搞清楚了这类题为什么难"这件事永远为真。

我们的 toy 实验 ex2 实证了这一点：

坏技能候选 val=62.5% < 最优 87.5% → 门控拒绝，skills 回滚成功
wiki 页数 4→4、logs 只增不删：wiki 层永不回滚
删掉 adddays 技能后重演化：提案=空（skill-impact 审计拦下重复提案）
但 wiki/patterns/adddays.md 仍在：知识活着

代价也要知道：严格门控会错杀"中性但长期有价值"的提案（分数没涨就被拒）——论文局限 2 原文承认这一点。

关联：[[发布交换与健康门回滚]]（发布是切换不是修改）、[[Checkpoint存档与持久执行]]（回滚到快照）——WikiSkill 把这套工程纪律第一次用在"技能集"上：skills 像蓝绿部署的实例，wiki 像只增不删的事务日志（[[JSONL事件日志与折叠模型]]）。

10skill-impact.md：一份让提案员"不二次踩坑"的审计账本

每次验证结束，外层 harness（不是 LLM）程序化追加一条记录：提案元数据、目标技能名、修改的 unified diff、验证分数、Accept/Reject。它同时服务两端：

读者用途
Skill Proposer看到"这条 diff 上轮被拒+为什么"，不再重复提交同款失败修改（我们 ex2 的审计拦截就是它的玩具版）
人 / 外层系统完整审计轨迹：技能是怎么一步步进化成现在这样的，每次转弯有据可查
本质是 [[事实与判断分离]] 的又一实例：收/拒的判断由门控做出，但记录由确定性代码写入——LLM 可以读账本，不许改账本。

11跨模型迁移：技能是"可携带的能力"，但会水土不服

演化出的技能可以直接搬给别的模型（Table 2 精选）：

场景裸考自演化用别家技能
27B 的技能 → 9B @SpreadSheet24.333.650.5
27B 的技能 → Gemma-31B @LiveMath33.956.773.7
9B 的技能 → 27B @ALFWorld—63.470.2
负迁移：4B 的技能 → Gemini-Flash @SpreadSheet—50.518.1（暴跌！）

负迁移的机制值得记住：4B 弱模型总结出的"低层 workaround"（为绕开自身局限设计的笨办法）注入强模型后，反而把强模型本来就优雅的解法捆住了，碎片化诊断还耗光了交互预算。同款技能给 27B 则升到 63.4——技能不是越通用越好，要匹配受体的能力档位。

我们的 ex3 也复刻了这个现象：B 模型全量迁移 A 的技能 50%→87.5%（正迁移），但单迁 A 的闰年"简化规则"技能，把本来全对的 B 带错世纪年（leap 2/2 → 1/2，负迁移实证）。

12我能拿它干什么？论文自己承认哪些坑？

论文四条局限（原文承认）：① 技能是全量注入 prompt 的，没评测技能检索/触发；② 严格门控会错杀中性但长期有价值的提案；③ wiki 没有自动剪枝，长期跑会臃肿；④ 没覆盖数百步/数小时的超长程任务，在线适应留作未来工作。
