01

它到底解决什么问题？为什么不是又一个聊天客户端？

CLIProxyAPI 是 Go 编写的代理服务器：客户端仍用熟悉的 OpenAI / Gemini / Claude / Codex 等 API，网关再连接 CLI/OAuth 或 API-key 上游。它位于“应用”和“模型服务”之间，而不是取代任何一边。

协议入口与上游提供方解耦；实际可用模型取决于你的账户和上游能力

没有它时

每个客户端各配一套 base URL、凭证和模型名；遇到协议不同就另写 shim；多个账号要自己在业务代码里轮换；流式与工具调用也要分别适配。

有了它后

应用指向本地网关，统一处理客户端鉴权、模型目录、协议转换、账号选择和热更新。业务代码不必知道当前选中了哪把上游凭证。

反向代理协议适配模型网关与知识库的 负载均衡与反向代理、Provider 适配层与错误契约 同族；与 magpie 的差异增量是：本次固定 v8 官方发布包并真实跑通协议与路由，不停留在源码结构检查。

02

为什么配置里有两类 API Key？是不是填重复了？

不重复。access.api-keys 是“谁可以调用我的网关”的客户端门票；api-keys.* 与 OAuth 文件是“网关拿什么调用上游”的出库凭证。两者信任方向相反。

泄露客户端 key 会开放你的网关；泄露上游 key/OAuth 文件会直接影响上游账户
access:
  api-keys: ["local-client-key"]       # 客户端 → CPA
api-keys:
  openai-compatibility:
    - name: "local-mock"
      base-url: "http://127.0.0.1:19001/v1"
      keys: [{api-key: "upstream-A"}, {api-key: "upstream-B"}]  # CPA → 上游
实测：不带客户端 key 请求 GET /v1/models 返回 401 {"error":"Missing API key"}；带 Bearer local-client-key 返回 200 和 demo-alias。这里所有 key 都是本实验假值，不是任何真实账户凭据。

还有第三把钥匙：management.secret-key 管配置、凭证、OAuth、日志等管理接口。它不应与客户端 key 混用；留空会关闭管理路由，allow-remote: false 再限制为仅本机管理。

03

一次请求穿过哪些部件？“翻译器”和“执行器”分别干什么？

可以把主链路读成七站：HTTP 路由 → 客户端鉴权 → 模型解析/别名 → 凭据选择 → 请求翻译 → Provider 执行器发出 HTTP → 响应翻译回客户端协议。翻译器改“语义格式”，执行器管“真实出站调用”。

架构依据：internal/api、internal/registry、sdk/cliproxy/auth、internal/translator、internal/runtime/executor
部件它决定什么它不应该做什么
Translator 注册表从入站格式到 provider 格式，及反向响应/SSE 转换不替上游真正生成 token
ProviderExecutor构造出站 HTTP、注入凭证、处理流和提供商细节不决定客户端是否有权进门
Auth Manager / Selector候选凭据、轮询、会话亲和、冷却与重试不凭空增加套餐额度
Payload 规则在最终业务负载上做 default / override / filter不应被后续翻译再次覆盖

项目自己的工程约束很有代表性：payload 规则必须是“送往上游前的最后语义屏障”，先完成内建翻译、规范化、注入和清理，再恰好应用一次用户规则。这避免“配置写了 override，却被后一步翻译悄悄改回”的隐蔽 bug。

04

Claude Messages 与 OpenAI Chat 到底怎么互译？有实测吗？

有。翻译不是换 URL，而是同时映射字段、角色、内容块、停止原因、用量与流式事件。本实验把 Claude 请求送进 CPA，mock 实际收到的已是 OpenAI Chat 请求。

真实方向：Claude 口径进 → OpenAI 上游 → Claude 口径出

客户端发出

POST /v1/messages
{
  "model": "demo-alias",
  "max_tokens": 64,
  "system": "你是协议演示助手",
  "messages": [{"role":"user","content":[
    {"type":"text","text":"Claude 口径进，OpenAI 口径出"}
  ]}]
}

mock 实际收到

POST /v1/chat/completions
Authorization: Bearer upstream-A
{
  "model": "mock-model",
  "messages": [
    {"role":"system","content":[{"type":"text","text":"你是协议演示助手"}]},
    {"role":"user","content":[{"type":"text","text":"Claude 口径进，OpenAI 口径出"}]}
  ],
  "max_tokens":64, "stream":false
}
响应也翻回来：mock 的 choices[0].message.content 变成 Claude 的 content[0].text；finish_reason=stop 变成 stop_reason=end_turn；prompt_tokens=11 / completion_tokens=7 变成 input_tokens=11 / output_tokens=7。证据见 exercise/runtime/upstream_requests.jsonl 与 experiment_results.json。

不要推出“所有字段 100% 无损”。不同协议并不总有一一对应能力；推理签名、服务端工具、缓存、特殊内容块与错误语义都可能受上游限制。兼容是逐特性工程，不是一句“OpenAI compatible”就结束。

05

/v1/models 和 alias 是在下载模型吗？为什么要区分 name 与 alias？

不是下载。模型注册表是在发布“路由目录”：客户端看见 alias，Executor 使用上游真正的 name。它把客户端稳定命名与上游可变命名分离。

name = 上游真实模型名；alias = 客户端可见、可用于路由的名字
models:
  - name: "mock-model"       # 发给上游
    alias: "demo-alias"      # 客户端使用
    display-name: "Local deterministic mock"
    input-modalities: [text]
    output-modalities: [text]

这套目录还有三个实际作用：

  • 稳定客户端配置：上游模型名变化，只改映射，不改所有应用。
  • 声明能力：输入/输出模态、thinking、上下文长度等元数据可帮助客户端与路由做决策；声明不等于上游自动获得能力。
  • 组成内部模型池：同一个 alias 可对应多个上游 name；候选失败时可尝试同池其他模型。但这与“同模型多凭据轮询”是两个维度。
实测：GET /v1/models 只返回 demo-alias，其 owned_by=local-mock；上游 6 次请求全部是 model=mock-model。这证明目录名与执行名确实分离。
06

多账号轮询、fill-first、会话亲和与故障转移有什么区别？

轮询决定“下一次从谁开始”；会话亲和决定“同一会话是否一直用同一凭据”；重试/冷却决定“失败后是否换、何时再试”。它们相关，但不是同一个旋钮。

可见参数变化：A→B→A→B 变为 A→A；不是推断，是 mock 的 Authorization 记录
机制适用目标要付出的代价 / 边界
round-robin候选凭据近似等价时均匀分配起点不等于真实额度均衡，也不知道每次请求成本
weighted-round-robin按整数 weight 分配比例权重是策略输入，不是实时剩余配额
fill-first优先用前序候选，适合主备主凭据承受更多流量；故障规则仍重要
session-affinity让同会话粘住上游，利于缓存与上下文连续性降低池化程度；绑定失效时需重绑策略
retry + cooldown对 408/429/5xx 等分类重试并暂时避开坏候选已经向客户端输出的流不能简单“无痕重放”

v8 默认配置显示 request-retry: 3 表示初始轮耗尽后的额外凭据重试轮数，不是“每个错误都固定重发三次”。max-retry-credentials 另限每轮尝试的不同凭据数。流式响应还有“首字节前可重试，已提交后难换路”的边界。

本实验为可复现而关闭额外重试：request-retry: 0。A/B/A/B 与 A/A 证明路由选择；本实验没有验证真实 429、配额重置、真实 OAuth 刷新或云故障转移。
07

为什么流式与工具调用比“JSON 改几个字段”难得多？

非流式像翻译一整封信；流式像实时口译。转换器必须记住“消息是否开始、哪个内容块开着、工具参数收到多少、是否见到结束原因”，并把 OpenAI chunk 重组为 Claude 事件生命周期。

本实验实际收到 message_start → content_block_delta → message_delta → message_stop

源码中的 ConvertOpenAIResponseToAnthropicParams 明确保存消息 ID、内容累积器、工具调用累积器、块索引、结束原因和 usage。工具调用的参数通常分片到达，不能每片都当完整 JSON；还要避免“宣告了 tool_use，却因为参数无效而没有真正发出”的假成功。

工具调用

schema、tool_call id、名称、参数片段、tool_result 对齐都要转换。执行工具的是客户端/Agent harness，不是 CPA 自己。

多模态与推理

图片/文档 content part、推理块与签名、缓存标记未必在另一家有等价物。要按具体路径测试，不可只测一句文本。

流式实测：mock 返回 OpenAI chat.completion.chunk 和 [DONE]，客户端收到 Claude SSE；文本 mock-B 已收到: 流式事件也要翻译 位于 content_block_delta。本实验未覆盖工具调用与多模态，故不在“已实测”清单里冒领。
08

OAuth 登录、凭证刷新与管理 API 是怎样配合的？

OAuth 流程取得的是上游凭证；CPA 把它交给凭证存储并在请求时选中，Executor 使用它，后台生命周期负责刷新。管理 API 是另一条受独立 key 保护的控制面，能管理配置和凭证，所以权限必须更小。

数据面跑模型请求；控制面改配置、凭证与 OAuth。两面不能共用“游客权限”
  • 凭证存储：oauth.auth-dir 默认指向文件存储；项目也支持 Postgres、Git、对象存储等。集中存储意味着备份与访问控制都更重要。
  • 管理 API：v8 基路径是 /v8/management；配置路径直接对应 YAML 树，如 /config/access/api-keys 与 /config/api-keys。旧 /v0/management 仍兼容但不再作为新功能重点。
  • 热更新：配置和凭证目录有 watcher；改动并非都需要重启。不过本实验为清楚对照路由策略，选择了明确重启。
  • 用量面板：README 明确说自 v6.10.0 起不再内置完整用量统计，而是指向独立外部工具。不要把“管理面板存在”误读成“历史账单天然齐全”。

账户条款与安全：“能登录并转发”是技术能力，不是上游服务条款许可。订阅/OAuth 的自动化调用、共享和配额规则要逐提供方确认；不要用多账号规避服务限制。凭证集中后，网关被入侵会影响全部账户。

09

怎样配置才不把“本地网关”变成局域网/公网漏洞？

先默认只有本机可访问，再按层加门：监听地址 → 客户端 key → 管理面独立 key 与 localhost → TLS/可信代理 → 请求体限制与日志卫生 → 凭证目录权限。不要先开 0.0.0.0 再补安全。

保护的不只是 key，也包括经过网关的对话、工具参数和模型响应
server:
  host: "127.0.0.1"          # 不让 LAN 直接连
  port: 8317
  max-request-body-bytes: 1048576
management:
  allow-remote: false
  secret-key: "独立、足够随机的管理密钥"
  disable-auto-update-panel: true   # 需要可控离线环境时
observability:
  logs:
    request-log: false       # 无审计需求时少留敏感正文
检查项为什么
不要把示例 key 留在生产项目对示例 key 有安全模式，但安全模式不是替换真实密钥的理由
谨慎启用 request-log / debug请求正文可能含代码、个人数据、工具参数；日志保留也属数据面
面板与插件是额外供应链管理面板会下载/更新；动态库插件是受信任的进程内代码，不是沙箱
代理与 TLS 要成对设计只信任明确的 forwarded-header 来源；跨机器用 TLS，不伪造“本地=永远安全”
发布包先校验再运行本实验 SHA-256 与 GitHub Release digest 完全一致，避免拿同名二进制当官方
10

我能拿它做什么？Go SDK 又能扩展什么？边界在哪里？

最直接的价值是“让已有 API 客户端复用现有上游连接”，更深入的价值是把同一套路由、鉴权、监听和翻译嵌入自己的 Go 服务。自定义 Provider 主要扩展 Executor 与 Translator。

SDK 复用的是网关内核，不是把模型权重嵌进你的进程

本地开发统一入口

多个脚本/Agent 共用一个 localhost base URL 与客户端 key。

协议桥

让只懂 Claude Messages 的客户端连接 OpenAI 兼容上游，或走支持的其他协议路径。

主备与多凭据

按轮询、权重或 fill-first 组织候选，配合冷却和重试。

稳定模型门面

用 alias 隔离上游命名变化，向客户端发布受控模型目录。

内嵌 Go 基础设施

把配置、翻译、路由与热更新嵌入桌面工具或自己的服务。

无费 mock 测试

像本实验一样用确定性上游验证鉴权、映射、流式生命周期与路由。

四个“不能”：不能本地推理；不能创造模型能力；不能创造额度；不能保证任意协议特性无损。它是网关，不是模型、不是破解器、也不是自动账单系统。

与已有 magpie 学习的关系：二者都属于订阅/BYOK 模型网关与多协议翻译。本篇新增的是 CLIProxyAPI v8 的配置树、Executor/Translator 分层、官方 Windows 发布物校验，以及真实 Claude↔OpenAI、SSE、A/B/A/B 与 fill-first 端到端证据。

主实验：不花一分钱，看见“翻译 + 路由”真的发生

目标：官方 v8.0.47 + 本机 mock 上游，跑通 6 次请求；验证客户端鉴权、alias、Claude 非流式/SSE、round-robin 与 fill-first。全程只监听 127.0.0.1，不使用真实 OAuth，不发真实模型请求。

  • Go 项目想内嵌网关内核

先别误解

  • 没有 GPU 也不能靠它本地跑模型权重
  • 不是“配置名字就获得该模型能力”
  • 多账号不等于额度无限，也不授权绕过限制
  • 文本跑通不等于工具/多模态/推理全部兼容

最小落地顺序

1 固定版本与官方摘要 → 2 localhost + 独立客户端 key → 3 单上游单模型非流式 → 4 SSE → 5 工具/多模态专项测试 → 6 再开多凭据、会话亲和与管理面。每一步都保留上游可见证据。
