问题 01 / 先看全局

模型会写代码了，基础设施还要解决什么？

交付的单位是一个经验证的任务，不是一段生成的代码。

原创示意：生成代码只是“行动”中的一个环节；验收仍需环境与证据。

从一个维修故事开始

假设你请智能体修复订单页。它改好了函数，但本地服务没启动、测试数据缺失、部署权限不清楚，最后只留下一句“已完成”。问题可能并不在这段函数，而在执行条件和验收流程。

五类问题一起看

本章把长期执行、知识与工具、运行环境、权限安全、可观测评测放在同一张架构图里。基础设施要把目标、操作、反馈和证据接起来，帮助智能体在失败后继续纠错，在越界前停下。

这次学习的重点

已有公开笔记涉及 Harness、MCP 和沙箱。本指南用这些概念搭桥，重点推进到任务委托、逐次授权、撤销传播与证据绑定；查到相关笔记不代表读者已经掌握全部内容。

自测：如果代码能编译，但没有验证实际需求，你会如何描述完成状态？

参考回答：只能报告已通过的局部检查，并列出未验证项；不能宣称整项任务交付。

问题 02 / 闭环而非一次回答

Harness 怎样让长任务不断线？

记住任务状态，读取真实反馈，再决定继续、交付或交给人。

原创闭环：把工具反馈接回任务状态；停止条件由目标、风险和证据共同决定。

先给术语落地

Harness 是模型之外的执行组织层，负责上下文、计划、工具调度、状态和停止条件。它像维修工的工单台：知道目标是什么、做过什么、哪些判断仍未证实。

一次失败不等于从零开始

测试报错后，系统保留命令、输出、修改和下一步，让下一轮针对失败继续。恢复的是可核对的任务状态，不是把过去的对话无限塞进上下文。

规则和硬约束的分工

规则文件或 Skill 告诉模型怎么做；强制安全边界要落到程序和资源侧。即使启动时获准，后续目标、参数或环境变了，每次关键操作仍要重新判定。

自测：把“不要访问其他项目”写入提示词，是否就建立了访问控制？

参考回答：没有。提示词可以引导，但执行点仍需要校验实际请求与资源范围。

问题 03 / 事实与做法分开治理

知识库和 Skill 分别承担什么责任？

知识给依据，Skill 给步骤；两者都要能更新和追溯。

原创示意：事实、方法、接口形成工作链，反馈应回到知识与方法维护。

三个部件各有工作

知识库保存有出处的事实、规则和领域关系。Skill 是一类任务的可复用方法，写清条件、步骤与完成标准。MCP 或 CLI 则提供执行接口：MCP 是模型连接工具与资源的协议，CLI 是命令行接口。

例子：处理一次服务告警

知识库说明服务负责人和当前故障规程；Skill 组织排查顺序；工具读取日志。旧规程即使检索排名第一，也可能已经失效，必须核对来源、版本、适用范围和更新时间。

保留历史不等于旧结论永远正确

已读笔记中的“知识层永不回滚”来自特定研究方法。这里的企业知识治理还要求纠错、撤回和权限管理；保留修订记录与继续使用错误知识是两回事。

自测：一段引用完整但已经过期的操作规程，能直接成为行动依据吗？

参考回答：不能。可追溯不代表仍适用，需核对版本、时间、范围及当前授权。

问题 04 / 选对与用成是两道关

接上很多工具，为什么仍可能做不成任务？

工具目录有多长，不如每个任务能否选对、用对、验对。

原创检查链：命中只通过第二格；后两格仍可能失败。

先看命中，再看成功

本章把工具评测分为命中率与成功率。前者问是否选中了合适的能力；后者问选中后，参数、顺序、依赖和权限是否足以完成预期操作。一次 API 返回成功，不自动等于用户目标已实现。

例子：找到日志还不够

排障智能体选中了查询工具，却把测试环境名称传给生产查询，可能得到一份正常但无关的结果。需要检查资源、参数、时间范围和结果是否支持下一步判断。

已有笔记的桥梁

工具暴露单调性讨论工具列表与客户端缓存，技能路由器讨论选择与硬门。两者都不替代调用时的授权。readOnlyHint 之类描述也不是执行侧权限防线。

自测：read 工具返回了文本，能否据此证明它读到了获准的正确文档？

参考回答：不能。还要核对委托、资源身份和内容适用范围，不能只看调用成功。

问题 05 / 两条独立的安全轴

沙箱和审批为什么不能互相替代？

沙箱限制能碰到什么，审批与策略判断这次该不该做。

原创分层图：隔离、授权、凭证管理承担不同责任，任一项都不是万能保证。

把围墙和门卫分开

Sandbox 指受约束的运行环境，涉及文件、网络、命令、资源、凭证和生命周期。审批是对具体操作的许可过程。受隔离的任务仍可能做错允许范围内的事情；获得批准的任务也不应因此失去运行边界。

凭证也有自己的边界

手册的方便演示把 API Key 传入环境变量，但同时明确区分生产中处理不可信代码时的可信代理注入建议。凭证代理在匹配目标、路径和方法后才代为附加真实凭证，不应把完整秘密交给不可信代码。

本实验做到哪里

我们只运行应用层授权状态机。合成文件读取包装器没有建立操作系统沙箱，也不能阻止同进程恶意代码绕开入口。即使使用路径解析，也不能凭此证明无逃逸或无检查与使用之间的竞态。

自测：在容器里运行是否足以证明模型无法泄露生产凭证？

参考回答：不足。要另外检查凭证是否进入容器、出站网络约束、注入策略和真实配置。

问题 06 / 环境定义不是任务现场

为什么有代码仓库，仍然复现不了运行结果？

长期维护环境定义，按任务创建实例，用干净实例复验候选结果。

原创示意：复用经过验证的定义与基线，同时保留每次任务的隔离边界。

代码不是全部输入

项目还依赖工具链版本、配置、数据库基线、依赖服务、网络策略、启动顺序和验证命令。Environment Definition（环境定义）描述这些可重建条件；Task Instance（任务实例）保存本次运行的文件、进程和排障现场。

例子：修复数据库迁移

一次修复在手工改过数据库的现场通过，不代表新人能重建成功。应保存候选配置与数据，再用新建实例按相同定义重跑。通过复验后才考虑形成新基线。

读架构图时别混淆产品

本章展示的是参考分层与概念配置，其中的 YAML 不是可直接执行的产品 API 契约。我们的 ZIP 通过合成夹具和在新目录中重新初始化并重跑验证教学可复现性，没有实现完整环境平台。

自测：同一脏工作区连续运行两次都成功，是否已证明环境可复现？

参考回答：没有。还应在新目录或干净实例按明确的输入与步骤重新运行。

问题 07 / 先把四个问题拆开

身份、委托、策略和凭证到底差在哪？

知道“是谁”，不等于知道“代表谁、此刻能做什么”。

原创责任链：每个方框是一种证据或判断，不能拿其中一个替代全部。

四个术语分别回答

Identity（身份）回答请求主体是谁；Delegation（委托）回答它为何能代表某人执行这项任务；Policy（策略）判定当前动作是否允许；Credential（凭证）供下游验证访问资格。共享账户或通用 token 很难表达完整责任链。

各层如何配合

PDP 是策略决策点，计算是否放行；PEP 是策略执行点，真正拦住不合规操作；Credential Broker 是按条件提供下游凭证的中介。模型提出意图，可信运行时与资源侧独立判断。

教学标识不是身份认证

实验中的 user、agent、runtime 和 task 都是预置字符串；它们演示绑定关系，没有签名校验或登录。调用者自报“已批准”，或在网页中看到某资源编号，都不能给自己增加权限。

自测：OAuth 登录成功，是否表示这个智能体可调用所有工具和资源？

参考回答：不表示。认证与连接成功后，仍要检查具体工具、动作、资源和任务委托。

问题 08 / 授权逐级收窄

把任务交给子智能体，权限应怎样传下去？

每次转交都要有自己的身份和边界，子委托不能比父委托更宽。

原创集合示意：子权限是父权限内的更小集合；收窄并非仅靠一句自然语言约定。

先给 scope 下定义

Scope（权限范围）描述允许的资源、动作、时间等边界。本章的有效权限同时受用户权限、Agent 能力上限、平台策略、本次委托和运行约束限制；不能只挑其中最宽的一项。

一张任务卡的例子

主智能体获准读取任务 A 的两份合成资料。子智能体只需要附录，那么子委托可收窄为附录的 read 权限，且到期时间不晚于父委托。它不能借“帮忙完成任务”的理由增添任务 B 的资料或 write 操作。

继承的不只是资源列表

运行实例与任务也要匹配；每次调用还要检查整条父委托链的有效期与撤销状态。父委托失效后，不能留下一个仍能通行的子委托，也不能继续从它签发新委托。

自测：子委托资源更少，但到期时间更晚，还算权限收窄吗？

参考回答：不算。时间也是权限维度；任何维度的扩大都应被拒绝或重新授权。

问题 09 / 过期与撤销不是一回事

有短期 token，为什么还必须做主动撤销？

短有效期缩小风险窗口；撤销要让当前授权立即走向失效。

原创时间线：验证重点是撤销后的行为，而不是状态字段看起来已改变。

先看撤销后的下一次请求

TTL 是有效期。即使 token 只剩一分钟，用户刚刚撤回委托，也不能把这一分钟当成继续操作的许可。任务结束、授权撤回或环境变化后，都需要重新判断是否还能使用。

生产问题是一整条链

本章要求停止新凭证签发、清除多层放行缓存，并处理下游会话、长连接和任务终止。只改一个 revoked 标记，却继续复用旧的 allow 缓存，撤销就没有落到执行点。

实验故意留一组坏对照

正确路径每次重验父子链；反例故意缓存一次允许结果，展示撤销后仍读取的错误。这个反例用于暴露漏洞，不能部署。实验只测单进程序列化的新请求，不证明跨服务传播时延或撤回已返回内容。

自测：撤销后根委托被拒绝，子委托还可以读，是否算撤销成功？

参考回答：不算。根与所有依赖它的子委托都必须在后续请求中重新检查并拒绝。

问题 10 / 分清两套三态

缺授权和缺证据，都应该返回“失败”吗？

授权的 Challenge 是等批准；检查的 UNKNOWN 是证据还不够。

原创双轨图：一轨处理资格，一轨处理现场证据；只有各自满足要求才能继续。

授权三态

允许表示符合当前权限条件；拒绝表示不允许执行；Challenge 表示需要补充授权。Challenge 应包含需要谁确认、什么动作、哪个资源和有效期，交给可信界面处理，不能让模型猜测如何绕过。

检查也有三态，但语义不同

Guardrail（操作守护检查）可给出 PASS、BLOCKED、UNKNOWN。PASS 表示当前检查满足条件；BLOCKED 表示发现阻断问题；UNKNOWN 表示缺数据、查询失败或无法解释。UNKNOWN 不能被当成 PASS。

小例子

一个任务已有读取权限，但服务健康查询超时，属于证据不足；另一个任务服务健康，却没有发布授权，属于权限问题。健康与授权不能相互兑换。本实验只实现 allow/deny，没有实现 Challenge 或真实审批界面。

自测：因为健康检查超时没有发现问题，能不能放行？

参考回答：不能。没发现问题可能只是没有拿到证据，应保留 UNKNOWN 并暂停相关动作。

问题 11 / 把结论绑在版本与现场上

昨天通过的 Guardrail，今天还能直接复用吗？

一次通过只覆盖当时的规则、目标、参数和有效状态。

原创绑定图：检查结论是有边界的证据，不是长期、跨目标的通行证。

理解三个对象

GuardrailSpec 是固定版本的检查规则；ChangeSet 是这次动作上下文的快照；Submission 是逐项结论与证据。把三者绑定，才知道一次通过检查了什么。Guardrail 做协议校验与机械聚合，不自动证明业务语义正确。

例子：发布批次变了

昨天检查的是测试服务的一小批实例，今天目标变成生产服务，昨天的通过结论不能沿用。即使检查规则未变，目标或动作参数变化也需要新一轮判断；最终执行系统仍要复核当前状态和权限。

证据要够用，也要克制

可保留脱敏摘要、来源、查询时间和受权限保护的引用，不应把凭证或全量业务日志搬进控制系统。固定摘要用于绑定版本，不能单靠一个哈希就声称记录绝不可篡改。

自测：同一个任务名称没变，但资源 ID 和动作参数变了，还能沿用结果吗？

参考回答：不能。应根据新的动作上下文重新检查，名称相同不代表检查对象相同。

问题 12 / 从系统健康走向任务结果

有了日志，怎样判断智能体真的做对了？

把目标、每步动作、状态变化和结果串起来，再用失败样本改进。

原创证据环：过程用于解释和定位，结果用于验收；可观测不等于已经安全。

系统层与行为层

系统可观测性关注延迟、错误、资源与成本；行为可观测性关注任务怎样被执行、是否达到目标、动作是否合适。Trajectory 是一项任务的完整执行轨迹，Trace/Span 是描述调用时序与关系的系统链路。

本实验能回答的事

审计记录可以关联任务、实例、委托、资源、动作、策略版本、决定、原因以及是否真的读取。拒绝也应留痕。JSONL 只是逐行 JSON 存储格式，不天然防篡改，也不能把多个事件任意换序。

把成熟度说清楚

手册结论明确是阶段性总结，部分基础设施仍在早期建设与验证。我们验证的是一个教学状态机及其反例，没有验证阿里内部平台、行业性能数字或完整企业方案。下一步应从低风险任务、明确验收和受控试点开始。

自测：所有工具都返回 200，用户目标却没达成，评测应记为成功吗？

参考回答：不应。工具状态只是过程信号，任务成功需要独立的结果验收。

可以用来做什么

五项能力和五个具体用途

获得的是一套分析与验证方法，不是直接上线的基础设施产品。

1. 把长任务组织成闭环

明确目标、状态、反馈、停止条件；出现失败时能够解释下一步。

2. 把知识和工具接到正确任务

区分事实、操作方法和执行接口，核对来源、版本与适用范围。

3. 描述可隔离和可复验的环境

分别检查运行边界、依赖与数据基线，要求干净实例复验。

4. 设计任务级最小权限与撤销

五个用途

  1. 读一个新的 Agent 项目时，用五类问题检查它缺的是模型能力、环境条件还是执行边界。
  2. 给学习资料读取器做任务级授权原型，只用合成文件演练跨任务访问与撤销。
  3. 设计多智能体任务卡，写清资源、动作、到期时间以及子委托允许收窄的维度。
  4. 为排障任务补一份可复验记录：输入、环境、命令、输出、验证标准和未完成项。
  5. 审查“已成功”的证据，区分已调用、已执行、已验证和已达成用户目标。
