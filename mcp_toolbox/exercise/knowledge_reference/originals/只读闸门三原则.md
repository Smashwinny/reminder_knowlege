# 只读闸门三原则

**一句话定义**：给 AI 开"生产数据口"（如供网页版模型调用的只读 MCP Server）时，安全必须落成三道独立闸门——**只读**（驱动层物理只读 + SQL 白名单）、**最小权限**（工具目录白名单、表白名单，写工具不存在而非被禁用）、**可审计**（每个请求含被拒的都追加 JSONL 日志）——并逐层可自动化验收。

**属于领域**：AI 工具生态 / 安全。

**通俗理解**：三道闸是三把不同的锁：SQL 校验是"门口保安查证件"（应用层，可能被绕），SQLite `file:...?mode=ro` 是"保险柜本身焊死"（驱动层物理事实，绕不过），审计日志是"每个进门的人无论成败都登记"。百行级 Python 即可复刻（codex_quota_mcp 实验 10/10 PASS：INSERT 被 `attempt to write a readonly database` 拒、sqlite_master 被白名单拒、8 请求=8 行日志对账）。**安全要做成多层闸门而不是一句提示词**——提示词可能被注入绕过，`mode=ro` 是数据库驱动层面的物理事实。

**与已有概念的关联**：
- [[MCP服务器]]：闸门装在哪个载体上（本文场景：网页版模型可挂的插件）
- [[快照契约与不可变只读]]：同一"物理只读"哲学（`mode=ro&immutable=1`）在离线数据交接面的版本
- [[CleanRoom只读读取器]]：同族"只读不碰"路线——CleanRoom 管读别人的数据，本概念管别人（AI）读你的数据
- [[提示注入]]：为什么不能靠提示词防线
- [[OAuth资源发现]]：闸门之外的门口身份认证（服务端接企业 IdP 如飞书）
- [[事实与判断分离]]：审计日志只记事实（谁调了什么、拒没拒），判断留给复盘
