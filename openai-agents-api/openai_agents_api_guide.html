Q1
Agents API 到底是什么？"又一个 Agent SDK"？

一句话：OpenAI 把自家 Codex 背后的 Agent harness 原样搬进云端，变成一个 REST API。你的应用只管发任务、收事件；模型循环、上下文管理、断点恢复、沙箱运维，全由 OpenAI 代管。

它和 SDK 的本质区别在"循环跑在哪"：SDK 是把一个库装进你的进程，agent 循环在你的代码里跑；Agents API 是循环根本不在你机器上——OpenAI 云端跑着一个托管版 Codex 实例（官方叫 it "managed Codex harness"），你通过 HTTP 跟它对话。API 端点是 POST /v1/agents/sessions，需要 OpenAI-Beta: agents=v1 头，目前处于 public beta。

官方自己的分界线（developers.openai.com 文档原话）：Agents API = "OpenAI runs a managed Codex harness"；Agents SDK = "The SDK runs inside your application"。一个是租整条生产线，一个是买机器回家自己开。
Q2
我会 LangGraph / CrewAI 了，为什么还需要"租 harness"？

先讲一个之前的世界：2025 年起人人都发现 模型本身不难接，难的是模型外面那一圈——上下文窗口满了怎么办？任务跑 3 小时进程挂了怎么办？工具执行环境怎么隔离？OpenAI 官方博客《Harness engineering》的原话：agent 反复失败，大多不是模型不行，而是环境欠规格（这正好印证知识库 [[AgentHarness智能体挽具]] 的七职责：改环境胜过改形容词）。

于是每家公司都在重复造这一圈。Agents API 的赌注是：这圈东西 OpenAI 已经在 Codex 里打磨好了，别再造了，直接调用。你写 client.beta.agents.sessions.create(...)，OpenAI 替你把压缩、恢复、subagent 调度、沙箱生命周期全做了。

LangGraph / CrewAI（已学）Agents API（本篇）
编排逻辑你写：状态图 / 角色分工harness 自主决定（可多给指令引导）
状态持久化你配 checkpointer（[[Checkpoint存档与持久执行]]）内建：session 自动保存 turns/items
执行环境你的进程 + 你选的沙箱方案三态沙箱开箱即用
上下文管理你写压缩策略（[[上下文预算与战略压缩]]）自动压缩内建
换模型/厂商自由（可接任意 LLM）锁 OpenAI 生态（gpt-6-astra 等）
适合要精细控制流程的产品长时自主任务、不想运维 agent 基建

记住这组对照：LangGraph 给你"流程图画笔"，Agents API 给你"一个已经会干活的员工"。前者赢在可控，后者赢在省事——代价是控制权。

Q3
Agent / Environment / Session / Events 四概念怎么咬合？

官方文档把 API 建在四个对象上，类比一个外包员工的工作档案：

概念是什么类比在请求体里
Agent模型+指令+工具+MCP 的配置包岗位说明书agent: {...} 或复用 agent_id
Environment可选的沙箱/电脑：跑命令、放文件、装技能工位environment: {type: ...}
Session持久化的 agent 实例：干活的主体，跨轮次存活员工本人在册创建后返回 sess_... id
Events & Items你发进去的输入、它干出来的每一步记录工作日志stream 事件 / sessions.items
易混警告：Session ≠ SDK 的 session ≠ Responses conversation ≠ sandbox，是四种不同资源。SDK 的 session 是你进程里的对象；Agents API 的 session 是存在 OpenAI 服务端的持久资源，可以 delete、retrieve、跨天继续。这是"会话即资源"（session as a resource）的思路——对照知识库 [[Checkpoint存档与持久执行]] 里 thread_id 一人一档的思路，OpenAI 把它做成了第一等 API 资源。
Q4
三层运行时（Agents API / Agents SDK / Responses API）怎么选？

OpenAI 现在有三条做 agent 的路，官方对比表的"人话版"：

Agents APIAgents SDKResponses API
用一句话选它长任务，OpenAI 替我管进度agent 循环要在我的应用里只要模型响应，循环自己写
循环跑在哪OpenAI 云（托管 Codex）你的进程你的进程
接入成本低中高
任务间状态session 自动存你自己的存储手动拼历史
执行环境官方沙箱/自有沙箱/无你的运行时你自己的环境
✅ 决策口诀：要"全自动代驾"→ Agents API；要"方向盘在我手里"→ Agents SDK（即知识库里 [[智能体框架]] 的角色，OpenAI 版）；只要"发动机"→ Responses API。注意别和 openai-agents 这个 pip 包搞混——那是 2025-03 的 Agents SDK，和新 Agents API 是两代东西（本机实测：装了 SDK 3.24.0 后 openai-agents 0.20.0 报依赖冲突，两代并存是个坑）。
Q5
"长任务自动压缩恢复"是怎么做到的？

长任务的死穴是上下文窗口：干几小时，历史记录爆窗。Agents API 的答案是托管压缩（automatic context compaction）——harness 把"总结之前的工作"当成常规操作，窗口快满就自动摘要旧进展、保留关键状态，任务不中断。推文说的"长任务自动上下文压缩恢复"就是它。

我们在开源 codex 仓库里找到了它的源码实锤（见 ex4）：

// codex-rs/core/src/compact.rs —— 压缩是一等公民，不是补丁
use codex_analytics::CompactionReason;   // 为什么压：自动触发 or 手动
use crate::context::CompactionSummary;    // 压出来的摘要对象
// 配套: compact_token_budget.rs / compact_remote_v2.rs /
//       compact_model_fallback.rs（压缩模型降级）

恢复则是另一半：session 的 turns/items 存在服务端，流断了可以 retrieve 回来续传（官方文档专门有一节 "recover a disconnected stream"），SDK 里 with_result_collection() 最后一帧给 final result + session_id。

对照已学：[[上下文预算与战略压缩]] 讲"50% 早压缩、逻辑断点才压、实现中千万别压"——这些是你自己写 harness 时的经验法则；Agents API 把同类策略做成了托管默认值，你不用再管。恢复侧对应 [[Checkpoint存档与持久执行]]（崩了从存档续跑不重花钱），区别：LangGraph 存在你配的 checkpointer 里，这里存 OpenAI 服务端。
Q6
Subagent 并行编排长什么样？

创建 session 时打开一个开关，主 agent 就获得了"招临时工"的能力：

"multi_agent": { "enabled": true, "max_concurrent_subagents": 4 }

之后 harness 在干活时会自己决定把独立子任务拆给并行 subagent（官方示例：对比多份 release notes，每份一个 subagent 并行读，最后汇总）。分工方式不是你画 DAG，而是 harness 自主拆解——这是和 [[工单任务图与前沿调度]]（你显式建模任务依赖）最大的差别。

对照已学：[[多智能体协作]]（crewAI 角色分工）是"你指定谁出场"；这里 harness 自己招人裁员，你只设并发上限。坑也对应 [[多Agent协作乱序竞态]]：并行的完成顺序≠依赖顺序，汇总逻辑仍要防"摘要先于数据定稿"。源码坐标：core/src/agent/control/execution.rs（实测命中 SessionSource::SubAgent(_) 分支）。
Q7
沙箱三态是什么？self-hosted 怎么连？

Environment 有三种形态，对应三种架构（官方 architecture 文档）：

type工位在哪能干什么适合
none没有工位回答问题、调远程 MCP / function 工具；没有 Bash、apply-patch、工作区文件问答、调研型 agent
openai_hostedOpenAI 云沙箱跑 Python/Node/CLI、改文件、产 artifacts；可配网络权限和依赖包写代码、跑脚本的通用型
self_hosted你的机器（笔记本/Docker/Lambda）你的代码起 executor 连上 session，harness 远程下发命令由 executor 执行私有网络、内网数据库、专有软件

self-hosted 的精髓：命令不是你转发给 harness 的，而是 harness 下发给你的 executor。你的代码只管 executor 的生死（开机、断线重连、关机），不需要逐条命令过手。key 永远不进沙箱（官方反复强调）。

✅ 本机实测（ex5，零费用）：装 npm i -g @openai/codex（0.160.0），codex sandbox python -c "print('hello')" 在 Windows restricted token 沙箱内成功输出；同环境尝试写文件 → PermissionError: [Errno 13] Permission denied，文件确实没落盘。这套沙箱和云上是同一个开源实现——开源仓库里 sandbox 家族有 5 个 crate：linux-sandbox / windows-sandbox-rs / windows-sandbox-service / mxc-sandbox / sandboxing。
Q8
程序化工具调用（Programmatic Tool Calling）被官方产品化了？

是的——正是知识库 [[程序化工具调用]]（CodeAct，cmu-agents 批次学的"模型写代码进沙箱一次跑完整策略"）的官方 API 版。创建 session 时声明：

"tools": [ { "type": "programmatic_tool_calling" } ]

打开后 agent 不再"每轮一个工具调用"，而是写一段代码把多个工具调用编排成一次执行（枚举→模拟→评估→选优一行循环搞定）。开源仓库里对应一整个 crate 家族：code-mode / code-mode-host / code-mode-protocol / code-mode-runtime + tools/src/code_mode.rs。

定位：CMU 作业里它是"自己搭的教学版"，现在 OpenAI 直接把它做成了 {"type": "programmatic_tool_calling"} 一个开关。从论文概念到产品开关只用了不到一年——这是本篇最值得记住的行业信号：知识库里那些"模式"正在快速变成云厂商的 API 参数。
Q9
harness 开源意味着什么？131 个 crate 里都是啥？

发布的核心事实：云上跑的 harness 和你电脑上能装的 Codex CLI 是同一套开源代码（openai/codex，Apache-2.0，127k+ stars）。官方公告原话 "backed by the Codex harness" + "view the public codebase"。实测仓库规模：131 个 Rust crate、5094 个 .rs 文件、约 200 万行代码。

开源意味着三件事：① 可审计——云上 agent 到底执行了什么逻辑，源码可查（本篇 ex4 就这么干的）；② 可自建——同一套 harness 可以本地跑（CLI），云 API 只是托管形态；③ 可学习——这就是市面上最完整的"生产级 harness 教科书"，[[AgentHarness智能体挽具]] 七职责每一条都能在里面找到对应 crate。

Q10
怎么计费？比直接调模型贵多少？

官方 pricing 一句话：模型按模型价、工具按工具价、沙箱按容器价——没有"Agents API 附加费"。具体三笔账：

账目怎么算
模型推理所选模型的标准 API 价（gpt-6-astra 等）
OpenAI 内建工具web_search 等按 built-in tools 标准价
托管沙箱openai_hosted 按容器（container）标准计费——沙箱开着就烧钱

风险点和 [[交易成本与鞭打效应]] 同理：账单放大器藏在"agent 循环圈数 × 沙箱时长 × subagent 并发数"。一次 session 主 agent 拆 4 个 subagent，token 消耗就是 5 条循环相加。session 记账有专门的 observability 端点（sessions.traces / usage），上线前先看这份账。

Q11
安全边界：API key 放哪？数据在哪？

四条红线，全部来自官方文档原文：

① key 权限最小化：会话操作要 api.agents.read + api.agents.write，模型推理要 api.responses.write——用应用级 key，别拿全家桶 key。② key 永不进沙箱：官方 quickstart 原话 "Keep this key outside the agent's sandbox"（agent 能执行任意代码，key 进去等于送给它）。

③ 数据驻留仅美国：目前只支持 US 数据驻留。④ 不支持 ZDR：Zero Data Retention 不适用，选 self_hosted 沙箱也改变不了这一点——harness 和会话状态始终在 OpenAI 侧。合规敏感场景要过一遍这条。

实测彩蛋（ex2）：无 key 请求返回 "A valid actor biscuit is required"——"actor biscuit" 是 OpenAI 内部鉴权层的术语，从错误信息能窥见服务端身份模型（actor = 发起动作的主体）。对照 [[控制面与数据面]]：认证闸门在控制面，一进 API 就验。
Q12
我能用它干什么？什么时候不该用？

能力清单（学完你手上多了什么）：

① 会话即资源的心智模型：把"一个长期干活的 agent"当数据库记录管理（create/retrieve/update/delete）；② 三态沙箱架构图：none / openai_hosted / self_hosted 的选型判断；③ 一套可读的生产级 harness 源码（131 crates），七职责逐条有实码；④ 本地 codex sandbox：零费用给任何命令套受限令牌沙箱；⑤ subagent 并发上限思维：multi_agent.max_concurrent_subagents 一个参数管并行度。

✅ 适合用❌ 不适合
长时自主任务（调研、批量改代码、事故排查）要接非 OpenAI 模型（锁生态）
需要断点续跑、服务端状态的 agent 产品要精细控制每步流程（选 Agents SDK / LangGraph）
个人项目快速获得"会干活的 agent"不想运维基建数据不能出内网/不能存美国（no ZDR）
内网自动化（self_hosted executor 连私有网络）高频短调用（沙箱容器费可能比模型费还贵）

给你的行动建议（结合你已会的）：先用 local CLI + sandbox（免费部分）体会 harness；要写 agent 产品时拿 quickstart 的 session 流程对接自己的 webhook；架构选型时把本篇 Q4 三层表和 [[Agent设计模式目录]] 的 Level 0-3 对号入座。
