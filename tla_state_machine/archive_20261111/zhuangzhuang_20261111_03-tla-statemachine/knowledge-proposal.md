# 有限状态模型检查与反例

**定义**：用Init与Next描述系统，遍历所配置有限模型的全部可达状态，逐状态检查启用的不变量，失败时给出到违规状态的反例前缀。有限图有环可表示无限行为，因此不是逐条枚举所有无限路径。

**通俗理解**：不是试开几次车看有没有撞墙，而是在一张明确画出的有限路网里检查每个能到的路口；路网没画出的道路和路况不会自动被证明安全。

**工程纪律**：
1. 先约定paid等变量语义、原子边界、环境与规模；模型必须对应可打开的实现函数。
2. 定义性质还要在cfg启用；通过只覆盖已启用性质。安全性不推出活性，公平性不是可随意添加的现实保证。
3. generated、distinct与queue分开读；预期反例的TLC退出12不是基础设施失败。驱动整体退出0仅表示它检测到了预期红灯，不代表bug模型通过。
4. 修复保持性质不变；先证明检查能在目标变异上失败，再确认基线通过。不能为绿灯删规则、改边界或屏蔽出错状态。
5. 代码改变后审查模型是否仍对应，区别in sync/updated/bug/blocked；不能靠旧绿灯宣称新代码安全。

**本轮锚点**：订单TOCTOU反例5状态4转移；固定版5个不同状态；N=2/3对应25/125。均为真实TLC结果，但只是合成系统有限实例。

**关联**：[[LangGraph与Agent编排]]（图编排不是模型检查）、[[工具调用生命周期]]（非原子领取/副作用）、[[动作投递语义与安全重试]]（外部效果未定不能盲重试）、[[证据优先质检ProofOverClaims]]（声明与运行证据分开）。
