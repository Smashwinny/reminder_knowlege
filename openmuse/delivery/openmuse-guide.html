问题 01 / 先看产品边界

它为什么不只是一个聊天窗口

OpenMuse 把对话、长期任务、审批和结果放进同一个应用。

同一件事有不同层：界面展示，服务编排，数据库保存状态，适配器才接触外部系统。

用一个具体任务理解

假设你让应用处理一份虚构的活动表单：它需要读材料、等你补充字段、保存新 PDF、提出发信审批，最后记录结果。聊天消息负责交流，任务对象负责记住这件事做到哪里；两者不是同一个数据结构。

已有知识在这里怎样落地

可复用 [[AgentHarness智能体挽具]] 与 [[工具调用生命周期]] 的公开概念，本指南不重讲智能体基础。OpenMuse 的新增看点是：AgentTask 有 status、state、actionId、artifactIds；这些字段把等待、恢复、审批和产物关联起来。

先选一个足够小的学习切口

本次实际运行任务引擎、审批服务和 PGlite 存储的核心切片，不启动完整前后端。没有配置模型、Google、CopilotKit Intelligence 或电脑服务，因此不能把后面的测试通过读成个人助理已部署。

参考回答：靠服务端保存的任务状态与仍在运行的执行服务；聊天界面不是任务状态的唯一存放处。

问题 02 / 从界面走到数据

为什么要把计划状态和结果分开存

任务的当前状态回答“现在怎样”，运行记录回答“这次发生了什么”。

一个任务连接可变进度、历次执行记录和可展示产物。图中是数据关系，不表示每个写入都在同一事务中。

四类信息各有职责

plan 是步骤列表，state 是执行器约定的恢复数据；runs 按一次执行保存开始和结束；run-events 写可读事件；artifactIds 指向结果。把一切塞进最后一条聊天文本，程序就很难稳定判断是否该继续。

数据库怎样容纳它们

Store 使用 records 表，以 owner、kind、id 为复合主键，data 为 JSONB。JSONB 是能被 SQL 条件查询的 JSON 数据。kind 区分 tasks、actions、runs 等记录；get/list 会带 owner 条件，避免把不同拥有者的数据混在一起。

留下记录不等于完成审计

记录便于追踪，但本切片没有证明追加不可改、防篡改、完整事务审计或多租户安全认证。把它接到已有 [[产物留痕与状态外置]]：应同时看实际状态、日志与产物，不能只看一条“成功”文案。

自测：为什么一个任务可能有多个 run？

参考回答：每次领取都会建立一次执行记录；任务重试或过期接管后仍是同一任务，却是新的执行尝试。

问题 03 / 真正运行的数据库

PGlite 保存了什么 又没替你解决什么

这次用的是真实 SQL 数据库，不是用字典假装持久化。

内存实例用于多数测试；文件目录实例用于关闭再打开的持久化检查。两条路径都执行真实 SQL。

存储选择来自代码分支

createStore 若收到 databaseUrl，就创建 PostgreSQL 连接池；否则创建 PGlite。PGlite 是嵌入式 PostgreSQL 实现。本实验使用后者；未连接独立 PostgreSQL 服务，不能宣称跨进程数据库部署已验收。

持久化的可观察证据

文件测试先写入数据，正常 close，再对同一路径 createStore 并读回。过期任务测试还会读回保存的 state。这个过程支持“正常关闭再打开后数据仍在”，而没有制造断电、进程强杀、磁盘损坏或备份恢复。

工程选择的边界

README 提醒不能由多个独立进程共同打开同一份 PGlite；独立任务进程应使用 PostgreSQL。本次两个 TaskWorker 共享一个 Store，只能观察同进程并发争抢，不能把它类推成分布式集群测试。

自测：两个 Worker 实例并发，是否已经验证两台服务器？

参考回答：没有。实例、进程、主机是不同层次，本实验只有同一进程中的多个实例。

问题 04 / 条件更新与争抢

两个 Worker 同时看到待办 谁能执行

先读到任务还不算领取成功；必须赢得一次带条件的 SQL 更新。

两个执行器都可能读到 queued；compareAndSwap 让只有仍满足旧状态条件的一次更新返回任务。

CAS 是什么

Compare and Swap，中文可叫比较并交换：当记录仍符合 expected 条件时才应用 patch。Store 把它实现为一条 UPDATE，条件含 owner、kind、id，以及 data 包含指定旧字段；成功时 RETURNING 返回新记录，失败时返回空。

领取流程怎样利用它

TaskWorker 先扫描候选任务，再用旧 status 与 leaseId 作条件；若接管 running 任务，还比较 leaseUntil。胜者把任务写成 running，并生成新的 leaseId、截止时间和尝试次数。败者拿不到更新结果，立即返回。

避免过度承诺

这比“先读再无条件写”更可靠，但它只把数据库中的领取变成条件更新，不把远程发信和本地写入合并为一个原子事务。已有 [[多Agent协作乱序竞态]] 在这里有了可以指到具体 SQL 的案例。

自测：为何不能只在 JavaScript 里判断 status 等于 queued？

参考回答：读完到写入之间其他执行器可能已领取；必须在数据库更新时再次比较旧条件。

问题 05 / 租约与栅栏

租约过期 为什么旧 Worker 不能继续写

leaseId 是本次执行的身份凭据；新执行接手后，旧凭据不能更新当前任务。

时间到期使任务成为可接管候选；新 leaseId 写入后，旧执行器的条件写入会失败。

租约与永久锁的区别

租约是有截止时间的执行资格。默认 leaseMs 为 60 秒，心跳约每三分之一个租期尝试续约。过期 running 任务可进入候选队列，防止一个失去响应的执行器永久占住任务。

真正挡住旧写入的条件

guard 检查中止信号、当前 leaseId 和 running 状态；checkpoint 用 leaseId 与 running 做 CAS。注意 guard 本身并不单独检查墙钟是否超过 leaseUntil。到期是允许接管的条件，新租约或状态变化才使旧执行身份失配。

这道栅栏保护到哪里

栅栏在这里指“用执行身份拒绝过期执行器的写入”。这是 UUID 身份比较，不是外部提供方强制检查的单调递增 fencing token。外部请求若已经发出，数据库无法把它收回来。每次不可逆动作前仍需要守卫、审批和外部服务的结果核对。

自测：刚超过 leaseUntil，尚无人接管，guard 一定抛错吗？

参考回答：不一定。代码检查的是中止、租约身份和状态，并没有直接比较 leaseUntil 与当前时间。

问题 06 / 恢复语义不能想当然

检查点能让程序从哪一行继续

本项目保存的是业务状态；如何跳过已完成工作，由任务处理器决定。

重新执行处理器时能拿到已存状态，不等于恢复任意 JavaScript 指令位置。

检查点里到底是什么

TaskContext.checkpoint 接收 AgentTask 的局部补丁，例如 state 中记录已完成步骤和文件 ID。它通过租约条件更新任务，再把新任务放进当前局部变量。保存粒度由调用代码决定，不是自动捕获整个进程内存。

上游测试真正观察了什么

测试先手工写一条租约已过期、state 含 completedStep 和 fileId 的记录，关闭并重开数据库。新处理器读到这份 state 并完成。测试证明状态被读回和任务可被接管，没有证明某次真实表单流程所有副作用都不会重做。

和已有 Interrupt 知识的连接

已有笔记中“恢复一定从暂停那一行继续、之前代码不重跑”过于绝对。LangGraph 的恢复也可能从节点起点重入；OpenMuse 这里更没有采用该框架的续执行承诺。需要把可重放计算和外部副作用分开，并用幂等键或结果核对保护后者。

自测：恢复时是否可以无条件重新发一遍邮件？

参考回答：不可以。先核对已保存动作状态和外部结果；检查点并不天然保证副作用只发生一次。

问题 07 / 取消的真实边界

点了取消 已发出的请求会消失吗

取消能阻止后续步骤；已经在途的外部操作仍可能完成。

时序决定边界：检查点前能拒绝新的动作，外部系统已经接收的请求不能靠本地状态撤回。

本次能够验证的取消

上游测试在处理器内把任务改成 cancelled 并清空租约，随后调用 guard，再尝试增加效果计数。guard 抛错，计数保持 0。这是“下一效果前有守卫”这一条路径的真实验证。

没有被测试替你保证的事

如果处理器没有调用 guard，或 guard 通过之后远程请求已经发出，本地取消不等于远程撤销。TaskWorker 的 AbortSignal 是协作式中止信号，外部调用必须支持并正确处理它，且仍可能出现返回丢失。

等待审批也有调度含义

任务在 waiting_approval 时，如果动作仍 awaiting_review 或 executing，就继续等；动作到期可被标为 expired。测试还检查等待审批不会让排队任务饿死。等待不是执行线程一直占着一个聊天请求。

自测：界面显示 cancelled，可以直接认定钱没付或信没发吗？

参考回答：不能。要看动作状态、提供方回执及实际结果；本次完全没有调用真实支付或邮件服务。

问题 08 / 审批绑定

审批的到底是一句话 还是一份快照

批准必须对应存下来的动作内容、账户连接和版本信息。

hash 把审批展示过的准备结果关联起来；它不是权限本身，也不是远程提供方的执行回执。

准备阶段做了什么

ActionService.propose 校验输入，查询连接，可调用 prepare 得到权威目标详情，再保存 proposal。hash 根据 input、connection、target、targetVersion 计算；有效期是 30 分钟。审批不是随口说一个 yes 就能替换成另一封邮件。

决定阶段再次检查什么

decide 查询对应拥有者的动作，检查 hash、状态、关联任务是否允许运行、有效期以及连接是否仍是同一账户与 connectionId。重新连接同一邮箱也可能有新的连接 ID，旧审批不能直接沿用。

版本测试容易被误读

上游测试把 revision-1 保存后，再把准备端版本改为 revision-2；批准旧提案时 fixture 仍收到旧 revision-1，且返回 succeeded。它证明保存版本被传给 execute，不证明真实 Google 服务拒绝旧 ETag；实际 HTTP 条件写校验属于另一层。

自测：目标版本变了，这个测试是否一定让旧审批失败？

参考回答：不是。这个 fixture 验证旧版本参数被传下去并返回成功；不能据此宣称远程版本冲突已实测。

问题 09 / 两种去重机制

重复点击和重复准备 是同一个问题吗

重复批准靠动作状态领取；重复准备靠幂等键和唯一插入。

上面保护既有动作的执行入口；下面保护准备动作时的记录身份。两条线不能互相替代。

幂等键解决哪一层

幂等性表示同一请求重复到达时，复用已有结果而不重复建立相同工作。propose 若收到 idempotencyKey，用其 SHA-256 作为动作 ID，先尝试读取已有记录，再用 insertIfAbsent 防止并发插入两个提案。主键仍包含 owner。

并发批准如何只进入一次

Store.claim 是带 awaiting_review、未过期以及关联任务状态条件的 SQL UPDATE。只有领取成功的一次 decide 才调用 execute。上游测试同时批准同一提案，检查 fixture 调用次数为 1、保存状态为 succeeded。

仍然需要设计请求身份

复用同一个幂等键会直接取回已有提案，包括已完成结果。调用者必须让键准确代表同一逻辑动作；这不是可随意复用的“万能重试按钮”。真正外部服务的一次性效果仍要考虑网络中断和提供方幂等机制。

自测：同一个键、另一个 owner，会读到前一个人的提案吗？

参考回答：本 Store 的读写主键含 owner；上游测试检查另一个拥有者得到新的待审提案。仍不等于完整多租户系统已通过安全审计。

问题 10 / 不确定外部结果

没收到回执 为什么不能自动再试

没有成功回执，不代表动作没有发生。outcome_unknown 要单独保留。

“外部是否完成”和“本地是否收到响应”是两个问题。未知状态不能轻率降级成可重试失败。

一个容易重复发信的故事

假设邮件服务已接收请求，响应却在路上丢失。如果软件把超时一律当成没发送，重试会再发一封。ActionService 识别 outcomeUnknown=true 或 code=outcome_unknown 的错误，持久化为 outcome_unknown。

本次测试观察到的行为

注入 execute fixture 首次被调用便抛出未知结果错误；再次批准同一个提案，decide 因状态已经不是 awaiting_review 而直接返回，fixture 调用次数仍是 1。没有真实邮件发出；未知情形是受控注入。

重启恢复也保持谨慎

Store.recoverInterruptedActions 可把留在 executing 的动作改为 outcome_unknown。它不是自动重放外部写入。工程上下一步应查询提供方、收集回执，再决定是否需要新动作；仅凭任务“可恢复”不足以承诺全链路 exactly-once。

自测：outcome_unknown 是否等价于 failed？

参考回答：不等价。前者承认无法确定外部是否已完成，避免盲目重试造成重复副作用。

问题 11 / 读当前代码而非旧宣传

浏览器终端桌面 是同一种电脑能力吗

当前代码已有 Docker 与 E2B 桌面分支；本次没有启动任何一种电脑。

图示区分浏览器服务与电脑后端。各自需要自己的运行环境；代码存在不等于部署完成。

接口相似 环境却不同

Browser worker 提供 Chromium 会话；ComputerBackend 提供启停、执行命令、文件等能力。DockerComputer 声明 network=disabled；配置类型还允许 e2b-desktop，E2B 分支有桌面流与 SDK 交互。不能把旧 Docker 的所有限制概括到新后端。

为什么 README 不能独自作证

固定提交的 README 仍把 graphical desktops 写成未来工作，但同一版本的 config.ts、computer.ts 与 computer-e2b-desktop.ts 已包含 E2B 桌面路径。这里以代码定位说明差异，保留“实际运行未验证”，不替上游编造统一成熟度结论。

学习时怎样划安全边界

参考回答：不能。要分别阅读和验证每个提供方的实现与部署配置。

能力与用途

五项能力和五个具体用途

把项目作为可拆解的应用样本，先验证核心，再决定是否连接真实服务。

可见的任务生命周期

代码把 queued、running、等待输入、等待审批、暂停与终态存为结构化状态；可以追踪长任务进度。

带租约的任务领取

CAS、心跳和租约身份帮助协调执行器，允许接管保存过状态的任务；仍需处理器正确设计恢复逻辑。

持久审批和结果分类

动作快照、内容 hash、连接身份、有效期与执行领取绑定，区分拒绝、失败、成功和未知外部结果。

能力适配与结果展示

应用连接浏览器、电脑、文档、Google 等适配器，并提供对应结果界面；外部能力需要独立配置和验证。

可复用的学习切片

核心测试能在不接真实账号的条件下验证若干边界；练习包保留原始源码、许可证、版本与完整日志。

五个用途

  1. 为自己的助理原型设计任务状态，区分任务、执行尝试、事件和最终产物
  2. 给邮件或日历原型加“准备快照再批准”的流程，先用 fixture 验证拒绝与过期
  3. 给后台任务加入租约身份检查，写一个取消后不得继续下一效果的回归测试
  4. 评估开源智能体项目时，制作“源码已实现、实跑已验证、真实服务未验收”的证据清单
  5. 把重复点击、版本变化、超时未知三类故障分别建模，减少盲目重试造成的重复动作
