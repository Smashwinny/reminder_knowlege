01

Patchright Enhanced 到底包住了什么

它把配置和会话组织起来，真正的浏览器仍由底层库创建

wrapper 就是包装层：在已有库外，补上常用的配置、调用次序和资源管理。这个 TypeScript 项目依赖 Patchright；仓库名是 patchright-enhanced，package.json 的包名却是 ghostprobe，检索时要对准仓库与提交。

像实验室里接好的仪器架：机架让操作顺手，却不等于换了测量仪器。这里的机架是 SessionManager、SessionRunner、BrowserManager；底层调用位于 context-factory.ts。

与 Agent-Reach 公开笔记只作一层衔接：工具路由负责选工具，本项目负责自己的配置与会话。两者不是同一层。

证据 源码阅读；没有运行底层浏览器

02

读到网页文本就算浏览器跑通了吗

检索、渲染和完成任务，各需要自己的证据

HTTP 检索是取得响应文字；浏览器渲染是执行页面环境并画出画面；任务成功还要求结果满足需求。取得 HTML 不证明脚本执行，也不证明按钮能点。

例如课程页面：能读出“提交”两个字，只证明文本存在；看到按钮，仍不能证明已提交。本轮只运行本地包装层单元测试，连真实浏览器启动这一关都没有验证。

03

从入口到关闭会经过哪些对象

会话调度、单次运行和资源关闭各有主人

main.ts 读配置后反复发起一轮会话；SessionManager 为单次运行建立状态；SessionRunner 调用创建函数、打开起始页，并等待关闭事件；BrowserManager 保存 context 与临时目录的引用。

生命周期指资源从创建、使用到释放的过程。这里需要特别看“何时接管”：只有 createBrowserContext 返回后，setContext 才登记资源；创建途中出错是否善后，不能靠后面的 finally 想当然。

已有“工具调用生命周期”谈的是 MCP 调用循环；这里谈资源所有权，仅关联，不同义合并。

04

README 的默认值就是实际默认值吗

没有环境变量时，MAX_PARALLEL 是 2，起始 URL 是空字符串

默认值是调用者没有提供值时程序选用的值。README 与 .env.example 写的是 MAX_PARALLEL=1、START_PAGE_URL=https://google.com/；源码直接调用时分别回退到 2 和空字符串。

两者能同时存在：把 .env.example 复制成 .env，且通过 main.ts 加载 dotenv，是一条输入路径；直接调用配置函数且环境为空，是另一条路径。要记录前提，不能把示例配置当成函数默认值。

实验会分别显示空环境与显式输入。这里不是文档改错实验，也不会启动页面。

05

MAX_PARALLEL 写成 oops 会被拒绝吗

parseInt 是转换函数，不是配置校验器

parseInt 把字符串开头能识别的整数读出来；NaN 表示“不是一个有效数字”。源码没有追加正整数、范围或完整字符串检查。实验矩阵会展示 3、0、负数、带字母后缀和完全非数字输入的区别。

例如“2junk”能被读成 2，却不意味着“2junk”是合法并发配置。调用端的循环可能因此走不同路径；本轮验证的是解析结果，不是实际并发性能或完整主循环。

改一个输入立即看到输出变化，是本实验的中间成果。若用于真实工程，应另加有限、正整数和上限校验。

06

Context 和 Page 为什么不是一回事

Context 是会话环境，Page 是其中的一张页面

BrowserContext 表示浏览器会话环境；Page 表示页面对象。此项目调用 launchPersistentContext(userDataDir, options) 创建带用户数据目录的会话，再调用 context.newPage()。持久目录可承载会话状态，不能把“新 Page”直接理解成“全新身份”。

这里的工厂返回 context、page、tempDir 三件东西。就像打开同一工作间里的另一个窗口：窗口多了，工作间仍是同一个。隔离效果、目录内容与实际浏览器行为，本轮都没有端到端测量。

不要与“健康探测三态”混淆：missing/broken/timeout 是诊断分类，不是 Browser/Context/Page 三层对象。

07

为什么关闭要 await，清理却是同步调用

先等关闭完成，再清理目录；顺序本身就是契约

异步操作用 Promise 表示尚未完成的结果；await 等待它结束或抛出错误。BrowserManager.close() 等待 context.close()，成功后才把引用设为 null；cleanup() 调用目录清理函数后清空路径引用。

closeAndCleanup() 顺序调用两者。实验的假 context 只记录 close，假的清理函数只记录 cleanup；它们不打开浏览器、不删除目录，却能证明真实管理器调用了谁、先后次序怎样。

“接缝与桩实现”在这里落地：换掉危险的外部效果，保留真正要检查的管理器逻辑。

08

关闭抛错后，目录仍一定会清理吗

当前顺序里，close 拒绝会跳过后面的 cleanup

拒绝是 Promise 的失败结果。closeAndCleanup() 没有自己的 try/finally；若 await close() 抛出错误，执行流直接离开函数，cleanup() 不会被调用。故障注入就是让替身按预定方式失败，再观察真实代码。

实验用合成错误证明这个分支，绝不声称实测了浏览器崩溃。修复思路可考虑 finally 中处理清理，并分别保留关闭与清理错误；但也要定义“关闭未完成能否删目录”，本教材不修改上游。

失败不是一句“没跑通”：要写清发生层、异常如何传播、哪些后续动作没有发生。

09

为什么还要测试重复关闭和失败后再关闭

一次成功看不到资源管理的边角行为

幂等性指同一动作重复执行不会产生额外效果。成功关闭并清理后再次调用，引用已经清空，理应没有第二次外部调用；关闭先失败、下一次成功时，路径是否还在，则决定后续能否清理。

还有所有权问题：setContext 只替换两个字段，本身不关闭旧资源。若重复登记新 context，调用者必须知道旧对象由谁负责。这里只验证能被桩观察到的调用行为，不把局部结果升级为“所有异常都安全”。

L05 确认成功后重复调用无额外效果；L07 确认关闭失败后的一次合成重试可继续清理。清理函数自身抛错尚未测试。

不安装 Patchright，测试的还是上游代码吗

运行固定的真实函数，替换边界依赖，并记录改写范围

看到源码矛盾，为什么不能直接写构建失败

静态疑点、编译结果和运行结果必须分栏

BrowserConfig 把 locale 声明为必填，但 getBrowserConfig 的 locale 行被注释；package.json 与 pnpm-lock.yaml 的依赖条目也不一致。这些都是该提交可定位的源码事实。

本轮没有可用 tsc，也没有安装上游依赖，因此没有编译器报错日志，不能写“构建已失败”。同样，仓库跟踪文件中未发现 LICENSE，不代表可以自由再分发或商用；应先核实许可。练习包只发自建脚本与源码指纹。
