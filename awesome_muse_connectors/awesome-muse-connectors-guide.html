Q1

这个仓库是什么？一句话能说清吗？

Muse（Meta 的个人 AI 助手）的社区连接器目录：固定版本中 158 个连接器条目加 1 个模板，给出能力描述、认证方式、允许主机、操作边界和成熟度——但它是独立社区目录，不隶属 Meta、不被 Meta 验证。Meta 官方也明确：用户自定义连接器不由 Meta 审核。所以这份目录是"审查线索集合"，不是"可放心安装的商店"。

Q3

可复用的五段审查框架（抽样条目结构）

每个连接器 SKILL.md 五段对齐法：
①Auth：凭据类型/收集流程/HTTP 头细节（如 x-api-key ≠ Bearer）
②catalog_hosts：允许主机白名单（越界主机=风险信号）
③Operating Rules：写操作确认门（如 email_send 需 --confirm）
④Files：文件清单与来源可核对
⑤Maturity：Draft(照文档写) vs Live-tested(带日期+命令证据)
这套五段法不限于 Muse——审查任何社区 Agent 技能/MCP 工具包都适用（与 [[技能路由器与授权硬门]] 的授权硬门思想互证）。
Q4

成熟度标签怎么读？（Draft vs Live-tested）

"🧪 Draft: written from public API docs; not yet live-tested"=按文档写就、未做端到端实测；"✅ Live-tested on 日期: 命令清单"=条目声称在真实 API 上跑过列出的具体命令。后者只证明所列命令与环境，不证明整个连接器、所有参数或今天的兼容性。Draft 先当待验证假设；Live-tested 也要复跑同一命令并核对当前版本。

Q7

装社区连接器前的五问（交付清单）

①Maturity 是 Draft 还是 Live-tested（有日期证据）？
②Auth 段凭据走什么流程？会不会经过第三方？
③catalog_hosts 白名单是否最小？
④写操作有没有确认门？（高风险写操作无硬门则拒绝或先补门）
⑤它读到的数据会进谁的历史/记忆？断开连接删得掉吗？
Q8

目录 vs 商店：社区目录的正确心态

应用商店可能有平台审核，但审核本身也不是绝对安全保证；社区目录更像线索集市。目录的价值是省得你从零找，审查责任一点没省。这个仓库把"非 Meta 验证/不审核自定义连接器"写得很清楚——读目录的人也要把这句话读进去。

Q9

这套审计法怎么用到自己的项目？

给自己的 Agent 引入任何外部技能/MCP 时：要求提供五段说明（Auth/Hosts/Rules/Files/Maturity），没有 Maturity 段的默认按 Draft 对待；高风险写操作无硬门则拒绝或先补门。把五段法写进项目 AGENTS.md，团队审查就有统一刻度。
