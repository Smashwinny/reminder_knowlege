Q1图生 3D 是什么？和我学过的 TripoSR 什么关系？

一句话：上传一张设计图，几十秒后得到一个能拖着转、能下载的 3D 模型（GLB）。背后的学术底座就是 vault 里已学的 [[LRM大型重建模型]] 前馈范式——TripoSR 是 Tripo（VAST）的开源研究版（2 秒本地出灰模），Tripo Studio 是同一家的商业产品管线：灰模只是起点，后面还挂着贴图生成、智能拆分、重拓扑、自动绑骨一整条服务链。

🔗 互链：[[LRM大型重建模型]]（一次前向出 3D 的原理）、[[Triplane三平面表示]]（内部表示）、[[glTF与GLB资产管线]]（产物格式）、项目笔记 [[项目笔记/triposr]]（开源版实测）。
图1：从一句话到能跑的场景——本书的整条流水线（类比 [[混合模型分工流水线]]：设计流出 AI，机制流出代码）
这条流水线的分工哲学（§15）：近景要细节的交给 AI 模型，远景只要"那儿有个东西"的交给代码——巴黎城里 2 万株行道树是程序化的（9 个绘制调用/8.4 万三角面），只有近景 110 株用 Tripo 的 GLB。

Q2"Generate 50"这个数字是怎么算出来的？

花叔干了件笨事：坐在表单前把"几何与贴图"弹层里的开关一个一个动，看按钮上的数怎么跳（全程只看不按，0 积分）。跳出来的结构特别规整：

状态按钮拆解
只关掉 Texture（灰模）⚡15几何底价 = 15
贴图 2K⚡30+15
贴图 4K⚡40+25
贴图 8K（默认！）⚡50+35 ← 默认价的一半在买 8K 贴图
8K 再开 Ultra Mesh⚡65Ultra 另算 +15（不在默认 50 里）
智能网格 P2.0⚡65 + 30网格 65（原价 100 划线），贴图另付 30
默认 50 分里 35 分买的是 8K 贴图——而做网页/游戏导出时本来就要降到 1k。生成选 2K、导出选 1k，两头都省：一件 30 vs 一件 65，×40 件差 1400 积分，接近半个月订阅额度（专业版 ¥140/月 3000 积分，免费档 200 积分约 13 个模型）。
三个账单陷阱：① Ultra 那 15 分不在默认 50 里，算进去预算凭空多四分之一；② "自动保存您的设置"是跨会话的——为特写件开的档会一直跟着后面每一件；③ 首页快捷框和工作台默认值不同（55 vs 50），规矩只有一条：以按下去之前按钮上当场显示的数为准。

Q3面数框骗局：同一个 8000 为什么不是同一个 8000？

两种模式的"面数"框数的不是同一种面：高精度模型（v3.1）出三角面，那个数就是三角面；智能网格（P2.0）出四边面，那个数数的是四边面。引擎最终只认三角面——四边面进引擎要拆成两个。E10 实验（同一张出租车图、都填 8000、只换模式，输入图 SHA-256 三方对齐）：

A 高精度 v3.1（15 分）B 智能网格 P2.0（65 分）
原生面7,379 三角面8,596 四边面（占 79.51%）
三角化后7,37915,431
顶点3,6468,580
同一个 8000，智能网格拿到的几何预算是高精度的 2.09 倍——B 的保险杠栅条、大灯圈、门把手、雨刷全都在，A 同位置是几块糊过去的面。跨模式比面数先换算，不然结论会反。
图2：同一个数字在两种模式里买到的东西（E10，输入 SHA-256 逐字节锁定）
面数框另外两个咬人处：它是目标不是硬上限（38 件里 35 件超出设定，中位超 13%）；"自动保存"管不了它——每件都要重设。凯旋门那件：浏览器自动化往框里打字 15000，界面明明白白写着 15000，接口读回 face_limit=5000（默认值），65 积分打水漂。根因是响应式框架托管的输入框：直接改 DOM 的 value，框架内部状态收不到通知。正确写法是调原型 setter 再补事件，硬验证是设完按一下 → 方向键：变 15002 说明真进去了，跳回 5002 就是白设。

Q4减面还是重拓扑？能减到多少由什么决定？

减面（decimation）在原来的面上合并删减，拓扑变乱；重拓扑（retopology）是同一形状重新铺一张规整的网（10 积分，要进 Blender 改/绑骨才需要）。先说反直觉的事实：巴黎 29 件资产面数 16,711~46,196、中位 18,509，没有一个超 10 万——整个项目一次重拓扑都没用上。所以第一个动作不是打开重拓扑页，是先数面数。

减面的下限由几何有多光滑决定：减面算法找相邻顶点判断"合并了看不看得出来"。连续曲面（人体）砍到 3.3% 还认得出是个人；建筑全是直角窗洞只能到 37~44%；铁塔的格构结构和树的分离薄片几乎砍不动（72.5%~95.3%）。光滑度 = 有多少个可以被牺牲的顶点。所以别拿一套统一参数跑全库：人物/载具/道具 0.25、建筑 0.45、树和铁塔 0.75。
情况动作成本
面数已在 1.5~3 万，做静态道具什么都不用做0
几十万面（镂空建筑）/ 要绑骨重拓扑（四边面）10 分

✅ 实验复现（见本指南实验一）：光滑球面 720 三角砍到 35（4.9%）触底；格构塔 1152 → 336（29.2%）触底，ratio 0.1/0.05/0.02 输出完全相同——"再减就崩"的硬下限现象亲手复现。

Q5卡顿的第一反应为什么应该是查贴图而不是减面？

小王子 demo 卡得没法看，本能反应是"减面、关泛光、砍阴影"。先量了一次：整条渲染链 GPU 只吃 0.37ms，预算（16.7ms@60fps）的八分之一都没用完——三角形是闲的。真凶在显存：

图3：显存才是瓶颈——只跑 gltf-transform resize --width 1024，几何一个面不动
指标改前改后倍数
贴图显存5.0 GiB0.22 GiB23×
GLB 载荷89.87 MiB12.30 MiB7.31×
资产就位3.90 s0.70 s5.6×
JS 每帧（中位）1.5 ms0.7 ms2.1×
三角面147,879 —— 未动
为什么显存这么爆：每个道具在画面里才几百像素，却挂着一张 8192² 底图，GPU 一直在做纹理换入换出，表现出来就是"卡"。用 resize 别用 optimize——optimize 默认顺手跑 simplify，而几何根本不是瓶颈。顺序：先量 GPU 耗时和绘制调用 → 量不出问题先砍贴图 → 再合并绘制调用 → 最后才轮到砍面。
按绘制调用分档比按三角面分档有用：巴黎 244 万三角 / 77 个绘制调用，渲染一帧 5.0ms，离预算还有三倍余量；"全场景 30 万面"那条流行经验值被实测推翻——照它做会把塞得下的东西砍掉。

Q6PBR 金属在白底上为什么死黑？（已亲手复现）

发动机 demo v1 深色底一切正常，v2 改纸感白底后整台机器变成一团黑影。原理：金属度高时漫反射被抑制，只靠直接光什么也看不见；深色背景把问题吃掉了，白底一换全暴露。模型没坏——缺的是环境贴图（scene.environment）。两条路：要金属质感就做环境贴图；不要就把 metalness 摁到 0（roughness 给足，让它以哑光身份好看）。最怕的是既不做环境贴图又保留高金属度。

studioEnv() 两个试出来的细节：① 渐变不能全亮——必须从 #ffffff 压到 #403c35 给暗部（摄影棚的黑旗），金属才有明暗对比；② 白底场景别用 ACESFilmic 色调映射（会把白底压成灰）。不需要任何外部 HDR 文件，canvas 画渐变 → PMREMGenerator 转环境光照。
连带坑：vendor 精选 5 个文件里 BufferGeometryUtils 不是可选的（r160 的 GLTFLoader 自己会 import，缺了的表现是"页面全白"而非报缺文件）；P2.0 资产只出一张 base color（没有法线图和 ORM），别拿着"Tripo 出 PBR 三件套"去 P2.0 产物里找不存在的文件。

Q7怎么把 Tripo 接进 Agent 工作流？五条路一个钱包

五条接入路其实是两类：让 AI 替你调生成（CLI / Codex 插件 / MCP——门槛是 Node 20+ 和一次浏览器登录）和把模型搬进你的软件（API / DCC Bridge）。三条 Agent 路都实测到"发起生成"才被拦下，拦的理由非常有教育意义：

Studio 订阅和 API 钱包是两套账，官方明说不互通。专业版订阅生成按钮照常能点，API Wallet 是 0/0 Credit——CLI、Codex 插件、MCP 三条路共享同一个 API 钱包，一分钱不通兑。要为 Agent 化使用单独充值。
路径门槛实测要点
Tripo CLI（npm -g tripo-cli）低doctor 未登录查 6 项/登录后 8 项；设备码登录 210 秒（页面会丢 query，验证码必须手打）；tripo view x.glb 白送一个零积分本地 3D 预览器
Codex 插件最低codex plugin add tripo-3d@openai-curated-remote 14 秒，不用 GUI；它不是 MCP server，是两个 Agent Skill，底层调同一个 CLI
MCP（CLI 自带 tripo mcp）中stdio server，5 工具（make/task_get/task_wait/balance/history）；配进 Claude Code：claude mcp add --scope local tripo -- tripo mcp --quiet --no-open
API（V3）高异步 task 轮询；官方 Game-Ready Character 管线 = image-to-model → rig-check → rig → retarget（约 105 秒/85 分）；V2 API 2026-11-01 下线
DCC Bridge低（要 Pro）浏览器生成一键推进 Blender/Unity 等 10 个软件，纯传输通道不涉 AI
退出码表值得贴在脚本里（把"白花钱"和"没花钱"分开）：3 认证错误 / 4 积分不足（没开始生成，不扣，实测印证） / 5 内容拒绝 / 6 任务失败（自动退款）/ 9 限流退避重试。另：quad=true 强制 FBX 输出——四边面拓扑存不进 GLB。
Agent 不该替你做的五件事：浏览器授权页点 Authorize（设备码流程的安全根基）、充值/领 14 天试用钱包、保证浏览器登录态、额度耗尽的决策、sudo npm 密码。

Q8P2.0 资产接入的五道工序与朝向陷阱

九月把沿街资产整批换成智能网格 P2.0 重出的件后发现：这是另一条路，坑几乎不重合。五道工序少一道就装不上去：

工序为什么
① FBX → GLBP2.0 带贴图只给 FBX（四边面存不进 GLB），浏览器不认；用 Blender headless 转（Creator 字段就是 Blender，同实现往返最稳）
② 降 8K 贴图8192²×26 件 = 9.3 GB，纸上就能算出来的显存灾难
③ 定 yaw朝向不能靠算（见下），每件渲六视图人工看
④ 烘变换旋转缩放乘进顶点，不写节点矩阵——"量的时候算了矩阵、用的时候没算"的不对称会让模型静默错位
⑤ 量 A/B 帧时间确认没把性能换坏（GPU timer query，见 Q11）
朝向三类资产三套惯例，混成一句话记一定会出事：绑骨人形与 +Z 差 90°（yaw=-90）；v3.1 静态行人朝 +Z（换 P2.0 时 -90）；v3.1 建筑朝 -Z（换 P2.0 时 +90，和行人反号而包围盒长得一模一样）；P2.0 家族 38 件里 36 件朝 +X，还有 2 个例外靠渲图读出来。包围盒推不出朝向（转 90° 只把 X/Z 互换，--yaw 90 和 --yaw -90 的包围盒完全相同），四视图分不出正反——必须渲六视图，在哪个视图里看见正面，正面就朝那个方向。
另一个"不像格式问题"的坑：KHR_mesh_quantization 的顶点是 normalized int16，自写解析器不认这个标志就把原始整数当坐标——1 米高的人读成 32767 单位，缩放系数算出 32783。一个只在一半输入上出错的 bug，比全错的难找得多。

Q9为什么整排行人会"同手同脚"？

巴黎城 18 个行人里 6 个共用同一个绑骨模型。第一版用普通 clone() 复制——所有实例共享同一副骨骼，于是一排队走正步。修法三件套：

import {clone as skeletonClone} from 'three/addons/utils/SkeletonUtils.js';
const root = skeletonClone(walkScene);              // ① 骨骼独立复制
const mixer = new THREE.AnimationMixer(root);       // ② 每实例一个 Mixer
mixer.clipAction(walkClip).play();
mixer.setTime((x*0.37 + z*0.11) % walkClip.duration); // ③ 相位按坐标错开，否则还是仪仗队
另外两条绑骨特有坑：① 切掉动画的位移轨——retarget 出的剪辑里 Hip.position Y 位移范围 1.338，而人才 1 米高；行走该是纯旋转，位移归游戏代码管，否则"走着走着弹回一大步"（Tripo 侧对应导出时勾"原地播放动画"）。② 带骨骼的模型不能用 Box3.setFromObject 量尺寸（包围盒缓存不随姿势更新，还叠 Armature 变换）——绕开 Three.js 直接读 GLB 的 POSITION accessor min/max，repo 里的 scripts/measure_glb.py 就是这个工具（还处理了蒙皮矩阵）。

Q10近景 AI + 远景程序化：这笔账怎么算？

巴黎城行道树：程序化实例画 2 万株只吃 9 个绘制调用 / 8.4 万三角面。想全换成 Tripo 的 GLB 树（15k 三角/株）？近景配额 150 株 × 15k = 225 万三角 = 整层预算的 26 倍。最终折中：近景 110 株 GLB（真实树冠+叶片贴图），中远景全程序化。

图4：AI 资产的面数成本撑不住数量——判据是"近景要细节，远景只需要那儿有个绿色的东西"（§15 分层）
接 GLB 树时还踩了缩放基准坑：城市层的 c.h 是"冠高"，GLB 树宽高比接近 1:1，按整树高度放大 2 倍时冠幅 14 米、而行道树间距才 8 米——整排糊成一堵绿墙。归一化前先问：这个资产靠哪个维度和邻居对齐？树按冠幅（heightScale 取 1.2）、建筑按临街面宽、人物按身高。还有一个一行代码的体检：顶点高度 p90 明显低于总高 70%，说明包围盒是被一根细杆/一顶伞撑起来的（取暖伞案例：桌椅从 1.1 米被压到 0.5 米），不能拿总高做归一基准。

Q11量性能：帧间隔会骗人，GPU timer 不会

换完 6 件资产要回答"有没有把性能换坏"，第一次就量错了：帧间隔被 vsync 锁在 8.3/16.6ms，两组资产中位数一模一样，差别全被锁没了。要量的是每帧 GPU 真正忙了多久——挂 WebGL2 扩展 EXT_disjoint_timer_query_webgl2 在 requestAnimationFrame 前后 beginQuery/endQuery，隔几帧收结果（GPU_DISJOINT 为真则丢弃）。三条协议纪律：

① 串行测量——另一轮和 headless 录屏抢同一块 GPU，量出中位 8.57ms/p95 61.8ms 的离谱方差，最小值和干净机器吻合判断是干扰，但这是推断不是测量，正确处理是丢掉重测；② 固定采样协议（刷新→自由漫游→回出生点静止采样）；③ A/B 表的结论是"量不出回归"而不是"变快了"——0.37ms 的差落在跑间噪声里，没有第二次独立跑就不说变快。把噪声读成改进，是性能测量里最常见的自欺，尤其在你正好希望它变快的时候。
🔗 这套"先量后动、噪声不当改进"与 vault 里 [[证据优先质检ProofOverClaims]]、[[事实与判断分离]] 是同一个家族：测量本身也要被怀疑（自测脚本的两个 bug 是同一轮清出来的）。

实验一：零依赖手写 GLB + 减面极限复现（验 §04 E1）

步骤1 怎么操作：python make_glb.py .（零依赖，照 paperroute 手写 GLB 先例）造两个网格：光滑 UV 球（连续曲面）和格构塔（细钢梁结构），都挂 metalness=1 铬材质。目的：拿到完全可控的测试资产。实现了：sphere_smooth.glb（720 三角）+ tower_lattice.glb（1152 三角），与笔算一致（球 2×24×16−48=720；塔 8 层×144=1152）。验证：
sphere_smooth.glb  bytes=14560  tris=720   verts=425  (indices.count/3=720)
tower_lattice.glb  bytes=23940  tris=1152  verts=768  (indices.count/3=1152)
步骤2 怎么操作：双通道对账——自写 count_faces（§04 口径 indices.count/3）+ 书 repo 的 measure_glb.py。验证：两通道顶点数一致（425/768），包围盒与构造值吻合（球 2×2×2、塔 1.0×1.0×3.0）。意外收获：塔按 Z-up 建，measure_glb.py 按 glTF Y-up 惯例把 Y 向 1.0008 当"高度"读出——亲手撞上书里"资产轴向/朝向不能想当然"的坑。
步骤3 怎么操作：npm i @gltf-transform/cli（4.5.1 装成本地依赖，印证书里"别每次 npx"的建议），对两个网格各跑 simplify，ratio 0.5→0.02。验证（真实输出）：
== sphere_smooth ==  ratio=0.5→359  0.2→144  0.1→71  0.05→35  0.02→42（触底反弹=到底了）
== tower_lattice ==  ratio=0.5→576  0.2→336  0.1→336  0.05→336  0.02→336（三档输出完全相同）
✅ 预期结果兑现：光滑球面砍到 4.9% 还是个球；格构塔 29.2% 触底、ratio 再小也不动——"减面下限由几何光滑度决定，格构结构几乎砍不动"亲手复现。
步骤4 怎么操作：npx gltf-transform optimize sphere_smooth.glb decim/sphere_opt.glb --compress quantize。验证：14,560 → 8,472 字节（−42%），量化压缩不需要运行时解码器（书里选 quantize 不选 draco/meshopt 的理由：沙盒里 WASM 解码器可能加载失败）。

实验二：PBR 白底死黑 A/B 复现与修复（验 §12 坑一）
