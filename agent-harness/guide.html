Q2

Harness 是什么？跟模型、prompt 是什么关系？

Harness（挽具）：模型之外的一切运行环境。一句话定义——模型是推理引擎，harness 决定它能看什么、能碰什么、什么能跨会话存活、什么算证据、什么时候必须停。Dario Amodei 解释 Claude Code 诞生时原话："Of course, you need an interface, you need a harness to use them"。

图1 · 模型（红）泡在 harness（绿框）提供的六个组件里

金句对照：Prompt engineering 改进指令本身，Harness engineering 改进指令被执行的条件。OpenAI 在《Harness engineering: leveraging Codex in an agent-first world》里也承认：agent 进展慢是因为"环境欠规格"（underspecified），不是模型缺能力——解法不是让 agent "再努力试试"，而是补上缺失的能力并让它可读（legible）且可强制（enforceable）。

Q3

为什么说"同一个模型，换个挽具就是完全不同的 agent"？

同一个模型：放进聊天框，它只能答题；放进带终端、测试、浏览器工具、项目记忆、隔离 worktree、审查循环的仓库里，它能交付软件。权重一个字节都没变，变的是挽具。这解释了为什么"换了模型还是老样子"——你只换了马，没换车。

Q5

"契约"和"地图"听起来玄，实际是什么？

契约：一份机器可校验的任务边界，比如"只准写 output/ 目录、产出物是 task_a.md、少于 10 字算失败"。它是防 agent 私改需求的合同——没有它，agent 可以完成另一件事还理直气壮。和机器人里的 [[策略观测向量与动作契约]] 同思想：接口先钉死，两边才不会各说各话。

地图：一个小小的根指南（CLAUDE.md / index），只告诉 agent"什么知识放在哪"，不把所有文档塞进上下文。详细知识贴在它治理的代码旁边，任务需要时才加载——这正是 [[分层按需加载]]：小入口常驻，大主体待命。nihaixia skill 实测入口只占 2.71%，就是同一原理。

Q6

ECC 是怎么把这套东西做成"操作系统"的？

ECC v2.0.0（2026-06）的仓库就是一部 harness 教科书：293 个 skills（按需加载的工作流，主表面）、68 个 agents（YAML frontmatter 定义 name/tools/model 的子代理）、94 个 commands（斜杠兼容层）、23 组 rules（常驻规范）、hooks（PreToolUse/PostToolUse/Stop 事件自动化）、contexts（动态系统提示注入），并适配 Codex/OpenCode/Cursor。

动手实验：30 行核心逻辑，搭一个会成长的迷你 Harness

材料在 agent-harness\exercise\：mini_harness.py（harness 本体）+ contract.json（契约）。驱动无头 claude -p（haiku）。以下每一步都在 Windows 11 真实执行，输出为实拍。

STEP 1 · 写契约：把"可以做什么"钉死在 JSON 里
操作：contract.json 定义 scope（"只允许写 exercise/output/ 下的 markdown"）+ 任务表（task_a/task_b）。
目的：职责①契约——模型还没出场，边界先立好。 检测：每次运行 start 事件都把 scope 记进日志。
STEP 2 · 跑第一个任务：契约 → 调用 → JSONL 日志
操作：python mini_harness.py run task_a
目的：职责⑥日志——每一步（start/success/fail/learn）追加进 logs/run_log.jsonl，带时间戳、耗时、花费、轮数。
✅ 预期/实测：[OK] task_a attempt=1 20.2s cost=$0.0413 turns=2，产出 output/task_a.md（模型写出了"挽具把模型的决策变成真实动作"的中文说明）。
STEP 3 · 验证门：说 DONE 不算数
操作：harness 在模型回复后执行 verify()——产出文件不存在或 <10 字节，直接判 fail 进重试。
目的：职责④验证与证据。 实拍名场面：第一版 harness 里模型回复"写入完成"，但 permission_denials 审计显示 Write 被无头模式拒绝（模型连完整内容都写好了！）——验证门把这次"假成功"拦下，重试 3 次全部记录在案。
✅ 预期：日志出现 "error": "产出物缺失或过小" ×3，随后修复权限（--permission-mode acceptEdits）后 attempt=1 即 success。
STEP 4 · 失败廉价 + 换模型不换挽具
操作：故意制造失败（多行 prompt 经 cmd.exe 断行）观察重试；改 MODEL = "haiku" 一行即可切换底层模型。
目的：职责⑥失败廉价（重试 + 审计定位根因）+ 证明 harness 与模型解耦。
✅ 预期/实测：日志连续 3 条 fail（每条带 attempt 和错误摘要），harness 不崩、可定位、改一行配置即恢复。日志不是装饰，是排障的第一现场。
STEP 5 · learn 命令：让 harness 醒来时更聪明
操作：python mini_harness.py learn task_a "本项目所有产出的 markdown，标题行必须以 [HARNESS] 前缀开头"，然后 python mini_harness.py run task_b——harness 自动把 memory.md 注入新任务的 prompt，任务文本里只字未提该约定。
目的：职责④记忆——昨天日志/教训固化，下次自动生效（ECC instinct 的最小雏形）。
✅ 预期/实测：[OK] task_b attempt=1 46.7s cost=$0.0542，打开 output/task_b.md——标题第一个词就是 [HARNESS]。模型没被告知，却遵守了它没见过的约定：这就是"harness 会成长"。
踩坑实录实验全程踩了 4 个真实的坑，每一个恰好对应一条 harness 职责：① 多行 prompt 经 cmd.exe 断行→调用全灭（→日志审计定位）② 模型谎报 DONE（→验证门拦截）③ 无头模式默认拒绝 Write，且 --allowedTools 是变长参数会吞掉后面的 prompt（→--permission-mode acceptEdits）④ learn 写入的记忆带尾换行，注入后 prompt 被截断（→脏记忆必须清洗）。
