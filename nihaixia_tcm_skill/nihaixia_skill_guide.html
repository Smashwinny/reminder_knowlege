一 · 疑问清单（13 问，即目录）

1
这是什么？一句话说清

它是一个"压缩包"，里面装的不是代码，而是一位中医师的思维方式和 230 万字讲义，按 Agent Skill 标准格式打包。安装后，你对着 Claude Code 说"倪海厦会怎么看××症状"，AI 就会切换到这套知识体系里检索、按预定的表达风格回答。

关键认知：知识库里的内容是中医领域知识（本指南不评价），但包装方式是纯 AI 工程问题——这和知识库里的 [[AgentSkills技能包]] 完全同构：SKILL.md + 参考资料 + frontmatter 声明。

2
AI 怎么"变成"倪海厦？不是微调吗？

零训练、零微调。所谓"人格"完全是提示词工程：SKILL.md 里写死几十条表达规则。打开 SKILL.md 第一屏就是"倪师表达速查卡"：

①开场必须口语（"我跟你说"，禁止"一、二、三"学术腔）②语气三件套：口头禅≥2处 + 上课式追问≥1处 + 断言式收束 ③辨证结论必须用固定模板行：**辨证：{证型}（{病机}·{方名}证）** ④提到任何方剂必须附"经方条文卡片"……

对比知识库里的 [[角色提示]]（crewAI 的 role/goal/backstory 三件套）：那是给"员工"发岗位说明书，这里是给 AI 写一份几万字的"演员剧本"——连"哪个词不许说、句式怎么排"都规定了，还带"输出前八查"自检清单。这就是大号版角色提示。

3
230 万字塞不进上下文窗口，怎么办？

核心设计：分层按需加载（progressive disclosure）。只有 2.71% 的内容常驻上下文，其余躺在磁盘上按需取用。我们实测算了这笔账：

入口层 SKILL.md 62,481 字符 ≈ 3.8万~6.2万 token ← 常驻（触发时整体载入） 全库 44 个 md 文件 2,303,298 字符 ≈ 138万~230万 token ← 磁盘待命 入口层占全库比例：2.71% → 不分层根本装不下

这就像图书馆：入口层是"馆内地图+常备手册"（永远在手边），速查层是"工具书架"（常见问题直接翻），底层是"密集书库"（要查某个条文才去调卷）。类比知识库的 [[三层记忆]]：也是逐层压缩、按需展开。

4
AI 怎么"发现"这个 skill？激活词是怎么回事？

Claude Code 启动时扫描 ~/.claude/skills/ 下每个目录的 SKILL.md，只读 frontmatter 的 name + description（不读正文！）来判断"用户这句话跟哪个技能相关"。所以 description 就是这个技能的"广告位"：

--- name: nihaixia description: 倪海厦（1954-2012）台湾中医师，经方派代表人物……触发词：倪海厦、海厦视角、中医倪海厦、经方思维、倪海厦会怎么看、倪师。知识库覆盖：伤寒论129条全+金匮23篇+黄帝内经72篇+……---

触发词直接写进 description，340 字符里塞满了"何时用我"的线索——这就是 skill 的检索键。实验一验证了这一点（见实验部分）。

5
知识库内部怎么组织？

三层结构，各司其职：

层内容（实测）作用
SKILL.md（入口）表达规则 + 蒸馏速查块（开阖枢总图、补虚方铁律、十二经原穴表、诊断公式）人格 + 高频知识常驻
modules/ 14 个文件 43161 行伤寒论太阳篇逐条解读、金匮 23 篇、内经 72 篇、针灸本草、扶阳论坛……系统性原始知识，深查才加载
cases/ 7 个文件1257 例结构化医案总表 + 按癌/心血管/代谢/自免/神经分类医案检索
references/distilled 8 个速查（诊断公式/剂量表）、audit 2 个审计清单、research 10 个研究档案速答层 + 质量审计

注意 references/audit：方剂 112 条、针灸 164 条的审计清单——作者给自己的知识库做了"对账表"，这是数据质量的工程化自查，很多 RAG 项目都没做到。

6
"蒸馏速查层"是什么？为什么要把答案提前搬进入口？

SKILL.md 正文里直接嵌了"蒸馏精华速查"：六经开阖枢图、两大补虚方铁律、脉舌速查、8 个诊断公式……本质是把预测到的高频问题，把答案提前从 230 万字里捞出来放在手边，省一次"加载模块文件"的往返。

类比：CPU 缓存（知识库的" locality 原理"）——全库是内存，SKILL.md 是 L1 cache，distilled/ 是 L2 cache。热点数据离计算越近越快。做任何大知识库 Agent 都值得抄这一手：统计高频问题 → 前置到入口层。

7
怎么防止 AI 瞎编条文？溯源机制是什么？

两个机制：①SKILL.md 明文禁止"输出 modules/XX 路径行号"给用户看，但内部回答要求可回溯到模块；②知识库本身就是纯文本 Markdown，随时可以 grep 对账——我们在实验三实测：查"小柴胡汤"命中 12 个文件、86 次出现在伤寒论太阳篇模块，随便抽一行都能看到原文上下文。

再加 audit 清单（112 方剂 + 164 穴位逐条对账）和 CHANGELOG 里"3 独立评审盲测"的记录，这套"可 grep、可对账、可盲测"的三件套，就是纯文本知识库相对黑盒向量库的隐藏优势。

8
输出格式为什么写了 130 条规则？连"表格每行"都管？

看 CHANGELOG 很有意思：v2.1.0 强制表格化 → 用户反馈"像学术清单没温度" → 改成全口语 → 又反馈"重点难找" → v2.3.1 定稿"折中版"：口语正文是主体 + 每答必达 1 个表格或加粗要点，两头违规都判"重写"。还有"表格行全铁律"：症状必须一行一个、禁止挤行合并；"八查"自检清单；输出前对账不过即重写。

工程视角：这是把"输出验收标准"写成可机器核对的规则集，和知识库里的 [[质检Gate与自我纠错循环]] 是同一个思想——把主观的"写得好不好"翻译成客观的检查站清单。写自己 skill 时直接抄这个套路。

9
它和 RAG / 向量检索是一回事吗？
本项目（分层文本 skill）经典 RAG（见 [[RAG检索增强生成]]）
检索方式frontmatter 匹配 + 关键词 grep + 人工预蒸馏Embedding 向量 + 相似度搜索（Qdrant 等）
基础设施零：纯 Markdown 文件需向量库、Embedding 模型
可解释性强：命中行直接可读可对账弱：向量命中需人工看
适合规模百万字级 + 领域结构清晰千万字级 + 语义模糊查询
维护成本改文件即生效，git 可版本化改数据要重建索引

230 万字以内的专家知识库，"分层纯文本"是更轻、更可审计的方案；两者不冲突，大规模时向量检索做第一跳、文本层做对账。

怎么安装？怎么激活？
# Claude Code 手动安装（README 原方案） git clone https://github.com/jangviktor-web/nihaixia.git cp -r nihaixia/ ~/.claude/skills/nihaixia/ # 之后新开会话，说激活词即触发： "倪海厦会怎么看……" / "用海厦视角……" / "经方思维分析……"

另有 ClawHub / 腾讯 SkillHub / 腾讯 IMA 手机端等分发渠道。安装本质 = 把目录放进约定的 skills 文件夹，没有任何编译或注册步骤——skill 的"安装"就是这么朴素。

11
安全边界怎么设计？（技术视角）

README 与 SKILL.md 双层免责声明："仅供中医学习与研究，不替代专业医疗诊断"；SKILL.md 还规定安全话术只出现在文末固定免责框、不得混入口语正文。从工程看这是"约束注入"：把安全要求写成角色规则的一部分，而不是指望模型自觉。同款问题在知识库 [[提示注入]] 里讨论过——技能包内容本身也是"进入上下文的指令"，装第三方 skill 前应像本实验一样先通读审查。
