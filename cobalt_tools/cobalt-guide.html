01

cobalt 是什么，三个网站是一回事吗？

cobalt 是 imputnet/cobalt 的开源媒体保存 Web + API 项目；另外两个网站只是本次来源里的对照服务。公开页面没有给出它们属于同一代码库的证据，绝不能把三站统称为“cobalt 开源项目”。

对象本次核实到的事实没有核实到的事
cobalt官方 monorepo、API/部署文档、AGPL 为主的代码许可不把官网在线服务当作可任意调用的公共 API
tiktokio.bio公开首页自称免费 TikTok 下载器，声明独立于 TikTok/ByteDance未见 imputnet/cobalt 或源码链接
greenvideo.cc公开首页 HTTP 200，元信息称支持小红书、TikTok 等多个平台未验证其下载成功率、内部架构或与 cobalt 的关系
02

它解决什么问题，合法边界在哪里？

没有统一工具时，用户要理解每个平台不同的页面、媒体地址、音视频分离和封装格式。cobalt 把这些差异收进服务适配层，给前端一个统一的 JSON 契约。

它降低的是“保存自己有权保存的公开内容”的工程摩擦，不是解除内容访问限制。官方 README 明确说它只处理免费、公开可访问的内容，不缓存内容，使用者仍需对下载、使用和再分发负责。

实用判断：公开可看不等于可任意再发布。保存自己的作品、已获授权素材或许可允许的内容；保留作者与许可信息，不把工具能力当作版权授权。
03

一次粘贴链接，内部经过哪些层？

仓库是 monorepo（单仓多包）：web/ 是 SvelteKit 前端，api/ 是 Express API，packages/ 放共享包。API 主链路不是“正则一下然后返回地址”，而是一串职责明确的 Pass。

规范化
短链别名、清理多余 query、统一 URL 对象；随后检查严格 schema。
路由与决策
extract 找服务和路径参数，match 调对应适配器，matchAction 再决定重定向、隧道、选择器或本地处理。

与知识库的 [[构建流水线与Pass]]、[[统一数据网关]] 相似：统一出口不意味着内部只有一种上游逻辑。

04

POST / 的请求契约怎么读？

请求只强制要求 url，但 HTTP 头也必须是 JSON。schema 是 .strict()：拼错或自造字段不会静默忽略，而是返回 error.api.invalid_body。

POST / HTTP/1.1
Accept: application/json
Content-Type: application/json

{
  "url": "https://youtu.be/ABCDEFGHIJK",
  "videoQuality": "720",
  "downloadMode": "auto",
  "localProcessing": "disabled"
}
默认项实测值含义
audioBitrate / audioFormat128 / mp3默认音频码率与格式
downloadMode / videoQualityauto / 1080自动模式，画质上限偏好 1080
localProcessingdisabled默认由服务端处理需要处理的媒体
实测：youtu.be/ABCDEFGHIJK?t=43&list=... 被规范为 youtube.com/watch?v=ABCDEFGHIJK；未知字段 madeUpOption 被拒绝。
05

为什么响应不只是“一个下载地址”？

因为不同媒体的后续动作不同：单个现成文件可直接跳转；音视频分离要合并；图集要让用户挑；失败则要让程序读懂原因。status 是客户端的分流指令。

实测：自写 Vimeo 形态夹具在 alwaysProxy:false 时得到 redirect，改为 true 后得到 tunnel；两个媒体项的夹具得到 picker 且保留 2 项。
06

tunnel 为什么像临时取件柜？

tunnel（隧道）是由 cobalt 签发的临时媒体流入口。API 返回的不是裸上游地址，而是带 id / exp / sig / sec / iv 的 URL。默认 TUNNEL_LIFESPAN=90 秒；元数据放内存或 Redis，内容本身仍流经代理而非长期缓存。

“不缓存内容”不等于“完全不存状态”。它短期保存的是处理计划：上游 URL、服务、文件名、头部、音频参数等；过期后入口失效。

实测：官方 createStream 生成五个签名参数；verifyStream 正确还原 local-fixture，把 sig 改成 43 个 A 后返回 401。没有请求夹具 URL。
07

localProcessing 把什么搬去了浏览器？

媒体处理常见动作有 merge（音视频合并）、remux（不重编码地换封装）、transcode（重新编码）。默认服务端用 FFmpeg；浏览器模式由前端依赖的 libav.js 工具承担合成，API 提供输入隧道与输出说明。

取值客户端意图本次可验证效果
disabled不要求本地处理merge 夹具返回 tunnel
preferred适合本地处理时优先本地merge 返回 local-processing、2 条隧道、video/mp4
forced强制本地处理并代理输入受实例 FORCE_LOCAL_PROCESSING 策略与动作类型共同约束

这不是“下载到浏览器”同义词：两种模式最终都可下载；差别是合成/转码计算发生在哪里。

08

本地跑起来后，怎样避免变成公开滥用入口？

开发模式只需 Node、Git、pnpm 和必需的 API_URL；官方更推荐 Docker Compose 部署。API 默认端口 9000，本次实验改用 19100 且只监听 127.0.0.1。

官方 API 使用纪律：托管实例有反滥用保护，不打算允许第三方项目随意调用。需要 API 时自托管，或获得实例所有者明确许可。认证支持 Api-Key 与短期 Bearer JWT；API_AUTH_REQUIRED=1 可强制认证。

部署还要理解 DISABLED_SERVICES、CORS、速率窗口、隧道 TTL。多实例模式需要 Redis 共享隧道缓存；这与知识库的 [[负载均衡与反向代理]]、[[缓存]] 直接关联。

09

失败时，错误码比“重试一下”多说什么？

POST 错误统一为 {status:"error", error:{code, context?}}。先定位是 HTTP 契约、URL、服务策略、上游内容还是限流，再决定是否重试。

本机实测输入HTTP实际 code
POST 空 JSON400error.api.link.missing
Accept: text/plain400error.api.header.accept
不支持的 example.com URL400error.api.link.invalid

GET /tunnel 的错误则通过 HTTP 状态码表达；文档列出 200/401/403/404/429/500。精确文件大小未知时只有 Estimated-Content-Length，不能拿它做严格字节校验。

10

这个项目给我哪些真实能力与用途？

最有价值的不是“又多一个下载站”，而是一套可自托管、可编程、可审计的公开媒体获取架构。

用途 1：个人素材归档
只保存自己的或获授权的公开素材，以 API 选项统一文件名、音轨和元数据。
用途 2：内部工具后端
在获授权的自有实例上，让脚本或 Web 应用处理五种响应，而不是硬编码“一定返回 URL”。
用途 3：媒体流水线实验台
用本地夹具测试 redirect/tunnel/local-processing 分支，再接真实、合法、公开的测试资源。
用途 4：架构复用
把“规范化 → 适配器 → 动作决策 → 临时签名资源”的模式迁移到其他公开文件转换服务。
不承诺：所有平台永远可用、所有公开页面都能保存、第三方网站与 cobalt 同等可靠，或工具能处理 DRM/付费墙/私有访问控制。

主实验：不抓媒体，也能跑通真实 cobalt

目标：启动官方 API，并直接执行官方请求规范化、动作决策和签名隧道代码。所有媒体字段都使用保留域名 .example，没有网络抓取；测试的是架构契约，不宣称任何平台下载成功。
