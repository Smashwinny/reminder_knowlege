Q135 种"Agent 架构"到底在解决什么共同问题？

一句话：大模型一次生成不可靠，就用"结构"把多次生成组织起来。

裸调 LLM 只有一问一答，而真实任务需要：多步推理（算 3 步账）、调用工具（查计算器）、自己检查（发现算错了重算）、查资料（RAG）、记住上下文（记忆）、分工协作（多智能体）。35 种架构就是 35 种组织 LLM 多次调用的"流程图"——这正是本库用 LangGraph 状态机实现它们的原因：每种架构 = 一张节点+边的图，节点调 LLM 或工具，边决定下一步去哪。

知识库关联：本概念是 Agent 循环 笔记的"全集"——那条笔记讲最小两节点环线，本库是把文献中所有变体标准化后的"货架"。

Q3这个库的工程骨架：统一 Architecture 合同

35 个类全部继承同一个抽象基类，只强制实现两个方法，换来三个白得的好处：

class Architecture(ABC):
    @abstractmethod
    def build(self) -> CompiledStateGraph: ...   # 编译出 LangGraph 状态图
    @abstractmethod
    def run(self, task) -> ArchitectureResult: ... # 跑任务，返回标准化结果
    # 可选：diagram() 自动生成 mermaid 图；explain() 输出原理论述

统一合同带来三个免费好处

① Notebook 统一：35 份教程全部同一套调用姿势 arch.build() / arch.run() / arch.diagram()；
② 可组合：元控制器、集成器能把任何架构当黑盒函数调用（"哪个架构都适合被路由"）；
③ 文档自动生成：每篇文档页的图和理论段都出自代码本身，不会和实现脱节。

知识库关联：这就是 规格书先行 SpecDriven 的正面案例——先钉死接口合同，35 个实现互不干扰还能互相组合。

Q4什么是"确定性选择器模式"？（本库最独特的工程纪律）

很多架构需要 LLM 当"裁判"（这份草稿打几分？这篇检索文档相关吗？）。直接让 LLM 输出"0-10 分"会发现一个病态现象：LLM 打分挤成一团，几乎什么都是 7-8 分（flat-band），阈值形同虚设。

本库的解法：不让 LLM 直接做最终决定，而是让它只回答"分类特征"（布尔/枚举），由 Python 用确定性逻辑组合出决定信号——这就是确定性选择器模式（deterministic-picker），35 个架构中 13 个使用它，另 9 个靠设计天然免疫。

具体例子（Constitutional AI 架构）：LLM 对宪法每条规则只判 pass/fail，Python 做 all(rules)，全过才算合格；CRAG 对每篇文档判 relevant / ambiguous / irrelevant 三档，Python 按多数档路由。LLM 出"模糊的判断材料"，Python 下"干脆的决定"——与知识库 事实与判断分离（LLM 只研判不口算）一脉相承。

Q5Reflection：生成-评审-改写循环怎么转？

generate 初稿→ critique 评委打分+评语→ 达标？→ refine 带着评语改写↺

评委是一个结构化的 LLMJudge：按 Pydantic schema 打 1-10 分并给文字评语；循环出口有两条：score ≥ 目标分 或 达到最大迭代数。注意打分器内部就是 Q4 的确定性选择器——分数由分项布尔/枚举合成，避免"永远 8 分"。

本机实测（Qwen2.5-3B，"给 10 岁小孩解释天为什么是蓝的"）：首稿即获 8/10，循环 4.7 秒收敛——评语指出"提到了散射但可更简洁"。

Q6Reflection vs Reflexion：一字之差差在哪？

Reflection（反思）Reflexion（反身记忆）
循环单位单任务内：改这一份草稿跨尝试：这次失败的经验写成文字存进记忆
灵感来源人类写稿"改二稿"强化学习：失败不丢梯度，丢语言化的教训
记忆无（历史只在当次 run 里）情景记忆向量库，下个任务还能检索到
出口分数达标任务被判成功 / 重试次数耗尽

一句话：Reflection 改"稿"，Reflexion 改"人"（把教训留给未来的自己）。知识库关联：本能学习与置信度评分（失败教训沉淀）与 Reflexion 同思路。

Q7ReAct 为什么把 Thought 和 Action 拆成两个节点？

经典 ReAct（ICLR 2023）是"想一步、动一步"交替：Thought（推理）→ Action（调工具）→ Observation（结果）→ Thought……但现代工具调用 API 里，Thought 和 Action 挤在同一条消息里，小模型常常跳过思考直接调工具，退化成裸 Tool Use。

本库的实现把这个隐患从结构上焊死：think 节点不给工具，逼模型先输出 Thought；act 节点才给工具做选择。代价是每轮 2 次 LLM 调用，换来"思考不可跳过"。

本机实测（农夫卖牛奶周收入题）：模型调用 calculator 分步算 15×4=60 升、1.2×60=72 元、72×7=504 元，最终答案 504 正确；但也暴露了 3B 小模型的通病——它反复"确认"已达成的结论不主动收尾，直到 max_rounds=5 强制结束。护栏参数 max_rounds 就是防止循环不刹车的安全带。

Q8Self-Consistency：多采样几次投票，为什么能提升正确率？

原理像"民主表决"：同一道题，让模型在高温（temperature 0.8，敢犯错也敢出新解）下独立解 5 次，提取每条的最终答案，Python 多数表决（确定性选择器）。单个采样有随机错误，但错误随机、正确收敛——正确答案像磁铁，错误答案四散，多数表决把磁铁吸出来。论文（Wang et al. 2022）里数学任务提升可达两位数百分点。

本机实测有一个重要发现：3B 小模型做应用题时 5 条采样会集体偷懒（全部输出同一个占位答案 "x"），温度 0.8 也拉不开多样性——架构再好也救不了模型能力不足；换单步乘法题后表现见"动手实验"部分。

Q9规划族（Planning / PEV）和 ReAct 边想边做有何不同？

ReActPlanning（Plan-and-Execute）PEV（Plan-Execute-Verify）
计划时机没有总计划，想一步做一步动手前先出完整步骤清单同 Planning
步骤质检无无（信任每步结果）每步加 Verify，失败带评语重试
适合场景路径不可预知（探索式）任务可分解、工具可靠工具会失败的真实环境

类比：ReAct 是边走边问路，Planning 是出发前先导航，PEV 是每个路口核对路牌，错了就地重走。知识库关联：PEV 的"逐步验证"就是 质检 Gate 与自我纠错循环 的 Agent 版。

Q10RAG 五变体各治什么病？

架构治的病药方
Agentic RAG普通 RAG 不管要不要都先检索检索变成工具，Agent（ReAct 小循环）自己决定何时查、查什么、查几次
CRAG检索回来一堆无关文档照样用每篇文档打分（相关/模糊/无关，枚举票），多数无关就降级走网络搜索兜底
Self-RAG检索时机和文档质量全靠运气模型自发 reflection token：needs_retrieval? 每条文档 relevance/support 由 Python 合成取舍
Adaptive RAG简单问题也走全套流程，浪费且慢先给问题分类定级（免检索/单跳/多跳），按级路由到不同流程
GraphRAG"整部《红楼梦》讲了什么"这类全局问题，向量检索抓瞎抽实体关系建知识图谱，按社区聚类+每社区预生成摘要，全局问题读摘要

知识库关联：基础 RAG 见 RAG 检索增强生成；五个变体全用它做底座，本库把这条演进线一次补齐。

Q11记忆族（MemGPT / Voyager）和"三层记忆"是什么关系？

知识库已有 三层记忆（L1 轨迹→L2 摘要→L3 画像）。本库记忆族的贡献是管理策略：

MemGPT把 LLM 上下文比作操作系统内存——Context 是"内存"（有限、FIFO 挤出），Archival 是"硬盘"（向量库无限），Agent 自己决定何时把记忆在内存/硬盘间倒腾（函数调用式记忆管理）；Voyager（Minecraft 成名）更进一步：每次完成任务沉淀一个"技能"（带文档的代码片段）进技能库，新任务先检索技能库复用，不会就现写——终身学习。

类比：三层记忆规定了书放哪几层，MemGPT 给了图书管理员（自己搬书），Voyager 给了秘籍收藏夹（越做越强）。

Q12多智能体族：黑板 / 辩论 / STORM / 元控制器怎么协作？

架构协作模式类比
Blackboard（1980s HEARSAY-II 老前辈）无中央指挥：所有 Agent 每轮看共享黑板，自评"我能贡献多少"竞价，最自信者上手写，直到无人再出价头脑风暴会议室
DebateK 轮 × N 个 Agent：每轮各抒己见+点评别人，末轮多数表决辩论赛+观众投票
STORM固定流水线：头脑风暴 N 个视角 → 每视角出题 → 分别作答 → 汇总成文章大纲编辑部联合采编
Meta-Controller一个 LLM 路由器看任务选架构：写作走 Reflection、多跳调研走 ReAct、可分解任务走 Planning……分诊台护士

知识库关联：与 多智能体协作（crewAI 角色分工）互链——那边是"人事任命"，这边是"协作机制"。

Q13Benchmark 怎么给架构打分？78% 意味着什么？

benchmarks/run_benchmark.py 用 17 道固定任务（写作、数学、检索、代码、多跳问答……）跑所有相关架构，每次运行由 LLM 按 rubric 判对错（确定性选择器式评分），输出排行榜。README 最近成绩：Llama-3.3-70B 跑 33/42 判分点 = 78%。这个数字的启示不在高低，而在可横向比较：同一任务、同一模型、不同架构，谁行谁不行一目了然。它也诚实地标注 "0 mocked runs"——所有示例都是真 LLM 输出，不是摆拍。

Q14没有 API key 能在自己电脑上跑吗？

能。本实验全路线：Ollama 本地模型 + 本库 ollama provider。配置就三行（写进 repo/.env）：

LLM_PROVIDER=ollama
LLM_MODEL=qwen25-3b        # 自己用 GGUF 灌进 ollama 的模型名
OLLAMA_BASE_URL=http://localhost:11434

有两个本机实测的坑（详见"动手实验"）：① ollama 官方拉模型时若挂着 Clash 类 fake-ip 代理会报 "redirect target not allowed"，可改从 hf-mirror.com 用 curl 下 GGUF 再 ollama create；② 安装别忘了 networkx（architectures/__init__.py 全量导入 35 个架构，缺一个依赖全体报错）。

动手实验：一题三架构，本机实测（Qwen2.5-3B）

实验材料在 exercise\ 目录：arch_compare.py（三架构对比）+ arch_voting_mul.py（表决补充实验）。全程不花一分钱 API 费，模型跑在本地 Ollama。

第 1 步 · 备模型（绕开 ollama 拉取被代理拦截的坑）

操作：

curl -L -o qwen25-3b-q4_k_m.gguf "https://hf-mirror.com/bartowski/Qwen2.5-3B-Instruct-GGUF/resolve/main/Qwen2.5-3B-Instruct-Q4_K_M.gguf"
printf 'FROM ./qwen25-3b-q4_k_m.gguf\nPARAMETER temperature 0\n' > Modelfile
ollama create qwen25-3b -f Modelfile
ollama run qwen25-3b "Reply with exactly: OK"

目的：ollama 官方源会把下载重定向到被 Clash fake-ip 污染 CDN（报 redirect target not allowed），改从 hf-mirror 拿 GGUF 再灌入。

验证成功标准：

✅ 预期结果：ollama list 出现 qwen25-3b:latest（1.9 GB）；冒烟提问回复 "OK"。
第 2 步 · 装库（注意 networkx 坑）

操作：

cd repo
python -m venv .venv
.venv\Scripts\pip install -e ".[ollama,faiss]" networkx json-repair
# repo\.env 三行：LLM_PROVIDER=ollama / LLM_MODEL=qwen25-3b / OLLAMA_BASE_URL=http://localhost:11434
.venv\Scripts\python -c "from agentic_architectures.architectures import Reflection, ReAct, SelfConsistency; print('imports ok')"

目的：装 ollama 集成 + FAISS 向量后端；networkx 必须单独补（35 架构全量导入，缺它全体 ImportError）。

✅ 预期结果：打印 imports ok。
第 3 步 · 跑三架构对比

操作：

cd exercise
PYTHONUTF8=1 ..\repo\.venv\Scripts\python arch_compare.py

目的：Reflection 写科普、ReAct 算农夫卖奶账（自带 calculator 工具）、Self-Consistency 解应用题并和单次直答对比。
