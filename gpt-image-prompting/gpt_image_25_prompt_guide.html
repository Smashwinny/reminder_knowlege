Q1
GPT Image 2.5 是什么？Flare 和 Sunburst 什么关系？模型选型

GPT Image 2.5 是 OpenAI 2026 年发布的图像生成/编辑模型家族，一次出了两个版本：Flare 是"小快灵"速度版，Sunburst 是"质量版"（base 模型）。两者都支持生成、编辑、透明背景，都提升了精确编辑和主体保持能力。

术语卡：Flare＝速度优化的小模型（质量约等于上一代 GPT Image 2）；Sunburst＝质量优化的基础模型（质量超过 GPT Image 2）。名字只是型号指纹，选型口诀：新工作流先用 Flare 起步求快，质量不达标再上 Sunburst；迁移老工作流则按"现任模型够不够用"反着选。
官方选型法：Sunburst 过了质量关，再用相同提示词测 Flare，速度确有收益才切换
Q2
官方指南教什么？和社区"六块协议"什么关系？方法论定位

这份指南不是提示词合集，而是一份系统性方法论：8 条提示词基本原则 + 约 20 个图文示例（生成+编辑）+ 模型选型/参数/迁移纪律，配套官方 Cookbook 可运行 notebook。

它和我们知识库里的 [[PromptAsCode提示词即代码]]（awesome-gpt-image-2 逆向出的六块协议）是同源思想的官方版与社区版：官方用 8 条"原则"讲框架，社区用 6 块"代码块"讲框架，都指向同一结论——好提示词是结构化工程产物，不是文采。

Q3
为什么"先说最终用途"排第一条？核心思想

因为"用途"决定了画面所有隐含标准。同一只马克杯：产品照要求影棚布光无杂物；广告图要求留出标语位置；信息图要求标注清晰。不说用途，模型只能按"平均审美"猜——这就是抽卡感的根源。

官方原话：说明拍摄对象和预期用途，具体说明构图、宽高比和重要的位置限制
Q4
一条完整提示词的官方顺序是什么？八要素流水线

推文总结的顺序（用途→主体→构图→风格→光线→材质→文字→负面提示词）与官方 8 条互为表里。先说清楚你最终想要什么，再描述画面细节——顺序本身就是"目标先行、细节殿后、约束兜底"。

Q5
提示词写成段落、标签还是 JSON？格式选择

官方明确：简短提示、描述性段落、类 JSON 结构、说明和标签都可以表达相同意图——没有必须遵守的特殊语法。选格式的唯一标准是便于阅读和更新（可维护性），复杂的拍摄需求用带标签的章节组织。这与 [[PromptAsCode]] "槽位化利于批量改参"完全一致。

Q6
图里要出现的文字怎么才不翻车？精确文字

文字渲染是图像模型最大翻车点，官方给了三件套：①引号逐字锁定内容（生僻词/品牌名逐字母拼）②写明位置和字体风格 ③额外要求"不要任何多余文字、Logo、水印"。生成后检查拼写与清晰度；小字/密集文字/多字体场景，用 medium 和 high 质量各出一版对比。

术语卡：负向提示词（negative prompt）＝明确写"不要出现什么"。图像模型不会自动"少画"，你不排除水印，它就可能长水印出来。
Q7
编辑图片时为什么要写"哪些不能动"？修改与约束分开

这是全指南最实用的一条（也是推文重点）。口语编辑"把椅子改一下"只交代了改什么，模型并不知道什么是禁区，于是顺手把光线、背景、人脸全动了。官方第 6 条：说"仅更改 X"，并列出要保留的细节——身份、几何形状、布局、光照、标签；再声明排除项（多余文字/徽标/水印）；精修局部还要点名饱和度、对比度、镜头角度不能变。

实验 ex3 实测：口语编辑 0 分；"其他所有元素不变"式泛泛保留 50 分；逐项点名 75~100 分
Q8
为什么复杂修改一轮只改一个变量？迭代纪律

官方第 8 条：把上一张输出作为下一次编辑的输入，一次只请求一处更改。因为每轮编辑都是"重新画一遍"，多变量同时改，跑偏来源无法定位；单变量迭代让每次漂移都可归因，结果跑偏就重申关键约束。若某区域必须像素级不动，官方建议直接把已批准的局部合成回原图，别指望提示词。

示意图（趋势非实测数据）：多轮修改是官方明确警告的漂移来源
Q9
API 参数和提示词怎么分工？参数纪律

官方原则：API 参数管"生产规格"，提示词管"画面内容"，两套系统分开设置。参数不用写进提示词（写了也未必生效），提示词也不用描述分辨率。

参数取值说明
modelgpt-image-2.5-flare / gpt-image-2.5-sunburst速度版 / 质量版
qualityauto(默认) low medium high xhigh max先选好模型再调质量；高挡位不保证每条提示词都更好
sizeauto 或自定义分辨率常用 1024x1024、1536x1024、1024x1536、3840x2160…
backgroundauto / opaque / transparent要透明必须参数+提示词双声明，PNG/WebP，并检查 alpha 通道（发丝/玻璃/阴影边缘）

调参顺序：选模型 → 调 quality → 才考虑重写提示词；一次只调一个设置，并统计"每张被采纳图片的真实成本"（含失败与重试）。

Q10
自定义分辨率的硬约束怎么算？可计算参数

自定义 WIDTHxHEIGHT 四条硬约束：每边 ≤ 3840px；两边都是 16 的倍数；长短边比 ≤ 3:1；总像素在 655,360 ~ 8,294,400 之间。超过 2560x1440（3,686,400 px）属于实验区。这套约束是纯算术，可以翻译成代码提前校验——实验 ex2 就干了这件事。

Q11
从旧模型换到 2.5，官方流程是什么？迁移六步

官方给了 6 步迁移法，核心思想是"先保质量、再赚速度、按工作流灰度"：

步骤做什么关键点
1 存基线收集代表性生产提示词与参考图（难编辑/精确文字/人脸/产品几何/透明件）记录当前模型、参数、结果
2 选首个候选现任够用→先测 Flare；现任不达标→从 Sunburst 起步首轮对比冻结提示词/参考图/尺寸/格式
3 查完整结果指令遵循/身份与产品保持/文字准确/意外改动/透明度整套编辑序列+单步都要测
4 质量过了测速度同门槛测 Flare，质量守住且延迟改善才切换一个工作流的提速≠另一个也提速
5 一次调一个参数先比 quality 再考虑改提示词统计每张采纳图成本，别假设快模型更便宜
6 按工作流灰度小流量试点→监控同样指标→逐步放量保留旧模型以便回滚
Q12
没有 API key 能练什么？学习策略

本指南的精华大部分在文本层而非像素层：8 条原则、提示词结构、编辑约束、参数约束、迁移流程，全都可以用确定性代码做成"体检器"提前练熟（见下方实验）。等有 API key，只差"把体检器接在真实出图前后"一步——届时 images.generate / images.edit 的输入早已被质检过。这延续了 [[awesome_gpt_image_2]] 项目"图像 API 不可用先练文本层"的思路。

Q13
这套方法能用到即梦 / MJ / GLM 吗？跨模型迁移

推文观点：模型越强，越不需要大段专业术语堆砌，但"提示词的框架/范式"不会变。用途先行、结构化、文字逐字锁、编辑写禁区、单变量迭代——这五条是方法论，不绑定任何模型 API。参数体系（quality/size 约束）是 OpenAI 专属，换家时查对应文档即可。与 [[转绘]]（照片管画什么、提示词管怎么画）互为补充。

🎁 这份指南给我什么能力

  1. 把抽卡变下工程单：按"用途→主体→构图→风格→光线→材质→文字→负面"八节车厢写提示词，产出可复现；
  2. 精确文字三件套：引号逐字 + 位置字体 + 负向排除，做海报/招牌/信息图不再怕错字；
  3. 言出法随的编辑术：改动区+保护区+排除区三段式，改椅子不动背景（A/B/C 模板可直接抄）；
  4. 多轮迭代不跑偏：一次一个变量 + 重申约束 + 像素级需求走合成；
  5. 参数纪律：模型/质量/尺寸/背景四参数与提示词分工，分辨率约束可代码预校验；
  6. 提示词质检器：可把八要素规则接进任何生成流水线当 Gate（[[质检Gate与自我纠错循环]]）。

🧪 主实验 ex1：八要素提示词体检器（真实运行）

把官方 8 条原则翻译成确定性正则规则，每条规则只在适用场景计分（不适用记 N/A），给提示词打 0~100 分。文件：exercise\ex1_eight_elements.py

步骤1 写规则表：8 条原则 → 8 个可机检函数（用途关键词、结构标签、光线×材质双条件、引号文字三件套、编辑"只改+保留"、多图角色、单变量迭代）
步骤2 python ex1_eight_elements.py——目的：验证"官方风格提示词得分应显著高于抽卡式"。实现了：6 条样例自动体检。抽卡式「画一个好看的咖啡店」40 分；编辑无约束「把椅子改一下」50 分；官方风格生成/编辑/迭代样例 100 分；缺光线材质版 60 分——得分与质量单调一致
步骤3 发现：规则必须按场景计分（R6 只在 edit/iterate 场景算分），否则单句迭代提示词被"用途/材质"误伤反而低于坏例——第一版就踩了这个坑，改为 N/A 不进分母后单调。
【坏提示词A（抽卡式·生成）】 ctx=generate  得分: 40/100
【坏提示词B（编辑无约束）】 ctx=edit       得分: 50/100
【官方风格·生成（烘焙店招牌）】 ctx=generate 得分: 100/100
【官方风格·生成（缺光线材质版）】          得分: 60/100
【官方风格·编辑（推文家具例）】 ctx=edit    得分: 100/100
【官方风格·迭代轮】 ctx=iterate            得分: 100/100

🧪 实验 ex2：自定义分辨率参数校验器（真实运行）

官方四条分辨率硬约束逐条翻译成 validate(w,h)：边≤3840、16 倍数、比例≤3:1、总像素 655,360~8,294,400。文件：exercise\ex2_resolution_validator.py

步骤 python ex2_resolution_validator.py——目的：验证文档示例尺寸全过、构造的非法尺寸全被拦。文档 7 个示例尺寸全部 PASS；1000x1000/4000x1000/5000x5000/640x640 全部 FAIL 且给出具体违反条目；3840x1280 恰好 3:1 临界合法——参数纪律是可计算的
[PASS] 3840x2160 4K横 = 8,294,400 px（恰触上限，实验区）
[FAIL] 4000x1000: 边超限; 非16倍数; 比例超限4:1
[FAIL] 640x640 : 总像素越界(409,600) 须在 655,360~8,294,400
[PASS] 3840x1280 比例3:1临界: 合法（实验区）

🧪 实验 ex3：编辑提示词约束检查器（真实运行）

官方第 6/8 条落地：A 修改段（只改什么）35 分 + B 保留段（逐项点名≥3 项）40 分 + C 排除段 15 分 + D 单变量声明 10 分。文件：exercise\ex3_edit_constraint.py

步骤 python ex3_edit_constraint.py——目的：量化"泛泛保留 vs 逐项点名"的差距。口语编辑 0 分；官方翻译信息图例 50 分（保留段只写"其他所有元素"被扣分）；推文家具例 75 分（A+B 满格）——"什么不能动"比"改什么"更容易被漏写
【推文原例（官方风格）】        得分 75/100  A✓ B✓(5项) C✗ D✗
【坏例：只说改什么】            得分  0/100  全缺
【好例：翻译信息图（官方编辑例）】 得分 50/100  A✓ B✗(仅1项) C✓ D✗
