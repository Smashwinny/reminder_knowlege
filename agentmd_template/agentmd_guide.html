一份 贴在仓库/配置里、AI 每次开工都先读一遍的"行为契约"。本指南用 12 个疑问拆解它，并用真机实验证明：模板里的规则不是玄学，贴上去模型行为真的 measurable 地变了。

📌 疑问清单（本篇目录）

Q1

AGENT.md 到底是个啥？谁在什么时候读它？

它就是一个纯 Markdown 文本文件，里面写着"你干活时要遵守哪些规矩"。Agent 软件每次接到任务时，会自动把它塞进系统提示（system prompt）里——相当于员工每天上班先看一眼贴在墙上的《员工守则》再开始干活。

关键认知：模型本身没有"记性"，每次会话都是新员工——所以规矩必须每次都重新发一遍，AGENT.md 就是那个被反复发的固定文本。

Q2

为什么写成文件，而不直接把规则写死在代码里？

三个理由：① 用户可改——不用改软件源码就能定制自己的 agent；② 可版本管理——git diff 一眼看清这条规矩哪天改的；③ 可移植——换 agent 软件（Astra / Claude Code / Codex）文件跟着走。这和知识库里的 [[DESIGN.md 规范文档]] 是同一招：LLM 的母语是 Markdown，纯文本规则零解析成本、人机共读。

Q3

模板为什么是这 6 个板块？各管什么？

板块管什么一句话人话版
沟通输出风格说中文、先结论、少列表、不废话
指令优先级听谁的安全 > 当前指令 > 项目规则 > 全局规则 > 记忆
执行方式干活姿态开工别磨叽、先干完再问、别迎合、别瞎警告
测试与验证验证力度改动越大测越多，改个错别字别跑全套 CI
工具与并行干活手法用 rg 搜、批量读、子代理只在真独立时才派
规则来源唯一事实源规矩只放一份 AGENTS.md，别的文件只引用不复制

这 6 块正好覆盖一个 AI 员工的完整生命周期：怎么说话 → 听谁指挥 → 怎么干活 → 怎么自证 → 用什么工具 → 规矩本身放哪。缺哪块，哪块就退回模型默认行为（往往是唠叨、过度谨慎、过度测试）。

Q4

"指令优先级"为什么排第二？听谁的到底有多重要？

Agent 工作时上下文里飘着好几种指令：系统提示、你的全局偏好、项目里的 AGENTS.md、历史记忆、Skill 文档……不排优先级，冲突时模型就只能"猜"，猜错一次就是一次事故。模板给出的序：

这就是操作系统的中断优先级思想搬进提示词工程：越靠近"当下、具体"的指令优先级越高，越"陈旧、泛化"的越靠后。与知识库 [[提示词权威边界]] 互补——那边管"一段提示词内部谁有权改哪部分"，这边管"多层指令之间谁听谁"。

Q5

"先干完再问""别迎合""别瞎警告"在治什么病？

这三条全是真实使用中的高频痛点：① 磨叽病——干两步就停下来问"可以继续吗"，人得全程陪聊；模板规定"已授权的先完整做完，再统一提问"。② 迎合病——用户说方案 A 其实不对，模型顺着夸；模板规定"不适合就直接说，不为迎合改口"。③ 警告泛滥病——随手写个玩具脚本，它给你上一堂 SQL 注入安全课；模板规定"不为假想风险加未经请求的警告"。（这条我们实验里实测到了，见下方场景 3）

Q6

测试还要"按改动大小分级"？全测不是更安全吗？

全测当然"安全"，但 agent 是高频干活机器：每改一行注释都跑 10 分钟 CI，时间全烧在仪式上。模板的分级：琐碎可逆改动（注释/文案/格式）不强制测试；测试力度与影响面成正比；收尾清理临时文件。这与知识库 [[质检Gate与自我纠错循环]] 不冲突——Gate 是"该检的地方必须检"，分级是"不该检的地方别烧钱"，一个是质量下限，一个是成本上限。

Q7

"工具与并行"板块：rg、批量读、子代理克制是在省什么？

① 搜索用 rg：比递归 grep 快一个量级，agent 一天搜几百次，累计省的是真实的挂钟时间。② 无依赖的读取批量并行发起：串行 5 次网络往返 vs 并行 1 次。③ 子代理只用于真正独立的工作流——乱开子代理 = 每个都要重新加载上下文，又贵又慢，最后还得主代理重新核实。共享状态、连续决策的事，主代理亲自干。（呼应知识库 [[GitWorktree并行隔离]]：并行的前提是物理隔离，不隔离就别并行。）

Q8

"规则来源"：为什么 CLAUDE.md 只当"兼容入口"？

不同 AI 工具读的配置文件名不一样（CLAUDE.md / AGENTS.md / .cursorrules…）。如果每个文件各写一份规矩，改一条规则要改 5 处，很快就会互相矛盾。模板的解法是教科书级的单一事实源（SSOT）：真规矩只写在一份 canonical AGENTS.md 里，其他文件只写一行"请见 AGENTS.md"。和知识库 [[源码即Prompt]] 的"发布期渲染"是同一思想的两个流派：一个多文件复制渲染，一个单源引用指向。

Q11

⚠️ 双刃剑：压掉警告是福是祸？

实验里真实看到的另一面：B 组连 SQL 注入警告都不发了。对你自己的玩具库这是"清爽"，对真实生产库这是"灾难"。安全红线应该放在系统层/平台层（模板第一条也是这么写的："遵守系统、平台和安全约束"），而不能指望"少警告"的用户指令兜底。自己抄模板时，务必保留指令优先级板块，把安全约束钉在最顶层。
Q12

我想自己写一份，从哪几条开始？换 agent 要改什么？

起步三件套（性价比最高）：① 语言与结论先行（沟通 2 条）→ ② 指令优先级全节 → ③ "不为假想风险加未经请求警告"。写规则的红线：每条规则必须对应一个你真实被烦到过的失败模式，写"保持专业、高质量回答"这种装饰性规则等于没写（模型本来就想做到，做到了你看不出，做不到它也不当真）。换 agent 要改的：工具与并行板块是 harness 专属（rg / Chrome / lark-cli 换成你那家的等价物）；规则来源板块换成你那家的配置文件名。
