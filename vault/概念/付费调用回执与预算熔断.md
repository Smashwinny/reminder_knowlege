# 付费调用回执与预算熔断

**一句话定义**：将每次付费请求的状态和结果持久保存，重试优先复用结果，并通过分钟/小时/日预算限制异常耗费。

**属于领域**：AI 应用 / 成本控制 / 可靠性。

**通俗理解**：买过的票留收据，任务断线后先查收据，不盲目再买；达到预算就停止继续购买。请求发出但结果未知时，还需要核对状态，不能保证零重复付费。

**源码来源**：AIHOT `packages/backend/src/providers/receipts.ts` 与架构文档。模型仅由后台任务调用，打开公开页面不触发付费请求。

**验证边界**：本次阅读设计，没有调用服务商、连接数据库或验证真实账单；不把架构说明写成“预算系统已在我的站点上线”。

**与已有概念的关联**：
- [[消息队列与异步削峰]]：队列负责何时做，回执负责重试时是否需要再付费。
- [[构建流水线与Pass]]：收费阶段与读取阶段分离。
- [[证据优先质检ProofOverClaims]]：账单、回执和状态都是需要核查的证据。

## Metrik：额度展示不构成预算硬停（2026-10-05）

[[项目笔记/metrik]] 的 [[多窗口额度的展示选择规则]] 决定仪表盘显示哪个读数；15% 告急线是展示选择阈值，不是本文的付款回执、重试去重或预算熔断机制。看到剩余 0、余额金额或估算成本，不代表应用已经阻止推理请求，也不保证不会超支或重复收费。

[[用量、额度与估算费用的计量分层]] 将官方额度、货币余额、Token 用量、参考费用和实际账单分开。原学习只执行离线 JS 组件测试；没有调用付费接口、读真实账单或验证预算硬停。已有回执与熔断概念沿用原定义，不新建“额度告警即熔断”的同义条目。
