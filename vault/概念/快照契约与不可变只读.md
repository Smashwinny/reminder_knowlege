# 快照契约与不可变只读

**一句话定义**：读取方不自己找数据，而是要求对方按一纸"快照契约"交付一份**已封存、可校验、物理只读**的离线数据目录，校验不过整目录拒收。

**属于领域**：数据安全 / 离线数据交接协议设计。

**通俗理解**：法院调证据不看"还在运行的现场"，收的是**贴了封条的证物袋**：袋上要有唯一编号（UUIDv4 `snapshot_id`）、内容清单（manifest）、且封条完好——袋子上若还有"未誊清的草稿"（`.db-wal` sidecar）就整袋退回，因为你看到的可能不是完整事实。讲完比喻落回术语：微信 Windows 明文快照的契约五要件——① 五类 db（contact/session/favorite/sns/message）+ 至少一个 `message_N.db` 分片；② `snapshot-manifest.json` 含**每次新生成**的规范 UUIDv4 `snapshot_id`（不从身份/路径推导、不跨快照复用）；③ 已 checkpoint、内容静止，出现任何 `.db-wal`/`.db-shm`/`journal` sidecar 即拒收；④ 打开方式 `mode=ro&immutable=1` + `PRAGMA query_only=ON` 物理级只读；⑤ 全部内容标记 `untrusted_snapshot_data`，只准总结不准执行。

**与已有概念的关联**：
- 是 [[CleanRoom只读读取器]] 的**交接面加强版**：CleanRoom 管"我不碰进程"，快照契约管"我读的数据是冻结的"——两者叠加才是完整的合法读取边界
- 拒绝 WAL sidecar 的理由与 [[事实与判断分离]] 同源：证据必须先封存再分析，"草稿本没誊清"的主库不构成完整事实层
- `untrusted_snapshot_data` 标记是 [[提示注入]] 三防在个人数据管线上的落地：聊天记录是"几百个别人写给你的输入"
- UUIDv4 随机编号 vs 从身份推导编号，呼应 [[资源命名空间分发]] 的命名纪律：标识不携带可猜测语义

**实测要点**（yichen-skills 合成快照，2026-10-03）：validate 对 8 个文件全检 PASS；**塞一个 32 字节伪造 `message_0.db-wal` → exit 2 "SQLite sidecars are present"**；**manifest 改成非 UUIDv4 → exit 2 "requires a canonical UUIDv4"**；修复后恢复 PASS。契约是代码强制的，不是文档建议。
