# 沙箱与审批正交

**一句话定义**：评估一个 coding agent 的安全性要用两个**互相独立的轴**——sandbox（能不能做到：OS 层面 agent 碰得到什么）× approval（该不该做：动作要不要人点头）——有沙箱没审批、有审批没沙箱都合法，且**能力清单 ≠ 默认姿态**。

**属于领域**：AI Agent / 安全模型（[[AgentHarness智能体挽具]] 职责"最小权限工具"的评估框架；[[沙箱三态与Executor]] 讲环境放谁家，本笔记讲安全能力怎么评估）

**通俗理解**（比喻/例子，讲完落回术语）：沙箱像**围墙**（物理上翻不出去），审批像**门卫**（每次出门问你要不要放行）。围墙再高也不等于门卫会拦人，门卫再严也管不住你已经翻出去的——所以"有围墙"和"有门卫"必须分开打分。更隐蔽的坑是**能力 ≠ 默认姿态**：grok-build 安全能力堆得最满（Landlock/Seatbelt+seccomp 手写 BPF），但 OS 沙箱默认值是 `"off"`；默认就关进沙箱的只有 codex（受信任项目默认 workspace-write）和 DeepSeek Harness（默认 read-only）。**"我用的 agent 安全吗"的答案取决于默认配置和运行环境，不是它有没有这个能力。**

**四方实测对照**（agent-kernel 系列精读源码结论）：

| 维度 | pi | DeepSeek Harness | codex | grok-build |
|---|---|---|---|---|
| OS 沙箱 | 无（故意，外包给容器） | 内建，默认 read-only（开） | 内建，默认开（Seatbelt/bwrap+seccomp） | 内建，默认 off（关） |
| 文件隔离 | 不硬隔离 | 写限 cwd | 内核硬隔离，.git 强制只读 | worktree 独立副本（CoW） |
| 审批 | 钩子默认不拦 | 插件化，headless fail-closed | 4 档默认 OnRequest | 5 档默认 Ask |

pi 的立场最极端也最诚实：`SECURITY.md` 明说 "intentionally does not have a sandbox"，信任边界 = 运行它的用户账号，明说 prompt injection 防不住（[[提示注入]]）；它唯一真正的安全闸是**工作区信任门控**（项目里能塞指令的资源加载前先过信任检查，且"两遍加载"保证信任决定前不执行项目代码）。codex 的 `--yolo` 注释"仅供本身已在外部沙箱里运行的环境"反向证明：外部容器 + 关内建沙箱是公认合法用法。
