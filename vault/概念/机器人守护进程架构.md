# 机器人守护进程架构

**一句话定义**：把机器人的"大脑"拆成多个常驻后台进程（daemon），各管一摊，通过 Unix socket 上的 JSON-RPC 互相调用；唯一碰电机的进程收口所有安全裁决。

**属于领域**：嵌入式软件架构

**通俗理解**：像一家餐厅——机器人本体是厨房，点菜的（手柄/手机/远程）都不许进厨房，全部把"意图"（"朝这个速度走"）递给唯一的厨师长 robotd，做不做、安不安全由它裁决。microduck 的三条设计铁律值得抄走：① robotd 是唯一能碰舵机的进程（权限收口）；② configd/updaterd/btd **故意不依赖 robotd**——控制环挂了的机器人恰是最需要被修复的机器人，恢复路径不能和被恢复对象绑死；③ 手柄、手机、脚本走**同一条 JSON-RPC**，客户端可替换而 API 不会悄悄腐烂。

**与已有概念的关联**：
- 进程间通话就是 [[JSON-RPC与stdio传输]] 换了个通道（Unix socket 替代 stdio）
- "统一协议降 M×N"与 [[MCP协议]]、[[M×N集成问题]] 同一经济学
- "意图与执行分离"呼应 [[事实与判断分离]] 的权责划分
