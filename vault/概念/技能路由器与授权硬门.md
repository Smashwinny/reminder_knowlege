# 技能路由器与授权硬门

**一句话定义**：在技能包前面加一层**路由器**——AI 接到任务先由结构化路由表（44 条规则 + 175 条回归用例）判断"该进哪个方法论模块"，再经过**授权硬门**（scope.md 里 auth.status=granted 才准碰目标），最后才打开对应 SKILL.md 干活；干活的踩坑记录回流 field-journal 经验库，越用越准。

**属于领域**：Agent 工程 / 安全技能组织（reverse-skill，39k star，45 个技能模块）

**通俗理解**：医院**分诊台**，不是超级医生。病人（任务）进门先分诊（route）：APK 逆向去 jadx/Frida 科，固件去 Ghidra 科——而不是 AI 抓阄猜命令。三件别人没做的事：① **授权门**：点名目标 ≠ 授权，`--force` 永远绕不过 scope 检查，未 granted 前任何"ACT"都拒绝——把 [[提示注入]] 的防线从"求模型听话"升级成"流程不放行"；② **工具自举**：tool-index.md 是唯一事实源，缺什么装什么，换机器不散架（对照 [[健康探测三态]]）；③ **经验进化**：case 复盘写进 field-journal，同样的坑不踩第二次（[[三层记忆]] 的项目级版）。

**与已有概念的关联**：
- 是 [[AgentSkills技能包]]、[[分层按需加载]] 的进一步演化：技能多了之后"选哪个"本身成了瓶颈 → 路由先行，条件读取（PRIMARY 有歧义才看全表）
- 授权硬门与 [[ClaudeCodeHooks与fail-open]] 互为**方向相反的镜像**：遥测挂了要放行（fail-open），安全授权没拿到必须拦死（fail-closed）
- "别重复装已装工具" 同 [[工具目录膨胀]] 的成本意识
- dev-pair（hermes_skills）的 daily_cap 是同一思想的微观版：预算上限由进程硬拒绝，台账 append-only 可审计——**行为约束靠不住的部分，用机制兜底**

**首次接触于**：[[项目笔记/six_skills]]（RULES_zh.md + MASTER-ROUTING 架构精读）

## Easel：技能提示、规则检查与行动许可分别核实（2026-10-05）

[[项目笔记/easel]] 的创作者画像是内容上下文，不是平台登录身份或当次发布许可。`easel skill` 将消息交给 OpenClaw agent；`publish-checklist` 与 `quality-gate` 主要是供宿主执行的 SKILL 文档。读过文档或跑过一个本地扫描器，不能证明宿主加载、技能执行或发布授权已经成立。

`content_guard` CLI 的 `scan` 对 BLOCK 命中返回退出码 7；共享函数 `guard_or_die` 只有在 `exec_mode` 且未设 `allow_unsafe` 时阻断 BLOCK，dry-run 或显式放行分支只告警。因此它是有入口和参数条件的内容规则闸门，不能等同于原项目中不可绕过的授权硬门，更不能把扫描通过当作用户允许发布。AI 措辞或模型名的 WARN 也不是隐瞒生成方式的理由。

固定版本另有契约差异：总规范使用 `.easel.json`，`publish-checklist` 文档仍提 `meta.json`。要核对实际消费者与字段，不能靠相近名称假定接通。检查范围与外部效果的证据边界见 [[证据优先质检ProofOverClaims]]。
