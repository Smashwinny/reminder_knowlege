# 失败反馈具体化

**一句话定义**：agent 循环里，失败反馈必须带三要素——哪一步失败（step）＋缺什么/错什么（missing）＋允许怎么改（fix）；"失败了，请重试"是 0 比特信息，只会引发原样重跑。

**属于领域**：AI Agent / 循环工程（Loop Engineering）

**通俗理解**：对着卡住的员工喊"错了，重来"，他只能把刚才的事原样再做一遍——你给了情绪，没给信息。告诉他"第 3 步算总数时没读数据表，去读 data.csv 把 sales 列加起来"，他下一轮就能修对。agent-engineering 实验 1 实测：同一个规则策略、同一套工具，0 比特反馈组 5 轮逐字重复同一动作全烧完；三要素反馈组 2 轮收敛通过。**变量只有一个：反馈里带不带信息。**

**与已有概念的关联**：
- [[图环挽具三层工程]] 的 loop 层讲循环**结构**（有界诊断→修复→复验），本概念补上循环里流动的**信息质量**——结构对了喂 0 比特照样空转
- [[HardFailure一票否决与发布门禁]] 是它的反面：某些失败不进循环直接熔断
- [[AgentHarness智能体挽具]] 七职责之"失败廉价"的量化形式：反馈每多 1 要素，重试期望轮数骤降

## Patchright Enhanced：把失败步骤、残留状态和重试主体写清（2026-10-05）

[[项目笔记/patchright_enhanced]] 给失败反馈补充资源清理案例：历史 L06 用例让惰性 context.close 拒绝，真实 BrowserManager 将同一错误向上传播，仍保留 context 引用，并且没有调用 cleanup。反馈应同时说明“关闭阶段失败”“引用仍在、清理未开始”“后续需要由调用方按契约处理”，不能只写一个失败布尔值或笼统保证最终都会清理。

L07 是测试代码主动第二次调用 closeAndCleanup，替身这次成功后才继续清理；它不证明管理器自动重试、自动恢复或真实浏览器崩溃恢复。L05 的重复调用证据只覆盖顺序执行且首次成功后的局部幂等，不覆盖并发关闭、初始化中途失败或 cleanup 自身抛错。

这复用 step/missing/fix 的诊断纪律，没有声称上游实现了结构化反馈协议。[[Provider适配层与错误契约]] 中 LLM EventStream 的“永不 reject”是另一接口契约，不能套到本管理器；[[健康探测三态]] 也不能用单个配置断言替代真实依赖探测。浏览器资源清理与 [[工具调用生命周期]] 的 MCP 调用循环相关但非同义，范围详见 [[接缝与桩实现StubSeam]]。
