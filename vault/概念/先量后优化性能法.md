# 先量后优化性能法

**一句话定义**：优化前先测量定位瓶颈——"页面卡"的第一反应（减面/关特效）可能是白砍，实测 GPU 只用了预算的 1/8，真凶是贴图显存；测量本身也有纪律（vsync 会骗人、要串行跑、噪声不当改进）。

**属于领域**：性能工程 × 工程方法论

**通俗理解**：病人说"难受"，第一反应不该是开刀（减面），是先量体温验血（GPU 耗时/绘制调用/显存清单）——小王子 demo 整条渲染链 0.37ms@16.7ms 预算，GPU 闲得很；卡是因为 31 张 8192² 贴图吃掉 5.0 GiB 显存，GPU 一直在做纹理换入换出。只跑 `gltf-transform resize` 降贴图：显存 5.0→0.22 GiB（23×），三角面一个没动，肉眼看不出差别。

**测量纪律三条**：
1. **别信帧间隔**——它被 vsync 锁在 8.3/16.6ms，两组资产的帧间隔中位数可以一模一样；要挂 `EXT_disjoint_timer_query_webgl2` 量每帧 GPU 真实耗时
2. **串行测量**——和任何其他渲染任务共享 GPU 的数据整批丢掉重测（实测被 headless 录屏干扰出 8.57ms/61.8ms 的离谱方差）
3. **诚实下结论**——A/B 差值落在噪声里就写"量不出回归"，不写"变快了"；固定采样协议（刷新→漫游→回出生点静止）

**与已有概念的关联**：
- 同族：[[证据优先质检ProofOverClaims]]（测量结果也是证据，测量方法本身也要被怀疑）、[[事实与判断分离]]（能测的绝不猜）
- 瓶颈定位序：先量 GPU 耗时 → 先砍贴图（[[面数口径与减面下限]] 的显存账：8192²=268MB+mipmap≈358MB/张）→ 再合并绘制调用 → 最后才砍面
- 对象：[[Three.js与场景图]] 场景（antialias 在 EffectComposer 下白付、阴影降档、自适应分辨率留死区防抖动）
