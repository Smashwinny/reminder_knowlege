# daemon缓存与在线解密

**一句话定义**：本地加密数据 CLI 的性能架构——CLI 只做客户端，常驻 daemon 进程把解密结果按"mtime 未变即复用"缓存到磁盘（Unix socket/named pipe 通信），并优先对加密库"在线打开"（每页随读随解、不落明文副本），把解密成本摊销到 daemon 生命周期。

**属于领域**：本地数据工具的系统架构。

**通俗理解**：全量解密像"每次查档案都把整馆书翻译成中文另存一份"；daemon 缓存像"聘一个常驻翻译官"——第一次开馆他把常查的书翻译好摆在自己桌上（cache），书没换新（mtime 不变）就直接递给你，毫秒级；在线解密则是翻译官连"另存"都省了，拿着词典读原版，读一页翻一页。讲完比喻落回术语：首次查询拉起 `wx-daemon`，解密库 + `_mtimes.json` 索引落 `~/.wx-cli/cache/`；SQLCipher 走 rusqlite raw-key `x'<64hex>'`（跳过 PBKDF2）+ `PRAGMA query_only = ON` 只读在线打开，打不开才降级为解密副本。

**与已有概念的关联**：
- "在线打开 vs 副本解密"是 [[进程取钥与副本解密]] 内部"临时副本"方案的进一步取舍：wx-cli 连临时副本都尽量不落，副本只是降级路径
- [[CleanRoom只读读取器]] 强调"只读"边界；本架构的 `query_only` + 只读 OpenFlags 是同一边界在 daemon 形态下的实现
- mtime 复用是 [[缓存有效期与发布边界]] 思想的最小实现：用文件 mtime 当失效信号，避免全量比对
