# 工具调用三段式流水线

**一句话定义**：工业级 agent 内核把一次工具调用拆成 prepare（找工具→schema 校验→权限钩子）→ execute（真正执行，唯一并行段）→ finalize（钩子可改写结果）三段——pi 内核 792 行中工具执行占 418 行（53%），主循环本体只有 126 行。

**属于领域**：AI Agent / 内核机制（[[工具调用生命周期]] 讲 MCP 协议侧的发现→调用→返回循环，本笔记讲内核侧一次调用内部的执行流水线）

**通俗理解**（比喻/例子，讲完落回术语）：像**餐厅出一道菜的流水线**——prepare 是接单员（核对菜名在不在菜单上、下单格式对不对、经理要不要否掉这单【权限钩子返回 `{block:true}` 即拒绝，拦截理由回喂模型】），execute 是后厨（唯一可以多灶同开的环节），finalize 是出餐口（试菜员可以改摆盘、标"出错"）。关键在三个"真踩过坑才会写"的防御：①**截断整批作废**——输出被 token 上限截断时残缺 JSON 可能"看起来合法"且 schema 校验通过，所以整批标记失败一个都不执行；②**一票降级、全票终止**——一批里有一个声明必须串行（edit 和 bash 混批）整批就串行，反过来必须全批要求终止才终止；③**按文件排队**——并发写同文件互相踩，按路径排队、异文件才并行。

**并行三顺序**（pi 刻意错开）：准备阶段**串行**（权限确认弹窗不能几个同时弹）→ 开始事件和结果消息按**源顺序**发（transcript 确定）→ 完成事件按**完成顺序**发（UI 先亮先完成的）。只有 execute 包进 Promise.all——"只并行该并行的那一段"。实测（agent-kernel demo-order）：3s/1s/2s 三工具总耗时 3.0s（串行 6s），完成序 2-3-1、喂回模型的顺序仍是 1-2-3——**执行是并发的，历史是确定的**。

## AI Native 手册：准备通过后，资源侧仍需检查（2026-10-05）

[[项目笔记/ai_native_handbook]] 的增量是：prepare 阶段通过 schema 或一次前置许可，不代表后续真实资源调用可以免检。工具可被发现、主体已登录、一次请求曾被批准、当前目标可执行，是不同证据。入口放行只对当时的上下文成立；目标、参数或权限状态变化后，执行方仍须以可信资源目录与当前委托重新判断。

手册分别讨论身份认证、代表用户的委托、策略判定和供下游验证的凭证；PDP（策略决策点）决定许可，PEP（策略执行点）把判定落实到执行路径，凭证代理是另一项职责。它们可与 [[控制面与数据面]] 对照，但不是原 pi 三段式调用的同义架构，也不表示原内核已实现手册全部角色。[[MCP协议]] 的互通或 OAuth 登录同样不自动批准每个工具、动作和资源。

本项目的自编 Python `Broker.request` 在打开固定合成资源前调用 `decide`，检查当前委托链及请求绑定；调用者自报“已批准”的文字不进入许可判定。程序只演示单进程应用层检查，没有运行 pi、MCP、OAuth、网关或凭证兑换链路；判定与读取之间也未验证并发 TOCTOU 或符号链接竞态。
