# 工具调用生命周期

**一句话定义**：AI 调用工具的完整循环：工具发现（tools/list）→ 模型决策（点名工具）→ 客户端传话（tools/call）→ 服务器执行 → 结果返回模型 → 模型综合回答。

**属于领域**：AI Agent 机制。

**通俗理解**（比喻/例子，讲完落回术语）：
模型像**点菜的顾客**（只会说"我要 write_file"），MCP Client 像**服务员**（传话），MCP Server 像**后厨**（真正动手）。关键认知：**大模型本身不执行任何工具，它只输出"我要调某工具+参数"的意图，执行方永远是外部程序**。另一关键点：模型选工具依据的是工具名和描述的质量——描述含糊的工具模型想不起来用（社区为此提出 TDQS 工具描述质量评分）。在 [[MCP模型上下文协议]] 中，这个循环由 [[JSON-RPC与stdio传输]] 报文承载。

## WeChatBridge：一次性消费不保证恰好一次外部效果（2026-10-06）

[[项目笔记/wechat_bridge]] 的 ConsumeIntent 先读取并删除 intent 文件，再解析和判断新鲜度。历史 +89 秒注入返回 Ready，恰好 +90 秒返回 Expired；顺序再次调用及同进程新 Reader 不再取得该请求。未来一小时的 RequestedAt 仍满足 age<90 秒，说明现有判断没有非未来下界；没有真实等待这些时长。

读取与删除不是原子领取，删除后至外部动作之间也可能失败。上述用例没有并发消费者、进程崩溃或真实目标动作，不能把源码注释“永不重放”升级为 exactly-once、防重放认证或下游幂等保证。

这是批次动作交接，不是 [[Handoff交接简报续跑]] 的跨对话摘要，也不是原 MCP 发现/调用协议的实现。与 [[项目笔记/openmuse]] 的操作键和未知结果相关：请求被消费、动作发出与目标接受分别取证，关联 [[证据状态机]]、[[沙箱与审批正交]]。
