# 单一馈送与schema冻结

**一句话定义**：整个系统的所有消费者只读**一个状态快照端点**（SideCrab crabd 的 `GET /v1/state`，一份 JSON 装下全部会话状态 + 用量表 + 燃烧量），并且 schema 版本号**只在破坏性变更时才升号**（钉在 5），新增字段一律靠"字段存在性探测"点亮，未知键一律忽略。

**属于领域**：软件工程 / API 设计（状态服务与版本演化策略）

**通俗理解**：对比两种反面设计就懂了——(a) 多端点：面板查 3 个接口拼图景，必有"端点 A 新了端点 B 还旧"的时序谎言；(b) 严格白名单版本：crabd 每加一个字段就得让所有已装出去的面板同步升级，否则直接变砖。SideCrab 的文档原话：*"schema marks the last BREAKING shape"*；真正的破坏 = 升号 + 协调部署，所以"应该罕见"。配套的诚实原则：未知值渲染成破折号（—）而不是 0；数据馈送超过 30 秒不更新就亮"数据截至 HH:MM"横幅并把螃蟹转 worried——**绿色永远意味着数据是新鲜的**。

**与已有概念的关联**：
- 三态诚实渲染是 [[健康探测三态]] 的面板版：fresh/stale/dead 必须可区分
- additive-only + 存在性探测，与 [[HomeAssistant自动发现]] 的"能力由数据声明、消费者按需点亮"同思想
- 单一事实源与 [[统一数据网关]] 同构：多个上游（hooks、转录、OAuth 用量）汇进一份快照，多个下游（面板、通知器）各取所需
- 消费端"open set"心态：见到陌生枚举值（如新状态 failed）回落中性渲染，别把 switch 写死——这正是 [[机器人守护进程架构]] 里版本兼容的通用功夫
