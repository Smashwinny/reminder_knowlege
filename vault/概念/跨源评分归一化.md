# 跨源评分归一化

**一句话定义**：把单位不同的多种热度指标（star / upvote / 下载量 / 调用次数）用各自的换算函数压到同一量级再统一排名——hype 的 `scorePost`：GitHub/HF 原值、Reddit ×0.3、Replicate 次数取 ^0.6 幂函数压平大数。

**属于领域**：数据聚合 / 排序工程

**通俗理解**：不同国家的钱不能直接比数字——100 日元买不到 100 元人民币的东西；排名前先"换汇"。幂函数（x^0.6）是给大数准备的"累进税"：数值越大增长越慢（32000^0.6≈504，和几千 star 同量级），不然调用次数动辄几万的平台会碾压全场。实测验证：Reddit 原始 3000 赞打折后排在 1000 star 仓库之后；权重 0.3→1.0 一改，Reddit 立刻登顶——**谁定权重，谁定什么是"热门"**。

**与已有概念的关联**：
- 排名全程纯规则零 LLM——热度本身是客观数字，是 [[事实与判断分离]] 的天然适用场景；黑名单过滤（6 个 banned 词）则是 [[确定性脚本]] 式闸门
- 与 [[混合检索与RRF融合]] 互为镜像：RRF 用"排名名次倒数"融合多通道检索结果，scorePost 用"换算函数"融合多平台热度，都解决"多来源分数不可直接相加"的问题
- 与 [[评分契约与护栏]] 同理：统一刻度 + 固定权重，结果可复现可后验
- **教训（先截断后归一误杀）**：hype 先在 SQL 里按原始 stars 排序 LIMIT 500、之后才做归一化——高原始值低换算分的条目（如 Reddit 神帖）可能在粗筛阶段就被挤出候选池，活不到加分环节；正确做法是把归一化下推进 SQL。任何"先粗筛后精排"的管道都要检查这个次序陷阱

**实例出处**：replicate/hype 的 src/db.ts scorePost 函数（6/6 本地实验全 PASS）
