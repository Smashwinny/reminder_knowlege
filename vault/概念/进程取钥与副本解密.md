# 进程取钥与副本解密

**一句话定义**：attach 进目标进程从内存取出解密密钥、只在数据的"临时副本"上解密读取的路线——原数据库文件从头到尾不被修改。

**属于领域**：数据安全 / 本地加密数据的合法读取（与逆向工程边界相邻）。

**通俗理解**：还用保险柜的比喻（对照 [[CleanRoom只读读取器]]）：CleanRoom 是"你本人把钥匙借我，我在客厅读文件"；这条路线是"趁保险柜主人在场，直接看他手里的钥匙，然后把柜子里的东西<b>复印一份</b>到桌上读"——自动化程度高（用户零操作），但毕竟动了"人"（注入运行中的进程），可被安全软件察觉，且目标程序一升级（换锁）随时失效。讲完比喻落回术语：Frida 是动态插桩框架，attach 已登录的微信 4.x 进程 → 内存取出 SQLCipher 密钥 → 复制数据库到临时目录 → 在副本上解密读取；密钥不落盘、数据源关闭即删临时文件。

**与已有概念的关联**：
- 与 [[CleanRoom只读读取器]] 是<b>同一目标的两条对立路线</b>：不碰进程、密钥本人提供 vs 注入进程、自动取钥；隐私底线一致（只读、密钥不落盘、临时文件即删）
- 读取对象同样是"SQLCipher 整库加密 → 压缩消息体 → 明文"的三道门结构（见 [[项目笔记/wechat-intelligence-hub]] 实测）
- "只在副本上动手"是 [[事实与判断分离]] 的数据来源前提：事实层永远只读

**实测要点**（wechat-ai-memory）：微信适配层六个模块（discovery/key_capture/crypto/media/voice/source）全部隔离在 `sources/wechat4_*` 后面，JSON 备用入口可以完全不触发这条路线——本批次实验即以此守住隐私红线（全程只用虚构样例，未连真实微信）。
