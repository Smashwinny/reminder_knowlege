Q1

手册的 Astra / Sol / Luna 该怎么理解？

“旗舰 / 平衡 / 轻量”是原手册的选型思路，不是永久官方规格。2026-11-22 官方模型索引列出 GPT-6.2 Astra、GPT-6.2 Sol、GPT-6.1 Terra、GPT-6 Luna、GPT-6 Cyber；旧 `gpt-6-sol` 与 `gpt-6.1-sol` 页面仍可读取，但后者未出现在当前索引。

具体差异：旧 `gpt-6-sol` 支持 reasoning effort `none`，`gpt-6.1-sol` 和当前 `gpt-6.2-sol` 页面均不接收 `none`。所以复现必须锁型号和查询日期，不能静默替换。

Q2

提示词缓存的当前事实是什么？

主题2026-11-22 官方缓存文档口径
最小前缀GPT-5.6+ 为 1,024 个可见输入 token；更早模型按型号与请求配置而异。
断点GPT-5.6+ 隐式断点跟随最新合格消息，也支持显式断点；不是固定每 128 token 一个断点。128 是部分旧模型回执向下取整的粒度。
变化影响精确前缀决定复用边界；变化点之后不能复用，不能夸张成“任何一处变化都让全部缓存归零”。
写入与 TTLGPT-5.6+：30m 默认且为最短覆盖，写入 1.25×；Responses API 的 12h 为 2.5×。读取可延长覆盖，TTL 不是保证删除时刻。
命中读价多数 GPT-5.6+ 为 0.1×；6.2 Astra、6.2 Sol、6.1 Sol、6.1 Terra 为 0.05×。必须按型号查价。
回执OpenAI `usage.input_tokens_details.cached_tokens`；写入与 TTL 另有细分字段。真实命中还受路由等条件影响。
Q3

本地实验到底算出了什么？

样本是当前 `vault/00-总览.md`，粗估 65,903 token；每次新增 200 token、共 10 次，普通读价假设 $5/M，首次写入 1.25×，之后假设全部命中。这只是确定性成本模型。

0.1× 命中读：不缓存 $3.3052；缓存 $0.7187；省 78.3%；平衡 2 次
0.05× 命中读：不缓存 $3.3052；缓存 $0.5704；省 82.7%；平衡 2 次

“平衡 2 次”只属于这组全命中假设。真实命中率、流量路由、TTL、输入价格和新增 token 改变时，都要重算；粗分词也不能替代真实 tokenizer 和账单。

Q4

缓存使用的四条纪律

  1. 稳定内容在前：易变时间戳、随机 ID 放在稳定前缀之后；
  2. 回执验证：看 cached/write tokens，不从“应该命中”推断“已经命中”；
  3. 写入入账：预热有成本，低频调用不一定划算；
  4. TTL 与路由：把调用聚在覆盖窗口内，同时接受命中不是保证。

Q7

选型实验的正确姿势

① 锁 model ID 与文档日期
② 同任务双跑：质量、返工、延迟和总账一起比
③ 缓存设计：稳定前缀在前，易变内容在后
④ 留 usage 回执；估算值与实付账单分开
Q8

订阅额度 ≠ API 缓存折扣

ChatGPT/Codex 套餐与 API token 计费是不同产品账。即使都出现“额度”或“缓存”，也不能直接建立汇率。套餐看套餐规则，API 看模型价格与 usage。

Q9

对本仓库有什么启示？

学习仓库是“大稳定资料 + 小新问题”的潜在缓存友好负载，但只有在同一 API 组织、型号、区域与合格前缀等条件满足时才可能命中。不能为了缓存把总览无脑塞给每次调用；先证明收益，再控制上下文成本。
