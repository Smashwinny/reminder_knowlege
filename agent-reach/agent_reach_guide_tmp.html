1
Agent Reach 是什么？

它是一个"能力层"（capability layer），不是又一个爬虫工具。官方原话："给你的 AI Agent 一键装上互联网能力"。你复制一句话给 Claude Code / Cursor，几分钟后你的 Agent 就能读推特、搜 Reddit、看 YouTube 字幕、刷小红书、抓 B站视频。

它做四件事：选型（每个平台替你选好当下最稳的接入方式）、安装（装好上游 CLI 工具）、体检（doctor 一条命令查所有渠道通不通）、路由（某条接入失效了换备选，用户无感）。真正的数据读取由 Agent 直接调用上游工具完成，中间没有任何包装层——所以它几乎没有性能损耗，也不会成为新的故障点。

2
为什么 AI Agent 需要它？

AI Agent 能帮你写代码、改文档、管项目——但你让它上网找点东西，它就抓瞎了：

你说结果
"看看这个 YouTube 教程讲了什么"拿不到字幕
"搜一下推特上大家怎么评价这个产品"Twitter API 要付费
"去 Reddit 看看有没有同样的 bug"403 被封，服务器 IP 被拒
"看看小红书上这个品的口碑"必须登录才能看
"帮我看看这个网页写了啥"抓回一堆 HTML 标签没法读

这些功能都不难，但每个平台都有自己的坑：付费 API、IP 封锁、登录门槛、数据清洗。自己一个一个踩坑装工具调配置，光让 Agent 读个推特就得折腾半天。Agent Reach 把"踩坑"这件事一次性做完，并承诺持续维护——平台封了它修，有新渠道它加。

3
它和 MCP 是什么关系？

知识库里我们已经学过 MCP 协议（AI 连接外部工具的开放标准）和 Agent Skill（装给编程智能体的方法论包）。Agent Reach 和它们的关系是"互补，不是替代"：

MCPAgent Reach
形态协议 + 服务器（进程/HTTP）Python CLI + 一份 SKILL.md 说明书
Agent 怎么用它框架内置工具调用Agent 直接执行 shell 命令（curl / yt-dlp / bili）
覆盖重点通用工具接口标准化互联网平台接入的选型与运维
反爬对抗取决于各 MCP server 自己核心战场：哪家 CLI 还活着、怎么绕过风控，持续换路由

它内部也用到 MCP：全网语义搜索走 Exa via mcporter（MCP 接入、免 Key），LinkedIn 渠道也是 MCP server。所以它其实是"MCP 生态 + 独立 CLI 工具"之上的又一层运维管家。

4
核心架构：一个渠道 = 一个有序后端列表

仓库 agent_reach/channels/ 下每个平台一个 Python 文件，全部继承 Channel 基类。设计契约非常漂亮：

  • backends 是有序候选列表：第 0 个是首选，其余是备选。"换后端" = 调整列表顺序，不是重写代码。
  • check() 必须真实探测各候选并设置 active_backend——代码注释强调：shutil.which() 不能证明健康（失效的 venv shim 也能通过 which）。
  • 用户可用配置 <channel>_backend 强制指定后端，覆盖值无效时自动忽略，永不藏掉可用后端。
5
doctor 体检：missing / broken / timeout 三态判定

agent-reach doctor 是项目的招牌命令。它的核心在 probe.py：probe_command() 会真的执行 cmd --version 这样的无副作用探测命令，并把结果分成三态：

状态含义典型场景
missingPATH 里找不到命令压根没装
broken命令在但执行失败（退出码 126/127，或解释器丢失）系统 Python 升级后 pipx/venv 装的 CLI 全部失效—— which() 照样能找到 shim！
timeout / error能执行但行为异常工具卡死、报错
💡 这个三态设计对我们自己的工具链也很有参考价值：shutil.which() 只能回答"文件在不在"，回答不了"能不能跑"。doctor 的处方（hint）机制也妙——broken 时直接告诉你"重装即可修复：uv tool install --force xxx"。
6
"首选 + 备选"路由的真实战例

bilibili.py 的文件头注释记录了一次真实战役：2026-06，B站风控把 yt-dlp 全面 412 封死（作者试过最新版、直连、代理、预热 Cookie 全部无效），而 bili-cli 无需登录仍能搜索/读详情。于是 yt-dlp 从 B站渠道退役（仍服务 YouTube），B站路由切换为：

bili-cli（搜索/热门/详情，免登录）▸ OpenCLI（浏览器登录态，补字幕）▸ B站搜索 API（零依赖兜底，仅搜索）

顺带一提：B站渠道还有个聪明的兜底——_check_search_api() 用 Python 标准库 urllib 直接请求 api.bilibili.com 搜索接口，连第三方工具都不需要就能确认"至少搜索可用"。本次动手实验我们直接验证了这个接口（见第 12 问）。

7
Cookie 与登录态：安全设计

Twitter、小红书、Reddit、Facebook、Instagram 这些平台必须登录态。Agent Reach 的安全承诺：

  • 🔒 Cookie / Token 只存本机 ~/.agent-reach/config.yaml，Unix 下权限 600（仅所有者可读写），不上传不外传；
  • Twitter 只接受用户用 Cookie-Editor 浏览器扩展手工导出，工具不替你扫码登录；
  • 小红书走 OpenCLI 时只复用你自己 Chrome 已有的会话，不读取、不注入浏览器 Cookie；
  • 配置读取支持 --stdin，避免敏感值出现在进程参数里被别的进程看到；
  • uninstall 一条命令清掉全部凭据与 skill 文件。
⚠️ 官方仍建议：凡是用 Cookie 登录的平台（Twitter/小红书等），一律用专用小号。因为平台可能检测到非正常浏览器的 API 调用行为导致封号——这不是工具的锅，是"自动化 vs 风控"的猫鼠游戏本身。

9
装完后 Agent 怎么知道调什么？—— SKILL.md

答案就在我们学过的 Agent Skill 机制里：安装时 Agent Reach 会往各 Agent 的 skills 目录写入一份 SKILL.md，里面写清每个平台该调什么命令、需要什么配置。用户不需要记任何命令——Agent 读了说明书自己知道该调 curl https://r.jina.ai/URL 还是 yt-dlp --write-subs。

所以它的完整形态是：Python CLI（安装/体检/配置）+ 一份 SKILL.md（教 Agent 用法）。这也解释了 README 里那句"任何能跑命令行的 Agent 都能用"——不依赖任何特定框架。

10
一条安装命令背后发生了什么？

你只需对 Agent 说一句话："帮我安装 Agent Reach"。背后的六步：

  1. 安装 CLI：从 GitHub 装 agent-reach 命令（自带 yt-dlp、feedparser；⚠️ 不要从 PyPI 装同名包，那不是本项目）；
  2. 检查基建：Node.js、gh CLI、mcporter 缺失项给出安装指引；
  3. 按授权安装配置：仅显式传 --system 才装系统依赖、接入 Exa；
  4. 环境探测：判断本地电脑还是服务器，服务器建议配代理（约 $1/月）；
  5. 注册 SKILL.md：同样只在 --system 时写入 Agent skills 目录；
  6. 点名才装：默认只激活零配置渠道，需要登录态的列菜单问你。
# 默认：只读安全检查，列出缺失项，不改系统
agent-reach install --env=auto

# 先看看会做什么
agent-reach install --env=auto --dry-run

# 明确授权后才真正安装依赖 + 写配置 + 注册 skill
agent-reach install --env=auto --system
🛡️ "默认安全"哲学贯穿全项目：dry-run 预览、显式 --system 授权、凭据本地 600 权限、卸载一键清——这本身就是一份优秀的 CLI 安全设计教材。

🧪 第 12 问 · 动手实验：亲手验证 5 个零配置渠道

以下实验于 2026-10-02 在本机（Windows 11, Python 3.14.7）全部真实执行。设计思路：Agent Reach 本身是"胶水层"，每个渠道底层都指向一个具体的上游接口/工具——我们直接验证这些底层事实，等于验证了 doctor 探测的对象。实验记录全文见 agent-reach/exercise/experiment-log.md。

✅ 实验 1：Jina Reader 读网页（web 渠道底层，零配置零 Key）

curl "https://r.jina.ai/https://example.com"

原理：把任意 URL 前面拼上 https://r.jina.ai/，Jina 的免费服务把网页 HTML 洗成干净 Markdown 返回。Agent Reach 的 web 渠道首选就是它。

✅ 预期结果：返回 "Title: Test Document" + Markdown 正文。实测通过——返回了标题和清洗后的 Markdown 内容。

✅ 实验 2：B站搜索 API（bilibili 渠道兜底后端，doctor 探测的同一接口）

curl -A "Mozilla/5.0 (Macintosh; ...)" "https://api.bilibili.com/x/web-interface/search/all/v2?keyword=agent&page=1"

原理：bilibili.py 的 _check_search_api() 用标准库探测的就是这个接口，code:0 即"至少搜索可用"。

✅ 预期结果：JSON 里 "code":0,"message":"OK"，且带搜索结果分页信息。实测通过——numResults:1000, numPages:50。

✅ 实验 3：V2EX 热帖（v2ex 渠道底层公共 API）

curl "https://www.v2ex.com/api/topics/hot.json"
✅ 预期结果：JSON 数组，含 node/title/url 等字段。实测通过——返回 programmer 节点热帖数据。

✅ 实验 4：GitHub 官方 API 读仓库（github 渠道 gh CLI 的底层）

curl "https://api.github.com/repos/Panniantong/Agent-Reach"
✅ 预期结果：仓库元数据。实测通过——stargazers_count: 88005，MIT 协议（推文传播速度惊人，88k stars）。

✅ 实验 5：RSS 源零依赖解析（rss 渠道概念验证）

python -c "import urllib.request, xml.etree.ElementTree as ET; ..."  # 抓 ruanyifeng atom.xml
✅ 预期结果：解析出 feed 标题与文章列表。实测通过——"阮一峰的网络日志"，3 篇 entry（第 413 期科技爱好者周刊等）。
📌 诚实声明：本机权限策略禁止执行本会话新克隆的外部仓库代码（pip install -e repo），故 agent-reach install / doctor 本体未在本机运行；但 5 个实验验证的全部是 agent-reach 各渠道真实依赖的底层接口（代码逐行核对过），你在自己机器上执行 pip install https://github.com/Panniantong/agent-reach/archive/main.zip && agent-reach doctor 即可得到体检报告。
