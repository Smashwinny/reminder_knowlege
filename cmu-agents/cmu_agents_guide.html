Q3

作业链为什么是 Harness→Eval→Training？

推荐人最推崇的就是作业设计。三次个人作业 + 一个团队研究项目，权重 10% / 15% / 15% / 项目 45%（含 proposal/check-in/poster/report）：

作业截止干什么背后方法论
A1 HarnessSep 14在开源 LLM 上搭 coding agent 的 harness（本指南实验的主角）调用模型只是基础，会搭才是工程
A2 EvalOct 1设计评测框架，度量 agent 的正确性与功能没测评就没有改进的方向（[[LLM裁判与自动评估]]）
A3 TrainingOct 29实现 SFT/RL 训练流程，改进自己的 agent从"调 API"升级到"造模型行为"
研究项目学期末团队攻一个开放研究问题（如并行 agent 的安全与可靠性权衡）课程明说：欢迎把作业发展成论文
✅ 这个顺序 = 搭起来 → 测得准 → 练得强 → 推出去。与工业界共识一致：先有 harness 与 eval，才谈得上 training——没有测量就没有优化。
Q4

从语言模型到 Agent，关键一步是什么？

Lecture 01 给出了全课最核心的一句话心智模型：Agent = 模型在循环里（A model in a loop）。语言模型本来只会"预测下一个 token"，而 工具调用就是另一种可以被预测的 token 序列——harness 负责解析、校验、执行它，把结果变成观察 token 喂回去：

三个立即可用的认知：①工具定义是暴露给模型的类型化接口（名字+描述+JSON Schema），chat template 把它渲染成文本；②工具调用是 assistant 消息里的结构化请求，工具结果是 role:"tool" 消息、靠 tool_call_id 与调用挂钩；③Russell & Norvig 的经典定义在这里落地：环境=仓库/网站/工作流，传感器=消息/文件/截图，执行器=工具。

Q5

ReAct 循环长什么样？（作业 1 的核心 + 我的实现）

作业 1 要求在 Agent 基类实现域无关的 ReAct 循环，再让 CodeAgent（修软件 bug）和 ChessAgent（下棋）各自只提供自己的工具。消息序列随步骤生长：

[system]  常设指令 + <system_information>（环境信息块）+ 技能目录
[user]    任务描述
[assistant] 推理 + tool_calls: [{id:"call_1", name:"execute", arguments:...}]
[tool]     {"tool_call_id":"call_1", "content":"命令输出（超 1 万字符掐头留尾）"}
[assistant] 下一步推理 + tool_calls ...   ← 每一步都把全部历史重新发给模型

Q6

观察爆炸怎么办：截断 + 上下文压缩

Agent 每步都重发全部历史，一次 cat 一个 2.6 万字符的文件就能把 prompt 撑爆。作业给出两层防御：

第一层：单条观察截断（harness 硬规则）

超过 10,000 字符的输出，头尾各留 4900 字符，中间换成省略提示——模型仍能看到文件开头结尾，并被告知可以"读更窄的范围"。这是确定性代码，不花 token。

第二层：上下文压缩（模型自己做工作记忆）

超阈值时，把老步骤喂给模型总结成一段工作记忆（保留目标、已跑命令、具体结果、失败路线、下一步），最近一步完整保留；system/task 消息永不压缩。

Q7

Skills 渐进披露怎么实现？

技能（Skill）是提前写好的"一类工作的操作手册"。问题：技能多了、每个又长，全塞进 system prompt 会吃光预算。作业采用 Agent Skills 协议的渐进披露（progressive disclosure）：

层内容何时进上下文
第 1 层：目录每个技能一行「name: description」（来自 SKILL.md 的 YAML frontmatter）常驻 system prompt
第 2 层：全文SKILL.md 正文（如 submit-task 的三步提交协议）模型主动调 invoke_skill(name) 才加载
# 实测验证（demo 输出）
catalog names submit-task in prompt: True
skill body (patch.txt) hidden until invoked: True   # 正文绝不提前泄漏

作业还埋了一个"负面测试"：技能不存在时，prompt 里不许出现 patch.txt 字样——防止模型凭幻觉自行发明提交协议。与本库 [[分层按需加载]]、[[AgentSkills技能包]] 完全同构：小入口常驻，大主体待命。

Q8

程序化工具调用强在哪？

普通工具调用一轮一个动作；程序化工具调用（programmatic tool calling）让模型写一段 Python，在沙箱里一次跑完"枚举候选招→模拟→评估→选最优"的整个程序——把"每步都要模型拍板"的循环，压缩成"一次代码执行"。作业 1 Part 3 的 run_python 就是它：模型写的代码经 base64 编码送进沙箱的 sandbox_python.py 执行（工具函数在那里可直接 import，棋局服务器就在本机），agent 进程从头不碰这些代码。

安全边界值得注意：代码永远在沙箱执行，返回值只是打印出的 JSON——模型代码与 agent 进程物理隔离，这正是 Q12 沙箱一课的伏笔。

Q9

SFT：把专家轨迹灌进模型（讲 8）

监督微调（SFT）= 拿大量"专家怎么干活"的完整轨迹（任务→一系列推理+工具调用+观察→成功收尾）当训练数据，让模型模仿。作业 1 的价值在此显现：你先亲手搭好 harness 跑出轨迹，作业 3 才有数据可训——harness 产出的日志格式，就是 SFT 的训练样本格式（课程读单 OLMo、StarCoder 即此类开放训练谱系）。SFT 便宜、稳定、教会"动作长什么样"；但它只能复制示范者水平，超越要靠 RL。

Q10

RL 训 Agent：奖励从哪来？（讲 9/11/12）

课程用整整四讲（SFT→RL 基础→高级算法→RL Systems）回答"怎么让 agent 比示范者更强"。核心是可验证奖励（verifiable reward）：

域奖励信号为什么适合 RL
Coding测试是否通过自动、客观、秒级判定（SWE-Bench 即此思路）
Chess赢 / 输 / 规则合法规则引擎就是免费裁判
Deep Research答案可核对 / 引用真实部分可验证，需设计

RL Systems 一讲（客座 Apurva Gandhi）讲工程真相：RL 训练的瓶颈常不在梯度，而在 rollout——要让模型对成千上万个任务各自跑完整 agent 轨迹，沙箱基建、生成吞吐、样本回收构成了真正的系统设计题。这解释了课程为何给作业配了 Modal 云沙箱与算力赞助商。

Q11

安全与框架课教什么？

Safety（7a / 9b）

沙箱与凭证管理：模型生成的代码不可信，执行必须隔离（作业里的 Modal 沙箱、Q8 的 base64 送代码都是实例）；可观测性：agent 生产环境要能回放每一步（作业强制保存轨迹 JSON 正是这个纪律的最小版）。

Frameworks（7b / 9a）

OpenHands（Neubig 亲授）与 LangGraph：手写 harness 之后再看框架，才知道框架帮你省了什么、藏了什么。本库 [[LangGraph与Agent编排]]、[[AgentHarness智能体挽具]] 可对照。
