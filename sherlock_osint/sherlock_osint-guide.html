01

Sherlock 到底能发现什么，不能证明什么？

它发现的是“符合站点规则的公开用户名页面线索”，不是一个人的全部账户，更不是账户归属证明。

OSINT 指公开来源情报。Sherlock 的输入是用户名，站点清单负责告诉它“去哪里看、怎样解释响应”。如果两个网站都有 learner_demo，结果只说明两个 URL 都呈现命中信号；它们可能属于不同人，也可能是他人抢先注册。

夸张宣传纠偏：“找到所有账户”遗漏了公开可访问、清单覆盖、规则有效、未受 WAF/限流影响、同名归属五个前提。把输出当线索清单，不当人物档案。

03

一次查询从命令行到结果，内部经过哪些步骤？

核心是一条“清单驱动的并发 HTTP 判定流水线”，不是一个能理解人物身份的搜索引擎。

  1. 读取本地或在线 JSON，移除排除项与默认 NSFW 项；--site 可缩小范围。
  2. regexCheck 不匹配时直接记 ILLEGAL，不发 HTTP。
  3. 把用户名替换进 url 或独立 urlProbe，空格转为 %20。
  4. 根据规则选择 HEAD、GET 或显式方法，使用 requests-futures 并发。
  5. 把响应映射为状态，通知终端，再按选项写 TXT/CSV/XLSX。

源码锚点：sherlock_project/sherlock.py 的 sherlock() 与 main()；sites.py 负责清单，result.py 定义状态。

04

一个站点规则到底写了什么？为什么还要 urlProbe？

站点清单是“探测适配器”：展示 URL、探测 URL、用户名约束和响应判据都可以分别配置。

"LocalMessage": {
  "url": "http://127.0.0.1:8765/message/{}",
  "urlMain": "http://127.0.0.1:8765/",
  "errorType": "message",
  "errorMsg": "PROFILE_NOT_FOUND",
  "username_claimed": "learner_demo"
}
  • url 是用户名资料页模板；urlMain 是站点主页。
  • urlProbe 可让程序检查另一个端点，同时保留给人看的资料 URL。
  • regexCheck 先排除站点不允许的用户名，减少无意义请求。
  • errorType 决定用状态码、错误正文还是重定向响应解释结果；request_method 与 request_payload 支持更复杂端点。
维护成本就在这里：网站改 URL、改文案、改跳转或加 WAF 后，旧规则仍可能运行，却开始稳定地产出错误结论。
05

status_code 判定怎样工作，为什么 429 不能叫“未找到”？

当前实现先倾向 Claimed；命中 errorCode 或落到非 2xx 时可改判 Available。429 因而可能被误写成“未找到”。

代码还允许 errorCode 指定单个或多个“未找到”状态；未指定时，非 2xx 会进入 Available 分支。这是站点规则启发式，不是 HTTP 标准对账户状态的保证。

响应常见含义不能直接推出
200服务器成功返回内容一定是目标用户资料页
404当前路由未找到资源用户名一定可注册
429请求过多或触发配额账户不存在 / 可注册
403拒绝访问，可能是权限或 WAF账户不存在
实验结论：429 是“我无法在这次请求中可靠判断”的强信号。更诚实的报告应把它单独列为受限/未知，而不是 Available。
06

message 与 response_url 又怎样判？200 为什么也会“未找到”？

message 看错误文案是否出现；response_url 禁止跟随重定向后看原始响应。两者都与只看状态码不同。

  • message：如果 errorMsg 出现在正文，判 Available；没有出现则判 Claimed。本站实验里，missing 页虽然 HTTP 200，但含 PROFILE_NOT_FOUND，所以正确识别“软 404”。
  • response_url：当前核心实现关闭重定向，2xx 判 Claimed，其他状态判 Available。missing 夹具返回 302 到登录页，所以判 Available。
  • 组合规则：errorType 可为数组，代码依次评估 message、status_code、response_url，后评估的特定分支可修订先前结果。
脆弱点：message 的“没有错误文案”不等于“有目标资料”。本地 429 页面只有 RATE_LIMIT，因此报 Claimed；由于夹具真值为存在，这次是碰巧命中而非可靠证明。真正误报也在实验中出现：missing_demo 的 LocalWaf 返回 404，却因正文不含指定 errorMsg 而报 Claimed。
07

Claimed、Available、Unknown、ILLEGAL、WAF 各是什么意思？

五种状态描述“本次规则探测的结果”，不是五种账户所有权结论。

状态本次实测正确解读
Claimedlearner_demo 返回 200该 URL 满足命中规则，仍需复核页面
Available404、302，也有 429只表示未命中；不能一律翻译成“可注册”
Unknown0.4 秒 timeout证据不足，保留上下文与错误类型
ILLEGALbad name 不匹配 ^[a-z_]+$站点规则不允许；本次没有发请求
WAF403 + challenge 指纹机器人防护干扰判断，不应强行判有/无

这与 可逆派生状态 相通：新证据到来时应能修订启发式结论，尤其不能让“未命中”覆盖 Unknown 或 WAF。

08

误报、漏报、限流与 WAF 为什么必须一起学？

因为同一次受限响应会沿不同规则走向相反结论；“程序有输出”与“输出可信”是两件事。

误报是把不存在或无法判断的页报成 Claimed；漏报是把存在的页报成 Available。常见根因包括软 404、错误文案变化、登录墙、地区差异、WAF、限流、超时和规则过期。

  • 在本次核对的 sherlock.py 主请求路径中，未见根据 Retry-After 自动退避或站点级 QPS 限速；timeout 只限制等待。
  • WAF 检测依赖代码中的特定响应指纹，而且需要能读到正文；它不是通用防护识别器。
  • 工程上应缩小站点、降低并发与频率、遵守站点规则、保存原始状态，无法判断就标 Unknown，而不是用代理绕过防护。
不要“修”成盲目重试：对 429 立即高频重试会加重限流。先停止、记录、按站点允许的方式等待或稍后人工作自查。
09

TXT、CSV、XLSX 输出怎样选择，怎样保留审计证据？

给人快速看用 TXT；逐站复核用 CSV + --print-all；表格交付用 XLSX。审计还需要命令、版本和原始日志。

本版本 CSV 字段为 username,name,url_main,url_user,exists,http_status,response_time_s。默认偏向只输出 Claimed；本实验加 --print-all，所以 Available、Unknown、ILLEGAL、WAF 也进入 CSV。

选项本版本实测/代码行为审计提醒
--txt启用文本文件，写 Claimed URL 与计数丢失未命中与错误上下文
--csv写逐站结构化行配合 --print-all 保留负例
--xlsx生成 Excel，URL 用 HYPERLINK不应把表格当身份背书
--output / --folderoutput分别控制单用户名文件/多用户名目录CSV 目录与 TXT 选项需一起核对
本实验证据链：上游提交 + 本地规则 + 命令输出 + CSV + 环回请求日志 + 自动断言。只有“找到一个 URL”远远不够。
10

怎样把它用于自己的公开账户自查，而不越界？

把范围锁在自有账户或本地桩，少请求、看原始页面、尊重站点规则；不批量枚举他人，不绕过防护。

  1. 明确对象：只列自己的公开用户名；研究规则时使用本指南的本地 JSON 与桩。
  2. 缩小范围：用 --site 选必要站点，不为了“数量好看”扩大请求面。
  3. 保存证据：记录版本、时间、站点、HTTP 状态和判定，保留 Unknown/WAF。
  4. 人工复核：打开自己的公开页面确认；同名页面仍不自动等于本人。
  5. 尊重限制：遇 429、WAF、登录墙就停止或按站点允许方式稍后处理，不绕过、不攻击。
能力边界：Sherlock 可帮助你整理自有公开账户线索、学习 HTTP 适配器和维护站点规则；它不能证明人物身份、发现私密账户或保证清单完整。

这个项目给我什么：5 项可带走能力

1. 自有账户公开面清单在合法授权与站点规则内，对自己的公开用户名做小范围核对；结果只作复查入口。
2. 读懂站点适配器能解释 URL 模板、正则、状态码、正文与重定向规则，知道规则为何需要维护。
3. 用本地桩做回归无需触达真实网站，即可构造 200/404/429/WAF/超时，验证程序分支与测试敏感度。
4. 识别误报与漏报不会把 200 当存在、404 当可注册、429 当未找到，也不会把 Claimed 当同一人。
5. 留下可审计输出用 CSV、终端日志、请求日志和版本号还原“为何得出这个状态”，而不是只交一张命中截图。
不能带走的能力没有身份归属证明、全互联网覆盖、私密信息访问、真实站点准确率认证或防护绕过能力。
建议定位：把 Sherlock 当作“清单驱动的公开 URL 探测框架”来学习，比把它当“一键人物搜索器”更准确，也更能复用其中的工程知识。
