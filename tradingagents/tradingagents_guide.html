一、疑问解答（14 问）

Q1

TradingAgents 一句话是什么？

它把一次"该不该买这只股票"的决策，拆成一家虚拟交易公司里 12 个 LLM 员工的流水线协作：4 个分析师分头调研 → 多空研究员互相辩论 → 交易员下提案 → 激进/保守/中性三人风险辩论 → 组合经理拍板。出自 arXiv 论文 2412.20138（AAAI 2026），作者 Tauric Research。
类比：你知道的[[多智能体协作]]是"几个 agent 分工干活"，TradingAgents 是把它做到金融决策上，并且辩论（debate）是核心工序——不是各写各的报告，而是真吵起来。
Q2

为什么要模仿交易公司的组织架构，而不是单 Agent 一次问答？

单 Agent 问一次"NVDA 能买吗"有三个毛病：①视角单一（一个 prompt 装不下基本面+情绪+新闻+技术面四套专业工具链）；②没有对抗（模型倾向于给一个自信的答案，没人唱反调）；③无法审计（错了不知道错在哪一环）。组织架构把"信息收集 / 观点形成 / 观点对抗 / 决策 / 风控"五件事强制分开，每一环都有独立报告留痕。论文实验显示多空辩论能显著减少单 Agent 的过度自信偏差。
Q3

12 个角色在 LangGraph 里是怎么接线的？

整个系统是一张 StateGraph（LangGraph 的状态图：节点=一个步骤，边=步骤间流转，全体共享一个状态字典）。实测拓扑（见实验 E2）：16 个节点、29 条边。接线逻辑：START 同时分叉给 4 个分析师（并行）→ 全部完成后汇入 Bull Researcher → 条件边在多空之间来回 → Research Manager → Trader → 三个风险角色条件边轮转 → Portfolio Manager → END。
🔗 已学过 [[LangGraph与Agent编排]]、[[多智能体协作]]：这张图就是它们的金融实战版。新看点是"分析师并行分叉 + 两段辩论环"的混合拓扑。
Q4

4 个分析师并行跑，怎么避免互相覆盖对方的结果？

这是 v0.5.2 最新改进。每个分析师不是直接挂进大图，而是编译成一个私有子图：模型和工具调用在自己的私有消息历史里循环，最后只把报告文本写回共享状态的一个专属键（output_schema 只暴露一个字段）。所以并行线程互不可见对方的工具报文。
_analyst_graph(spec, agent, max_tool_rounds): graph = StateGraph(AgentState, output_schema=TypedDict(..., {spec.report_key: str})) # 工具轮超过 max_tool_rounds → 强制注入 WRAP_UP 消息要报告（防死循环打爆递归上限）
还有兜底：分析师赖着不停调工具，wrap_up 节点会数它调了几轮，超限就塞一条 HumanMessage 勒令交报告（issue #1420 的修复）。类比[[多Agent协作乱序竞态]]：解法同源——私有作用域 + 只回传约定字段。
Q5

多空研究员的"辩论"到底怎么实现？

没有魔法：就是一个条件边路由器 + 计数器。共享状态里有 investment_debate_state，含 count（已发言次数）和 current_response（谁刚说完）。路由规则（实测，见实验 E4）：Bull 说完→Bear 接；Bear 说完→Bull 接；count ≥ 2×max_debate_rounds → 交给 Research Manager 收官。max_debate_rounds=1 时完整序列是 Bull→Bear→Bull→Research Manager（Bull 先手，所以多空各 1 次共 2 轮）。Research Manager 不是裁判打分，而是写出一份综合双方论点的投资计划（investment_plan）。
Q6

风险辩论为什么是三个人？和多头空头有何不同？

多空辩论辩的是"该不该做"（方向），风险辩论辩的是"做了会怎样死"（下行）。三个风险角色的立场是Aggressive 激进（支持扩大敞口）、Conservative 保守（强调回撤/流动性）、Neutral 中性（对冲与执行细节）。路由同理：Trader 固定先咨询 Aggressive，然后 Conservative→Neutral 轮转，count ≥ 3×max_risk_discuss_rounds → Portfolio Manager。实测序列：Conservative→Neutral→PM（实验 E4）。三方出场保证风控不是一个人的独角戏——激进观点也必须被记录在案。
Q7

"决策 → 结算 → 反思"的记忆闭环怎么运转？

这是 TradingAgents 最有产品感的设计，一个 append-only 的 markdown 记忆日志走三步： ① store_decision：决策落盘，标签 [日期|代码|评级|pending]；② 结算：持有窗口走完后，用真实行情算出 raw_return 和 alpha（相对区域基准的超额收益），原子写回标签变成 [+3.1% | +1.2% | 5d]；③ Reflector：LLM 把"决策+结局"浓缩成 2-4 句教训，下次分析同一只票时，这些历史教训会被注入 prompt——相当于这个框架有"经验值系统"。
[2026-01-09 | NVDA | Overweight | +3.1% | +1.2% | 5d] ← 实验E5真实输出 DECISION: BUY, Overweight... REFLECTION: 教训：样本窗口太短，别把周线波动当日线信号。
重复写入同一 (日期,代码) 会被幂等挡掉（实测写 2 次只有 1 条），结算用 temp-file + os.replace() 原子写，崩了不坏账本。类比[[JSONL事件日志与折叠模型]]：同样是只追加事件日志，只是这里存的是"决策事件"。
Q8

怎么防止"未来函数"（用未来数据做过去的决策）？

回测领域的经典毒瘤——你已知的[[事件驱动回测]]核心就是防它。TradingAgents v0.5.0 起全面落实 point-in-time 完整性：每一条带日期的数据路径都只返回"分析日当天或之前发布"的数据：财报按 SEC EDGAR 的申报日（不是报告期！）供数；FRED 宏观、社交媒体、新闻都有 look-ahead 过滤；回测网格里每个 (ticker, date) 单元只看得到该日期前公开的信息。连记忆日志都做 point-in-time：反思教训只来自"该日期之前已结算"的条目。
Q9

12 种数据需求，是怎么路由到 7 家免费数据源的？

vendor router：一张 VENDOR_METHODS 表把"方法名 → {供应商名: 函数}"映射起来，分析师只声明"我要 get_fundamentals"，路由层决定去 Yahoo 还是 SEC EDGAR 拿。实测 12 个方法全部被命中（实验 E3）：
数据供应商
行情/OHLCV、技术指标、新闻yfinance + stockstats（免费）+ Alpha Vantage
财报三表/内部人交易SEC EDGAR（按申报日供数）+ yfinance
社交媒体情绪StockTwits + Reddit
宏观指标FRED（免费 key）
事件概率Polymarket 预测市场
全部免费，跑通整个框架只需要一个 LLM 的 API key。数据缓存进本地（data_cache_dir），重跑不重复请求。
Q10

LLM 输出是自由文本，怎么保证"评级"解析得出来？

两层保险。① 结构化输出：Research Manager / Trader / Portfolio Manager / 情绪分析师走 with_structured_output，直接吐 Pydantic 模型（枚举类型 PortfolioRating 从根上杜绝"评分格式五花八门"）；供应商不支持时自动降级自由文本。② rating 完整性校验：自由文本路径里用五档制 Overweight / Bullish / Neutral / Bearish / Underweight 正则硬解析，解析失败进 review 状态而不是悄悄变成别的信号。决策信号 signal、state["final_rating"]、记忆日志里的 rating 三处必须一致（实验 E3 断言验证过）。类比[[Agent输出协议契约]]。
Q11

它没有现金账本，怎么评价自己"决策得好不好"？

backtest.py 开头有一段非常诚实的 scope 声明："这评估的是决策质量，不是组合模拟器；把评级变成真实订单需要数量、成交价、现金账本，这里都没有；硬造一个就会把执行模型藏在评估工具后面"。所以它的回测是：同一个图跑 (ticker, date) 网格 → 每格一个决策 → 记忆日志就是结果表 → 用 raw/alpha 回报结算打分。各格独立，没有仓位滚动。这是少见的"知道自己边界在哪"的开源项目设计。
Q12

跑到一半 LLM 挂了怎么办？

LangGraph 的 checkpoint（SQLite）持久化：每过一个节点存一次状态。LLM 调用失败抛异常后重跑，只补做没完成的调用，已完成的节点直接从存档恢复（repo 测试实测：fail_at=12 中断后续跑，新增调用数恰好等于全量调用数减去已完成数）。CLI 还支持 checkpoint resume 交互式续跑。类比[[Checkpoint存档与持久执行]]——同构思路：状态外置 + 断点续传。
Q13

我能拿它去实盘买股票吗？

不能，也不该。三重原因：①框架定位：官方 disclaimer 写明 research purposes only；②工程缺口：无仓位管理、无成交模拟、无手续费滑点（参见已学[[交易成本与鞭打效应]]——真实交易里这些足以吃掉全部 alpha）；③模型局限：决策质量随 backbone LLM、温度、数据质量剧烈波动，论文自己的回测也只是研究性质。它真正能给你的是一套可复用的"多智能体决策流水线"工程范式——把分析师/辩论/风控的角色拆分搬到任何需要"调研→对抗→决策"的领域都成立（竞品分析、投资尽调、技术选型）。
Q14

它和 NautilusTrader 这类回测引擎是什么关系？

完全互补，管的不同段。你已学的[[事件驱动回测]]（NautilusTrader）管"执行层"：纳秒级撮合、手续费、保证金、订单生命周期——回答"这个策略交易成本后还赚不赚钱"。TradingAgents 管"决策层"：回答"这个时点该看多还是看空"。TradingAgents 自己明说没有执行模型，所以真要严肃研究，产出信号后应该丢给 NautilusTrader 这类引擎去做含成本的真实回测——两者接起来才是完整闭环（决策→执行评估），这也是一个不错的进阶 DIY 方向。

二、这个项目给你什么（能力清单）

🎁 你能拿走的东西：

实验 E5 · 记忆日志：存储 → 幂等 → 结算 → 反思
操作：同 E4 脚本后半段。目的：验证 Q7 的三步闭环。
✅ 实测结果：同一 (2026-01-09, NVDA) 写 2 次 → 只剩 1 条（幂等）；结算后标签 [+3.1% | +1.2% | 5d]、pending→False、REFLECTION 段原子写入。落盘 markdown 全文见实验输出。
