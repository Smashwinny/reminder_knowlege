微信 AI 记忆库 wechat-ai-memory

把散落在微信里的对话，整理成 Agent 能读、能检索、能引用的本地记忆档案
仓库 ikevss/LOGO127 · wechat-ai-memory 版本 v0.3.7-alpha 协议 MIT 平台 Windows 10/11 × 微信 4.x 技术栈 Python 3.11+ · PySide6 · Frida · ReportLab · faster-whisper 学习日期 2026-10-03
一句话微信 AI 记忆库是一个本地优先的开源 Windows 工具：直接读取本机微信 4.x 的聊天记录（也支持纯 JSON 数据源），按会话 / 日期 / 关键词筛选后，导出成 PDF + Markdown + 结构化 JSON 三件套——目的不是"备份聊天"，而是给 AI Agent 准备一份可引用、可追溯的个人上下文记忆。

疑问即目录：10 个问题讲透它

Questions First —— 工科毕业生的视角
Q1
这是什么？解决什么问题？

Agent 时代有个尴尬现实：模型能不能帮上忙，取决于它懂不懂"事情的来龙去脉"。项目决策、需求变更、关键承诺……这些上下文不在项目管理工具里，而是散落在微信私聊和群聊里。你给模型几句临时描述，它只能靠猜。

这个项目的定位一句话：微信 = 你的最大上下文仓库，但它对 Agent 是个黑盒 → 这个工具把黑盒变成 Agent 可读的档案。导出的 JSON 里每条消息都带 id、sender、timestamp、reply_to，模型引用时能精确回溯到原文——这就是"可追溯"的含义。

Q2
为什么需要它？没有它之前人们怎么做？

现有的路各有毛病：

老办法痛点
付费闭源导出工具要花钱，且聊天记录上传到谁的服务器无法独立审查——心里没底
手工复制粘贴 / 截图几百条消息不可持续，截图里的文字模型没法直接检索
口头向 Agent 复述背景转述必有遗漏和失真，承诺、结论这类细节最容易丢

它的差异化主张就三条：开源免费（MIT）、本地优先（无遥测无远程 API）、数据不上传。当前版本先把"可靠的提取与归档"这一层做扎实，语义检索 / RAG / MCP 都排在路线图上（见 Q9）。

Q3
它是怎么做到的？整体架构长什么样？
图 1 · 双数据源汇入统一 ChatSource 接口，筛选后分流三格式导出

架构上最值得学的一手是适配器隔离：微信数据适配器（sources/wechat4_*.py 六个模块）和渲染、导出模块完全解耦，两者只通过 ChatSource 抽象接口对话。就算哪天微信改了内部格式把适配层打挂，JSON 数据源和整条导出管线照样独立存活——这也是我们本批次实验敢跑的前提（只用 JSON 入口，绝不碰真实微信）。

Q4
微信的数据到底是怎么被读出来的？

微信 4.x 的本地数据库是 SQLCipher 整库加密的，密钥只存在于运行中的微信进程内存里。这个项目的读取流程：

图 2 · "进程内取钥 → 副本上解密"路线：原数据库文件从头到尾不被修改
对比已学概念这与 vault 里 [[CleanRoom只读读取器]]（wechat-intelligence-hub 的路线）是同一目标的两条技术路线：CleanRoom 坚持不碰目标进程，密钥材料由用户本人提供（授权问题）；本项目走 Frida 动态注入拿密钥——自动化程度高（用户零操作），但代价是要注入微信进程、被安全软件盯上、且微信升级随时可能打挂。两条路线的隐私底线一致：只读、密钥不落盘、临时文件用完即删。
Q5
导出的 JSON 到底长什么样？Agent 怎么"读"？

所谓"Agent 可读"，核心就是这份规范化（normalized）JSON。我们用官方虚构样例 demo_chat.json 实测导出，结构如下：

{
  "version": 1,
  "conversations": [{
    "id": "eco-project", "name": "ECO 项目讨论群", "kind": "group",
    "messages": [{
      "id": "m004",                        // 稳定消息 ID（路线图 v0.4 会强化去重）
      "sender": "张三", "timestamp": "2026-08-21T09:22:00",
      "type": "text",                      // text / image / file / voice / system
      "content": "图里有两个信息需要复核：……",
      "is_outgoing": false,               // 谁在说话：本人 or 对方
      "reply_to": "m003"                   // 引用回复 → 消息间的引用链
    }, ...]
  }]
}

三个设计点：① is_outgoing 区分"我说的"和"别人说的"——对 Agent 理解立场至关重要；② reply_to 保留消息引用链——"张三那句话是针对哪张图说的"不再是悬案；③ type 五类全覆盖，图片/文件导出后指向 _assets 目录的相对路径。这其实是给 LLM 喂上下文时最省 token 又最不丢信息粒度的中间格式。

Q6
语音和图片这些"非文字消息"怎么处理？

🔊 语音（SILK 格式）

微信语音是 SILK 编码（微信自家的语音编解码格式，普通播放器打不开）。项目用 silk-python 解码，再交给 faster-whisper（本地运行的开源转写模型，首次需联网下载约 500 MB 的 small 模型）转成文字并缓存——转写全程在本机，语音不上传。

🖼 图片（V2 / WXGF）

微信 4.x 的图片是自有封装格式（WXGF），需要"原图恢复"；恢复后再做 EXIF 方向修正（按拍摄方向字段转正，避免 PDF 里横躺），输出预览图 + 300 DPI 高清独立页。实测 PDF 里图片页还带"来源会话/发送者/时间"的元数据头。

要点语音转写缓存和模型都存 %LOCALAPPDATA%\WeChatAIMemory，首次下载模型后可完全离线使用——这延续了"本地优先"的承诺。

Q8
隐私红线是怎么设计的？
数据行为是否发生实现机制
上传聊天内容 / 图片 / 导出文件否无遥测、无远程 API、无 AI 云请求
写密钥到磁盘否Frida 内存取钥，进程结束即消失
修改原始微信数据库否只解密"临时副本"，原库只读
发 / 撤 / 改微信消息否纯读取，无写通道
临时文件残留否数据源关闭时删除临时库与恢复图片
但要注意① 未做代码签名，SmartScreen 会拦；Frida 注入行为可能触发安全软件告警——只从官方 Release 下载。② "数据不上传"承诺目前靠自律 + 开源可审查，alpha 阶段没有第三方审计背书。③ 本批次实验的纪律就是这条红线的实践：只用官方虚构 demo 和自造样例数据，绝不连接真实微信库。
Q9
现在能干什么、不能干什么？

已经能（当前能力）：

本机微信读取（只读副本） 会话/日期/关键词三重筛选 文本·图片·文件·语音·系统消息 语音本地转写（whisper） PDF/MD/JSON 三格式导出 GUI + CLI + JSON 备用入口

还不能（明确的边界）：AI 问答、RAG 语义检索、OCR、向量索引——它现在是"可信数据层"，不是"智能层"。路线图：v0.4 持久记忆库+增量同步 → v0.5 SQLite FTS5 全文检索 → v0.6 结构化实体（人物/项目/决策）→ v0.7 带引用的本地 AI 问答 → v0.8 只读 MCP 接口。也就是说，"变成真 Agent 记忆"是它自己认定的终局，只是当下先把地基打牢。

Q10
怎么跑起来？普通用户和开发者各一条路

普通用户（连真微信）

  1. Release 下载 WeChatAIMemory-Portable.exe（免安装，内含全部运行库）
  2. 登录微信 4.x → 点"连接微信"→ 微信重启后 5 分钟内确认
  3. 选联系人 / 日期 / 关键词 → 生成记忆档案

开发者（只跑 JSON 入口，本次实验路线）

  1. git clone → 建 venv
  2. 装依赖（JSON 入口最小集：Pillow + reportlab + zstandard + pycryptodome）
  3. python -m wechat_context_exporter --source demo_chat.json ...
实测坑包的 __init__.py 会连带 import 微信适配层 → 即使你只想用 JSON 入口，也必须装 zstandard 和 pycryptodome，否则 ModuleNotFoundError。Frida 和 faster-whisper 这两个大件倒是可以不装（用不到就不触发）。

体检"Agent 可读性"：规范化 JSON 的字段契约

操作：用 Python 检查导出 JSON 的字段完整性与引用链：

import json
d = json.load(open("my-context.json", encoding="utf-8"))
msgs = d["conversations"][0]["messages"]
print([m["id"] for m in msgs])                     # ['n001'..'n005']
print([m["id"] for m in msgs if "reply_to" in m])  # ['n003'] 引用链在

目的确认 id/sender/timestamp/type/content/is_outgoing/reply_to 六要素齐全——这才是"Agent 能引用原文"的合同 ｜ 检测

✅ 预期结果（实测）：六字段全在；is_outgoing 布尔正确；引用链无损。结论：数据层确实"可信、可追溯"，配得上它 README 里"先做好地基"的定位
