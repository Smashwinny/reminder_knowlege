逐条解答

Q1

这条推文背后发生了什么？

推文作者 kabikabi（GitHub: jackwener）说"太多人找我要 wx-cli 了，再度 public 一下"——背景是：原版 jackwener/wx-cli 在 2026-07-15 被 GitHub 以 DMCA 理由封锁（投诉方指向微信，gh API 实测返回 451 Repository access blocked (reason: dmca)）。作者随后把代码以 wx-cli-again 名义重新公开（Apache-2.0，771 stars），并声明灵感来自 ylytdeng/wechat-decrypt。

诚实记录：本指南学习对象是公开的 jackwener/wx-cli-again；原仓库的完整历史已不可访问，两者差异只能从 README 自述（"fresh start from wx-cli"）推断。
Q2

wx-cli-again 是什么？解决什么问题？

一句话：一个 Rust 写的单一二进制命令行工具，查询/解密/导出你自己电脑上的微信 4.x 本地数据——会话、聊天记录、全文搜索、联系人、群成员、朋友圈、公众号文章、收藏、统计、附件图片导出，全部输出 YAML/JSON，还专门给 AI Agent 设计了一套 SKILL.md（npx skills add 一键装进 Claude Code / Cursor / Codex）。

没有它之前：想翻自己的微信聊天记录只能靠微信自带搜索，弱、慢、无法批量导出。它把"个人数据自己拿回来"做成了类 Unix 的命令行体验：wx history "张三"、wx search "关键词"、wx export "AI群" --format markdown。

类比已学项目：它和 [[wechat-ai-memory]]（导出 PDF/JSON 喂给 Agent）、[[wechat-intelligence-hub]]（情报信号引擎）是同一层的工具——但 wx-cli 更"基建"：不预设记忆/情报用途，只做通用数据访问层 + 毫秒级查询服务。
Q3

为什么查询能毫秒级？——daemon 缓存架构

核心设计：CLI 本身不干活，只是客户端。首次查询时自动拉起后台 wx-daemon 进程，daemon 解密数据库后把明文库 + mtime 索引持久化到 ~/.wx-cli/cache/。之后每次查询通过 Unix socket（Windows 是 named pipe）发请求，mtime 没变就直接复用缓存，毫秒级返回。

对比：wechat-ai-memory 每次导出都要重新解密一遍；wx-cli 把"解密"摊销到 daemon 的生命周期里——查 100 次只解密 1 次。

Q4

SQLCipher「在线打开」和「全量解密」差在哪？

微信 4.x 的每个 .db 都是 SQLCipher 4 整库加密（AES-256-CBC + HMAC-SHA512）。传统做法（如 [[进程取钥与副本解密]] 描述的 Frida 路线）：拿到 32 字节密钥 → 把整个库解密复制一份 → 在副本上查询。wx-cli 的做法更激进：用 rusqlite 的 bundled SQLCipher 直接对加密库"在线打开"——PRAGMA key 以 raw-key 语法 x'<64hex>' 喂进去（跳过 PBKDF2），SQLite 每读一页就地解密，不落任何明文副本；只有在线打不开时才降级为解密到 cache。

源码依据：src/crypto/sqlcipher.rs 的 open_encrypted_readonly()——只读标志 + PRAGMA query_only = ON，先尝试 key-only，失败再回退 key+salt 拼接。

类比：全量解密像"把整本外文原著翻译后另存一个文件"；在线打开像"带着词典读原版"——页级（page）随读随译。

Q5

message_N.db 分片是什么结构？

微信把聊天记录按时间和体量切成多个分片库：message/message_1.db、message_2.db…还有独立的 biz_message_*.db（公众号文章）和 message_resource.db（附件索引）。每个分片有独立的 32 字节密钥——旧消息所在的分片可能长期不被微信加载，密钥也就迟迟不出现在内存里，这就是"冷分片缺钥"问题。wx-cli 的对策是 meta.unknown_shards：查询结果里明确告诉你哪些分片没密钥、结果可能不全（possibly_stale 状态），而不是悄悄返回残缺的"假完整"。

Q6

聊天图片 .dat 为什么有三档解码？

微信存的聊天图片不是 jpg/png 原文件，而是 msg/attach/.../*.dat 加密文件，而且历史上换过三次加密方案，工具必须兼容全部：

档位文件头 magic算法密钥来源
legacy XOR无（靠内容反推）全文件单字节 XOR用已知图片 magic 反推
V1 固定 AES07 08 V1 08 07AES-128-ECB (PKCS7)硬编码常量 cfcd208495d565ef（= md5("0") 前 16 位）
V2 AES + XOR07 08 V2 08 07三段拼接：AES-ECB + 明文 raw + 单字节 XOR平台派生 image AES key（macOS 从 kvcomm cache / 暴力枚举 uin；Windows 扫 WeChat.exe 内存）
Q7

legacy XOR 没有 magic，怎么知道密钥？

妙招：用"正确答案"反推。图片格式都有固定文件头（PNG 以 89 50 4E 47 开头、JPG 以 FF D8 FF 开头…），假设明文第一个字节是 magic[0]，那么 XOR key = 密文[0] ⊕ magic[0]；拿这个 key 去验 magic 剩余字节，全部命中才算数。按 magic 长度降序尝试（PNG 4 字节优先于 JPG 3 字节），避免短 magic 的假阳性；BMP 只有 2 字节 magic，还要额外校验文件头里的 bf_size/bf_offset 合理性。

本批次实验 1 实测验证：合成 PNG 用任意 key 0x5A XOR 成伪 .dat，上游真实源码 dispatch() 自动反推出 key 并无损还原 87 字节原图（见动手实验）。
Q8

meta wrapper 是给谁看的？

history/search/sessions 等命令的 stdout 不是裸数组，而是 {data, meta} 包装：meta.status（ok / possibly_stale…）、meta.unknown_shards、chat_latest_timestamp vs session_last_timestamp（对账：session.db 里微信自己记的最新时间若领先于查到的，说明漏消息了）。这是写给 AI Agent 看的"数据新鲜度声明"——agent 消费输出时自己判断能不能信、缺了哪块，不用人类盯 stderr。配套还有 SKILL.md / AGENTS.md，让这个 CLI 可以被 Claude Code 当技能安装。

Q9

「不需要关 SIP」是真的吗？

按 README 与 src/scanner/macos.rs 注释：取钥两阶段（① task_for_pid 进程内存扫描搜 x'key+salt' 模式；② LLDB hook CCCryptorCreate 补冷分片密钥）都不依赖关闭 SIP——SIP 保护的是系统组件，不是"能不能读微信内存"的开关。需要的是本机 GUI Terminal + sudo（Hardened Runtime 官方包）+ 在"隐私与安全性 → 开发者工具"里授权终端。

诚实记录：本机是 Windows 11，没有 macOS/SIP/LLDB 环境，该声明无法在本机复验，只转述源码注释与 README。Windows 版取钥是扫 WeChat.exe 内存匹配 V2 key 候选，同样未在本机复验（无微信 4.x 测试环境）。

Q11

隐私与法律红线在哪？

  • README 免责声明：仅限解密自己的微信数据，用于学习研究；原仓库被 DMCA 下架就是越过红线的代价写照。
  • 技术层护栏：数据库只读打开 + PRAGMA query_only = ON；密钥存本机 ~/.wx-cli/all_keys.json，不联网。
  • 本批次学习全程零真实微信数据：实验只用 Pillow 合成的 87 字节 PNG 走编解码往返（对比 wechat-ai-memory / yichen-skills 两批次的同一红线做法）。
Q12

现在能装吗？

现实有点绕：README 宣称的"源码与发布仓库"botiverse/wx-cli 当前是 private，匿名 curl/旧 npm 包 @jackwener/wx-cli@0.3.0 拿不到新二进制。可行路径只有一条：源码自编译——而本批次已在 Windows 11 实测走通（见下节实验，含 MinGW 坑）。Windows 上微信 4.x 取钥支持是"扫 WeChat.exe 内存匹配 V2 候选"，比 macOS 路线年轻，稳定性预期低一些。

这个项目给我什么能力

  • 秒查自己的聊天历史：wx history "张三" -n 2000、按时间段过滤、全文 wx search——一旦配好密钥，比微信自带搜索强一个量级。
  • 给 Agent 接上微信数据源：meta wrapper + SKILL.md 是专门为 LLM 消费设计的，装上技能后可以让 Claude Code 直接查你的聊天上下文。
  • 导出归档：markdown / JSON 导出任意会话，时间范围可控，适合做项目复盘材料。
  • 朋友圈/公众号/收藏检索：三个常被忽视的本地数据源（sns-feed、sns-search、biz-articles、favorites）。
  • .dat 图片抢救：三档解码器兼容微信历代图片加密，能把自己的聊天图片批量还原成 jpg/png。
  • 学习样本：即使不用微信，它的"daemon 缓存 + 在线解密 + AI 友好输出"架构也是本地数据 CLI 的范本（本批次 decoder 实验可直接搬运其源码）。

实验结论与边界

  • 已实证：源码可编译（MSVC 路线）、二进制可运行、上游图片解码器对合成数据的往返与负向护栏全部正确、daemon 架构从源码读通。
  • 未复验（诚实记录）：macOS SIP/LLDB 取钥、Windows 扫 WeChat.exe 取钥、真实 SQLCipher 库在线打开——三者都需要真实微信环境，本机不具备，只做了源码级研读。
