01

Qdrant 是什么？"向量数据库"和 MySQL 有什么本质区别？

一句话：Qdrant 是一个专门存放"意义"、并按"意义相似"来检索的数据库。 它读作 quadrant（象限），用 Rust 写成，既提供带 API 的网络服务，也在 2024 年后成为向量数据库领域口碑最好的开源项目之一。

MySQL 按"精确匹配"检索，Qdrant 按"语义距离"检索——这是两种完全不同的提问方式：

  • 问 MySQL：“title 字段等于《星际穿越》的行是哪几行？”——答案非对即错，没有"差不多"。
  • 问 Qdrant：“哪些内容最接近‘在太空深处寻找人类的未来’？”——答案是一张按相似度排序的榜单。
图 1-1　同一个提问动机，两种完全不同的检索哲学
它同时保留了传统数据库的本领：每个点可以带 payload（元数据）并做条件过滤——所以 Qdrant 自我介绍时强调 "vector database" 而不只是 "vector search library"（对比第 11 问的 FAISS）。
02

Q2｜"向量 / embedding"到底是什么？文字怎么变成一串数字？

术语卡向量（vector）：一串固定长度的数字，如 [0.12, -0.87, …]。 embedding（嵌入）：把一段内容（文字/图片/音频）"压"成这样一个向量的过程和结果。

关键直觉：embedding 模型把"意思相近的文本"映射到高维空间里相邻的位置。 这不是把字编码成编号——"猫吃鱼"和"小猫捕食鱼类"几乎没有共同字符，但它们的向量夹角极小；而"猫吃鱼"和"今天股市大涨"的向量几乎垂直。

图 2-1　embedding：把"意思"变成高维空间中的"位置"

为什么一串数字能代表"意思"？ 可以类比坐标：地图上两个点的 (经度, 纬度) 近，两地就真的近。 embedding 模型把每段文本放到一个 512 维（本实验用的 bge-small-zh 是 512 维）的"意义地图"上—— 训练时模型见过海量文本，学会了把"同义""相关"的内容放到邻近坐标。维度本身没有人工含义，是模型从数据里学出来的压缩坐标。

记忆锚点：embedding = 意义的坐标；向量数据库 = 按坐标距离找邻居的仓库。

03

Q3｜为什么需要它？没有向量数据库之前，"找相似"怎么做？

人类的"找相似"技术一共进化了四代：

世代做法致命弱点
① 关键词 / LIKE字符串匹配，如数据库 LIKE '%猫%'换个说法就找不到："猫吃鱼"搜不到"小猫捕食鱼类"
② 倒排索引（Elasticsearch / BM25）把文档拆成词，建"词 → 文档列表"的字典仍然基于字面，同义词、换说法依然失配
③ 自己算向量自己比把所有向量放内存/CSV，逐条算距离取最小数据一多就崩溃：百万条 × 512 维的暴力比对既慢又占内存，还没有增删改、过滤、持久化
④ 向量数据库（Qdrant 等）专职存储 + 索引（HNSW）+ 过滤 + 增删改 + 服务化 API——（这就是本指南的主角）
图 3-1　"找相似"的四代进化：从字面到语义

本指南实验 2 会让你亲眼看到第①代和第④代的差距：三个查询用关键词搜索全部 0 条命中，Qdrant 语义搜索全部命中正确答案（见实验步骤 4 的 ✅ 预期结果）。

04

Q4｜余弦相似度是什么？凭什么一个分数能衡量"像不像"？

术语卡余弦相似度（Cosine Similarity）：用两个向量夹角的余弦值衡量方向是否一致，取值 [-1, 1]，越大越相似。

直觉：只看方向，不看长短。 两段文本哪怕一个长一个短，只要"意思指向"同一个方向，夹角就小、分数就高。

图 4-1　余弦相似度 = 比"方向"不比"长度"；右框为本机真实运行结果

除了 Cosine，Qdrant 还内置 欧氏距离（Euclid，比"直线距离"）和点积（Dot，推荐系统常用），建集合时二选一。文本 embedding 的业界默认是 Cosine。

05

Q5｜几千万条数据一条条比，不慢吗？Qdrant 怎么做到毫秒返回？

暴力比对（exact search）确实太慢。Qdrant 默认使用 HNSW（分层可导航小世界图）近似最近邻索引——用"可能错过亿点点、但快几百倍"换速度的技术，思想类似"先走高速，再走省道，最后走小巷"：

图 5-1　HNSW：每层是一张"邻居图"，查找时自顶向下逐层逼近目标

要点三个：

  • 快：几千万点也只需访问几十个节点（对数级复杂度），毫秒返回；
  • "近似"的含义：结果以 hnsw_ef 等参数权衡精度与速度——99% 的场景你感知不到差异；
  • 建索引要时间：写入后 Qdrant 在后台异步建图，点数少时（如本实验 16 条）甚至直接暴力比对，小数据本来就快。
06

Q6｜核心概念：Collection、Point、Payload 是什么？和传统数据库怎么对应？

Qdrant 的概念体系非常克制，只有四层：

Qdrant类比 MySQL是什么
Collection 集合database / table一批点的容器，创建时声明向量维度 + 距离度量
Point 点一行记录(id, vector, payload) 三元组——检索的基本单位
Payload 载荷行的其他列点附带的任意 JSON 元数据（标题、年份、来源……）
Distance 距离度量—（MySQL 没有）建集合时定死：Cosine / Euclid / Dot
图 6-1　Collection / Point / Payload 全家福——本实验 movies 集合的真实结构
为什么 vector 和 payload 分开？ 分工明确：vector 负责"像不像"，payload 负责"是不是"。 向量走 HNSW 索引做语义近邻，payload 走普通索引做精确条件过滤——两者在查询里组合使用（见第 9 问）。

Q7｜真实的文字怎么变向量？embedding 模型从哪来？

第 2 问说了"向量是意义的坐标"，但坐标由谁颁发？答案是 embedding 模型。本实验用的是 BGE-small-zh-v1.5（北京智源发布、对中文优化、512 维、模型仅约 100MB），通过 fastembed 这个库在本地 CPU 上运行：

图 7-1　数据 → embedding 模型 → Qdrant 的分工。模型与数据库是解耦的

三个工程上必须知道的规则：

  • 入库和查询必须用同一个模型——不同模型的空间坐标互不相通，混用等于拿北京坐标在纽约找路；
  • 维度由模型定死——bge-small-zh 是 512 维，建 Collection 时 size 必须一致；
  • 模型在哪跑都行——本地（fastembed / ollama 的 nomic-embed-text）或云端 API（OpenAI / 智谱），Qdrant 无感知。
⚠ 本机坑：计划用 ollama 拉 nomic-embed-text 时被 Clash fake-IP 劫持 DNS，ollama 拒绝重定向到 198.18.x.x 非公网地址。改用 fastembed（走 HTTPS_PROXY 正常下载）。你日后若复现，二选一即可。

Q8｜RAG 是什么？Qdrant 在大模型应用里站在哪个位置？

术语卡RAG（Retrieval-Augmented Generation，检索增强生成）：回答问题前先去知识库里检索相关资料，把资料塞进提示词再让大模型生成答案。

你已经在学的 langchain / langgraph 项目里，RAG 是头号应用模式，而 Qdrant 就是 RAG 链路里的"外挂记忆体"——大模型不知道你的私有文档，但可以从 Qdrant 里现查现用：

图 8-1　RAG 五步：提问 → 向量化 → Qdrant 检索 → 拼进提示词 → LLM 生成

一条产业链的位置感：ollama 跑模型（你已学）→ langchain 编排流程（你在学）→ Qdrant 存知识（本项目）——三者拼起来就是一个完整的私有知识库问答系统。Qdrant 官方甚至提供 langchain-qdrant 集成包，后续做 langchain RAG 实验时可以直接接入今天建的 movies 集合。

Q9｜"过滤搜索"是什么？为什么 Qdrant 特别强调 filtering？

真实需求几乎总是："在符合条件的那部分里，找最像的。" 比如"在 2015 年后的科幻片里找和这段简介像的"。这就是过滤搜索——payload 条件（第 6 问）和向量近邻（第 5 问）联合作战。

图 9-1　过滤搜索 = 先按条件收窄子集，再在子集内做语义搜索（本机实验 3 实测）

Qdrant 强调 extended filtering，因为它把过滤做在了索引层（称为 filterable HNSW）：是在图里"只走满足条件的路"，而不是先搜 Top-100 再把不合格的扔掉。后者在条件命中稀少时会全军覆没——先搜后滤可能一条都不剩，先滤后搜永远有答案。支持 must / should / must_not 组合，等值、范围、全文匹配都可以。

Q10｜数据量大到内存装不下怎么办？什么是量化？

算一笔账：1 亿条 × 512 维 × 4 字节（float32）≈ 200 GB——全放内存很奢侈。Qdrant 的答案有两层：

① 量化（Quantization）——把每个数变"矮"：

方式存储压缩比说明
原始 float324 字节/维1×默认
Scalar 量化1 字节/维（int8）~4×精度损失极小
Product 量化每段向量用码本编号最高 ~64×损失较大，适合超大库
二值量化1 bit/维~32×配合 oversampling 使用
图 10-1　标量量化：把"高精度小数"压成"整数刻度"，体积÷4

② 分级存储——热的放内存，冷的放磁盘： Qdrant 支持把原始向量留在磁盘（mmap），内存只放量化后的向量和索引，搜索时用量化向量粗筛、偶尔回磁盘校验原值（rescoring）。单机扛亿级向量因此成为可能。

一句话：量化省内存，分级存储省钱，HNSW 省时间——三者合体就是"亿级向量毫秒级搜索"。

Q11｜Qdrant、FAISS、Milvus、pgvector、Chroma……到底怎么选？

这些名字极易混淆，用两个维度切开就清楚了：它是"库"还是"服务"？它是"专职"还是"兼职"？

名字形态一句话定位适合
Qdrant服务（Rust）过滤能力最强的专职向量数据库生产 RAG / 语义搜索，单机到分布式
FAISS库（C++/Python）Meta 出品的索引算法集，无服务无增删改便利研究、离线批处理、嵌入自家系统
Milvus服务（Go/C++）重装 distributed 风格，组件多超大规模团队，有专职运维
pgvectorPG 插件给 PostgreSQL 加向量能力数据已在 PG、想少一个组件时
Chroma嵌入式（Python）一行代码起步的原型玩具notebook 快速试验、demo
Elasticsearch服务（Java）搜索老牌巨头后加的向量功能已用 ES 全文检索想顺带向量
初学者的务实路径：原型期用 Chroma（零部署）→ 需要真服务时上 Qdrant（单二进制 30MB 就能跑，本实验已验证）→ 数据已在 PG 就先试 pgvector。 Qdrant 对"过滤 + 向量"复合查询的支持是其最常被选中的理由（第 9 问的 filterable HNSW）。

另外它还是少数把 Rust 内存安全 + 单二进制部署 + Web UI + 三种 API（REST/gRPC/客户端）同时做齐的向量数据库——本实验用的是官方发布的 Windows 原生二进制，连 Docker 都没装。
